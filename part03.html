1. Why IP addresses exist — MAC addresses cannot scale

📍 OSI Layer 3 — Network

In Part 2 you met the MAC address (Media Access Control address): a 48-bit identifier burned into every network interface at the factory, like 3c:7d:0a:12:34:56. MAC addresses are how frames find their target within one network — the switch keeps a table of which MAC lives on which port and forwards accordingly. So an obvious question: if every device on Earth already has a globally unique MAC address, why invent a second addressing system at all? Why not route everything by MAC?

🧭 Why this exists

Because MAC addresses are flat. A MAC address tells you which device but nothing about where it is. The first half identifies the manufacturer and the rest is a serial number — two laptops bought the same day in the same shop can end up on opposite sides of the planet, with near-identical MACs. There is no geography in the number, so there is nothing to summarize: a router trying to deliver "to MAC 3c:7d:0a:12:34:56" would need a table with one entry for every device on Earth — tens of billions of rows, changing every time any phone moves between networks. No router could hold that table, and no protocol could keep it up to date. Routing needs addresses that are hierarchical and aggregatable: addresses where one short prefix ("everything starting 142.250…") can stand for millions of machines in one direction. That is exactly what the IP address (Internet Protocol address) provides — and why Layer 3 exists as a separate layer at all.

🌍 Analogy — delivering worldwide post by fingerprint

A MAC address is like a person's fingerprint: globally unique, permanent, and utterly useless for delivering a letter. Imagine addressing an envelope with only a fingerprint. Every post office on Earth would need a constantly updated directory of every fingerprint and the building it is currently in. Nobody would even try. Instead, the postal system invented hierarchical addresses: country → city → street → house number. A sorting center in Mumbai doesn't know where Frau Müller lives; it only needs to know "Germany → put it on the Frankfurt plane." Each step narrows the search, and each sorting center holds a tiny table. An IP address is the postal address of networking: the front of the number says which network (country/city), the end says which machine on that network (house number). The fingerprint — the MAC — still matters, but only for the final handover, when the local courier is standing on the right street.

This gives us the division of labor you saw at the end of Part 2, now with its full meaning:

🔑 Key point

MAC answers "which device on this wire?"; IP answers "which machine on the planet?" A frame's MAC addresses are rewritten at every router hop; the packet's IP addresses stay the same from source to destination (until NAT complicates this — section 13). You need both: IP to plan the route, MAC to execute each individual hop. Section 12 (ARP) is the glue that converts one into the other.

📜 What came before

The ARPANET's first protocol, NCP (Network Control Program), assumed one single network — addresses were essentially "which port of which ARPANET switch." The moment researchers wanted to interconnect different networks (packet radio, satellite links, Ethernets), NCP's addressing collapsed: it had no concept of "a different network over there." The fix was the Internet Protocol, whose version 4 was standardized in RFC 791 (Request for Comments 791) in 1981 — an address split into a network part and a host part, so that routers could forward on the network part alone and ignore the rest until arrival. That two-part split, refined over four decades (classes → subnets → CIDR), is still the core idea under every VPC, every Docker network, every Kubernetes cluster you will ever touch.

2. IPv4 — anatomy of an address

📍 OSI Layer 3 — Network

An IPv4 (Internet Protocol version 4) address is simply a 32-bit number. That's it — one unsigned integer. Humans are bad at reading 2398795598, so we write the 32 bits as four 8-bit groups (octets), each shown in decimal (0–255), separated by dots: dotted-decimal notation. Here is a real address — one of Google's — taken apart:

Fig 3.2 — One IPv4 address is just 32 bits: 142.250.183.78
   dotted decimal:        142     .    250     .    183     .     78

   binary octets:       10001110   11111010   10110111    01001110

   bit values:          128 64 32 16 8 4 2 1   (per octet)

   octet 1:  10001110 = 128 + 8 + 4 + 2          = 142
   octet 2:  11111010 = 128 + 64 + 32 + 16 + 8 + 2 = 250
   octet 3:  10110111 = 128 + 32 + 16 + 4 + 2 + 1  = 183
   octet 4:  01001110 = 64 + 8 + 4 + 2             = 78

   as one 32-bit integer:  10001110 11111010 10110111 01001110
                        =  2,398,795,598

Because the address is 32 bits, there are exactly 2³² ≈ 4.29 billion possible IPv4 addresses. In 1981 that looked infinite. It was not (section 4). Three facts to install permanently:

  • An IP address identifies an interface, not a machine. Your laptop's Wi-Fi interface, its Ethernet port, its loopback interface, and its docker0 bridge each have their own IP. A router, by definition, has at least two. Run ip addr or ipconfig /all (section 15) and count how many addresses "your machine's IP" actually is.
  • An IP address is two fields glued together: the leading bits name the network, the trailing bits name the host on that network. Where exactly the split falls is the subject of CIDR (section 6) — it is configurable, and that configurability is most of this chapter.
  • IP addresses are assigned, not burned in. Move your laptop from home to the office and its MAC stays the same but its IP changes — because the IP describes where you are plugged in, exactly like your postal address changes when you move house.

Why does this concept live at OSI Layer 3? Because Layer 3's contract is deliver a packet between machines on different networks — and that requires an address with location structure that routers can aggregate. Layer 2 addresses (MAC) deliberately have no such structure, because their contract ends at the edge of one network. The layer boundary is the addressing boundary.

3.1 TTL — the loop killer

🧭 Why TTL exists

Routing tables are maintained by independent routers exchanging information, and during failures or misconfiguration they can briefly disagree: router A thinks the path goes via B, and B thinks it goes via A. A packet caught in that disagreement would bounce between them forever, and with thousands of such packets arriving every second, the loop would melt both routers. TTL is the circuit breaker: the sender sets a hop budget (typically 64 or 128), every router decrements it by 1 before forwarding, and any router that decrements it to 0 drops the packet and sends back an ICMP (Internet Control Message Protocol) Time Exceeded message to the source. A loop now wastes at most 64 hops per packet instead of infinity. Despite the name — a leftover from an early design where it meant seconds — TTL counts router hops, not time.

And here is the beautiful part: traceroute is a deliberate abuse of TTL. It wants to discover every router between you and a destination — but routers are invisible by design. So it sends a packet with TTL=1: the first router decrements to 0, drops it, and replies "Time Exceeded" — revealing its own IP address. Then TTL=2 exposes the second router. Then TTL=3, and so on, until the destination itself answers:

🟢 Beginner — say it simply

An IPv4 address is a 32-bit number written as four dot-separated values like 142.250.183.78 — a postal address for one network interface. Every packet carries a small label (the IP header) with sender, receiver, what's inside (TCP or UDP), and a hop counter (TTL) that stops lost packets from circling the Internet forever.

🟡 Intermediate — the mechanics

The 20-byte IPv4 header is prepended to every Layer-4 segment. Routers forward on Destination IP, decrement TTL, recompute the header checksum, and drop at TTL 0 with ICMP Time Exceeded — which traceroute exploits with incrementing TTLs. The Protocol field (6/17/1) is the demultiplexing key to Layer 4. Fragmentation fields exist but modern stacks avoid them via DF + Path MTU Discovery.

🔴 Advanced — what experts know

IP is deliberately a best-effort, connectionless service: no delivery guarantee, no ordering, no duplication protection — packets are independent datagrams that may take different paths. That minimalism is a design philosophy (the end-to-end principle): keep the network's core dumb and fast, push intelligence to the endpoints (TCP, Part 4). It is why routers scale to terabits and why every reliability feature you rely on lives in the endpoints' operating systems, not in the network. When ICMP is blocked by an overzealous firewall, Path MTU Discovery silently breaks — the classic "small requests work, big uploads hang" production mystery.

4. Running out — address exhaustion and IPv6

📍 OSI Layer 3 — Network
📜 What came before — how 4.3 billion ran out

4.3 billion addresses, 8 billion humans, each with a phone, a laptop, a TV, and a doorbell — the math was always going to fail. It failed faster because of how early addresses were handed out: the original classful system (section 6) allocated in wasteful fixed blocks of 16 million, 65 thousand, or 254 — early universities and corporations received blocks of 16,777,216 addresses they could never use. By the early 1990s the IETF (Internet Engineering Task Force) saw the cliff coming and responded on two tracks: a series of stopgaps to stretch IPv4 (CIDR in 1993 — section 6; private addresses + NAT in 1994–96 — sections 5 and 13), and a permanent replacement, IPv6, standardized in 1998. The stopgaps worked almost too well — they delayed the crisis by two decades and with it the urgency to migrate. The milestone dates: on 31 January 2011, IANA (Internet Assigned Numbers Authority) handed out its last free IPv4 blocks to the regional registries; the regions then ran dry one by one (Asia-Pacific in 2011, Europe in 2019…). Today, "new" public IPv4 addresses are bought second-hand at auction — tens of dollars per address — which is why AWS started charging for every public IPv4 address in 2024.

IPv6 (Internet Protocol version 6) solves exhaustion by brute force: 128-bit addresses — 2¹²⁸ ≈ 3.4×10³⁸ of them, comfortably enough to address every grain of sand on Earth with billions to spare. An IPv6 address is written as eight groups of four hexadecimal digits separated by colons, with two compression rules to keep it readable:

Things genuinely changed in IPv6, beyond length: the header was simplified (routers no longer fragment or recompute checksums — faster forwarding); there is no broadcast (multicast does that job — section 11); ARP is replaced by NDP (Neighbor Discovery Protocol — section 12); and machines can configure their own addresses without a DHCP server via SLAAC (Stateless Address Autoconfiguration — section 10). Every interface also automatically gets a link-local address starting fe80::, usable only on the local network segment.

4.1 Why isn't everything IPv6 already?

IPv6 is over twenty-five years old, and still carries roughly 40–45% of global traffic, not 100%. Three reasons:

  • NAT bought IPv4 time. The killer motivation — "we have no addresses left!" — was defused by letting thousands of devices share one public address (section 13). Pain postponed is migration postponed.
  • IPv6 is not backward compatible. An IPv6-only machine cannot talk to an IPv4-only server. So everyone who enables IPv6 must keep IPv4 too — running both at once, called dual-stack — which doubles configuration and halves the incentive (you cannot drop IPv4 until the last service you rely on supports IPv6).
  • No flag day is possible. The 1983 switch to TCP/IP worked because the ARPANET had a few hundred hosts under one authority. Today's Internet has no owner (Part 1), so the transition is voluntary, incremental, and driven mostly by mobile carriers and big clouds, where address scarcity actually bites.

What changes for you as a backend engineer? Mostly small but sharp edges: DNS has a separate record type for IPv6 addresses (AAAA instead of A — Part 6 tells the full story); your code and logs must not assume an IP fits the dotted-decimal shape (regexes that match only \d+\.\d+\.\d+\.\d+ are a classic bug); and because IPv6 literals contain colons, which URLs already use before the port number, a literal IPv6 address in a URL must be wrapped in square brackets — http://[2001:db8::1]:8080/health — otherwise the parser cannot tell address colons from the port colon. Spring Boot, Node, and FastAPI all listen happily on dual-stack sockets today; your cloud load balancers (Part 9) typically accept IPv6 from clients and speak IPv4 to your services behind them, so most backends meet IPv6 only at the front door.

🔑 Key point

For the rest of this course we compute and reason in IPv4, because every concept — subnets, CIDR, routing, gateways — transfers to IPv6 unchanged (a /64 is a prefix exactly like a /24, just longer). The things that do NOT transfer are the IPv4 workarounds: IPv6 needs no NAT, no ARP, and no broadcast. IPv6 is not "longer IPv4" — it is IPv4 with forty years of regret removed.

5. Public vs private addresses — two parallel worlds

🧭 Why private addresses exist

By the mid-1990s it was obvious that not every machine needs to be reachable from the whole Internet — your printer, your build server, your database have no business being globally addressable (security agrees enthusiastically). So RFC 1918 (1996) carved out three address ranges that are never routed on the public Internet: anyone may use them inside their own network, without asking anyone, for free, forever. Millions of networks reuse the same ranges simultaneously — every home in your city probably has a 192.168.1.1 — and it works precisely because those addresses never appear on the public Internet. The price: a private machine that wants to reach the Internet needs a translator at the border. That translator is NAT (section 13).

Four more special ranges complete the map of "addresses that are not normal public addresses":

  • 127.0.0.0/8 — loopback. Part 1 promised the full story of localhost: here it is. The entire 16-million-address block is reserved for "this machine talking to itself." Packets to any 127.x.x.x address never leave the operating system — they go down the network stack and straight back up through a virtual interface, never touching a cable. 127.0.0.1 is merely the conventional first address. This is why your Spring Boot app on localhost:8080 is unreachable from a colleague's laptop — loopback is not on any wire.
  • 169.254.0.0/16 — link-local, a.k.a. APIPA (Automatic Private IP Addressing). If a machine asks for an address via DHCP (section 10) and nobody answers, it gives itself a random 169.254.x.x so the local segment still works. Burn this into your debugging instincts: seeing 169.254.… in ipconfig means "my DHCP request failed" — the network's equivalent of a check-engine light.
  • 100.64.0.0/10 — CGNAT (Carrier-Grade NAT): a range for ISPs (Internet Service Providers) that NAT their own customers, meaning the "public" address your home router shows may itself be private inside the ISP — one more reason inbound connections to home networks are hard (section 13).
  • 0.0.0.0 — not an address you send to but a wildcard meaning "no/any address." When a server binds to 0.0.0.0 it means "listen on all of this machine's interfaces"; binding to 127.0.0.1 means "loopback only — local clients only." This single distinction explains the classic Docker mystery "the app works inside the container but the published port is dead": the app bound to 127.0.0.1 inside the container, so Docker's forwarded traffic, arriving on another interface, found nobody listening. Part 5 returns to binding in depth.

🟢 Beginner — say it simply

Public IPs are like street addresses — globally unique, handed out by authorities. Private IPs (10.x.x.x, 172.16–31.x.x, 192.168.x.x) are like apartment numbers — reused in every building, meaningful only inside. 127.0.0.1 means "this machine itself," and 169.254.x.x means "I asked for an address and nobody answered."

🟡 Intermediate — the mechanics

RFC 1918 space is non-routable on the public Internet and infinitely reusable; NAT bridges it to the public world. Public space flows IANA → RIR → ISP/cloud → you. Loopback never leaves the OS; APIPA signals DHCP failure; CGNAT means even your router's "public" address may be translated again. Binding to 0.0.0.0 vs 127.0.0.1 controls which interfaces a server accepts connections on.

🔴 Advanced — what experts know

Private-range collisions are a real architectural constraint: when two companies merge, or you peer two VPCs, or a VPN connects your laptop's 192.168.1.0/24 home network to an office using the same range, identical prefixes cannot be routed to two places — fixes range from renumbering to double NAT, all painful. This is why cloud network design guides say: pick boring, unusual CIDR blocks early (e.g. 10.137.0.0/16, not 10.0.0.0/16) and keep a company-wide address plan. Kubernetes makes it worse by consuming three independent ranges per cluster (nodes, pods, services — Part 12).

6. CIDR and subnet masks — where the address splits

📍 OSI Layer 3 — Network

Everything so far said an IP address is "network part + host part." Now the obvious question: where is the split? The modern answer is written after a slash: CIDR notation (Classless Inter-Domain Routing, pronounced "cider").

🔑 Key point

10.0.0.0/16 means: the first 16 bits are the network part; the remaining 32−16 = 16 bits are the host part. That is the entire notation. /N = "N leading bits identify the network." Bigger N → more specific network → fewer hosts inside it.

📜 What came before — classes, and why they failed

Original IPv4 (1981) had no slash — the split was hard-coded by the address's first bits, giving three fixed "classes": Class A (first bit 0 → split after 8 bits → 16,777,214 hosts per network, only 128 such networks possible), Class B (split after 16 bits → 65,534 hosts), Class C (split after 24 bits → 254 hosts). The fatal flaw was the gap: a company with 2,000 machines was too big for a Class C and absurdly small for a Class B — so it took the Class B and wasted 63,000 addresses. Early allocations of entire Class A blocks (16 million addresses to single universities and corporations) accelerated exhaustion, and the rigid sizes bloated routing tables (a company with sixteen Class Cs needed sixteen separate routing entries worldwide). CIDR (1993, RFC 1519) abolished classes: the split can fall after ANY number of bits, declared explicitly with /N — allocations can finally fit actual need, and adjacent blocks can be summarized into one routing entry. "Classless" in the name is literal: it is the classful system's tombstone. (The word "octet," and phrases like "class C-sized network," survive as vocabulary fossils.)

6.1 The subnet mask — the same fact, written for machines

Before the slash notation, the split was expressed as a subnet mask: a 32-bit value with N ones followed by zeros. Both notations carry identical information, and you must read both fluently because tools mix them freely (ipconfig shows masks; ip addr shows slashes):

Fig 3.7 — /24 and 255.255.255.0 are the same statement
   address 192.168.1.7/24

   address:   11000000 . 10101000 . 00000001 . 00000111   = 192.168.1.7
   mask /24:  11111111 . 11111111 . 11111111 . 00000000   = 255.255.255.0
              └────────── 24 ones ──────────┘ └─ zeros ─┘
                    NETWORK PART                HOST PART

   bitwise AND of address and mask  →  the network address:
              11000000 . 10101000 . 00000001 . 00000000   = 192.168.1.0

   the mask is a stencil: 1 = "this bit is network", 0 = "this bit is host"

The AND operation in that figure is not a teaching toy — it is literally the computation your operating system performs on every packet it sends (section 8) and every router performs on every packet it forwards (section 9). Networking is bitwise AND all the way down.

6.2 Reading a block: network address, broadcast address, usable range

A CIDR block like 192.168.1.128/26 defines a contiguous range of addresses. Two of them are reserved: the network address (all host bits 0 — the name of the block itself, used in routing tables) and the broadcast address (all host bits 1 — addresses every host in the block at once, section 11). Everything between is usable for hosts. Let's compute one by hand — given the address 192.168.1.130/26, what block is it in?

Fig 3.8 — Hand-computing the block of 192.168.1.130/26
   /26 mask:  11111111.11111111.11111111.11000000  = 255.255.255.192
                                          └┬┘└─┬──┘
                            2 network bits ┘   └ 6 host bits (in last octet)

   last octet of address:    130  =  1 0 0 0 0 0 1 0
   last octet of mask:       192  =  1 1 0 0 0 0 0 0
   bitwise AND:                      1 0 0 0 0 0 0 0   =  128

   NETWORK address  = 192.168.1.128      (host bits all 0)
   BROADCAST        = 192.168.1.191      (host bits all 1: 10 111111 = 191)
   usable hosts     = 192.168.1.129 … 192.168.1.190
   count            = 2^6 − 2 = 62 usable addresses

The general formula: a /N block contains 2^(32−N) addresses, of which 2^(32−N) − 2 are usable for hosts (minus network and broadcast). The table interviewers expect you to reproduce:

🌍 Analogy — CIDR is postal-code granularity

Think of a CIDR prefix as a postal code of adjustable precision. "Germany" (a /8: huge, vague) contains "Frankfurt" (a /16) contains "Kaiserstraße" (a /24) contains "Kaiserstraße 17" (a /32: one exact house). Mail sorting works because a sorting center in Mumbai needs only the coarse prefix ("Germany → that plane"), while the Frankfurt office uses finer prefixes ("this district → that truck"). Routing tables (section 9) work identically: far-away routers store coarse prefixes covering millions of addresses, and the closer a packet gets, the finer the prefixes become — which is exactly why hierarchical addressing keeps routing tables small, the problem that opened this chapter.

🟢 Beginner — say it simply

/24 after an address says "the first 24 bits name the network; the rest name the machine." The subnet mask (255.255.255.0) says the same thing in mask form. A /24 network holds 254 machines; each extra bit of network halves the room. Two addresses per block are reserved: the lowest (the network's name) and the highest (the broadcast address).

🟡 Intermediate — the mechanics

network = address AND mask; broadcast = network OR (NOT mask); usable = 2^(32−N) − 2. CIDR replaced fixed classes (1993) so allocations match need and adjacent blocks aggregate into single routing entries. Fluency drill: given any address/N, produce network, broadcast, and range in under a minute — it is the networking equivalent of knowing your times tables.

🔴 Advanced — what experts know

Aggregation is CIDR's deeper purpose: an ISP announcing 198.51.100.0/24 and its neighbors as one short prefix keeps the global routing table (~1 million routes today) from being 100× larger. The same trick works in reverse as longest-prefix match (section 9): more-specific routes override coarser ones, which is both a routing-policy tool and a hijacking vector — announcing a more-specific prefix of someone else's block steals their traffic (BGP hijacks, Part 1's advanced note). Inside your infrastructure, the same idea appears in security groups and Kubernetes NetworkPolicies: rules are written against CIDR blocks, so your address plan IS your security topology.

7. Subnetting by hand — carving 10.0.0.0/16 into tiers

Subnetting sounds like an exam topic, but it is something you will genuinely do the first week you touch cloud infrastructure: every VPC begins life as one CIDR block that you must slice into subnets. Let's do the canonical exercise — the exact plan you will later build for real in AWS (Part 11 reuses this layout line for line).

Given: one block, 10.0.0.0/16 — 65,536 addresses. Wanted: separate subnets for a public tier (load balancers), an application tier (Spring Boot services), and a database tier (PostgreSQL, Redis) — duplicated across two availability zones for redundancy.

Choosing /24 for each subnet gives 254 hosts apiece (plenty per tier) and has a priceless side effect: because the split falls exactly on the third octet, the subnet is readable by eye — 10.0.X.y means subnet X. Since the host part of the /16 gave us bits 17–32 and we now fix bits 17–24 per subnet, we can mint 2⁸ = 256 such /24 subnets: 10.0.0.0/24, 10.0.1.0/24, … 10.0.255.0/24.

Why bother carving at all, instead of dumping everything into one flat /16? Three reasons that will echo through the rest of the course:

  • Different routing per subnet. The public subnets get a route to the Internet; the app and db subnets get none (or only outbound via a NAT gateway — section 13). A database that cannot route to the Internet is safe from whole categories of attack and exfiltration by construction.
  • Security boundaries follow subnet boundaries. Firewall rules like "the db tier accepts port 5432 only from 10.0.11.0/24 and 10.0.12.0/24" are CIDR statements. Clean subnetting makes security rules short and auditable.
  • Blast radius. Broadcast storms, address exhaustion, a misbehaving DHCP server — many failures stop at the subnet edge, because (as the next two sections show) the subnet is precisely the boundary where direct delivery ends and routers take over.
🔑 Key point

A subnet is not paperwork — it is a behavioral boundary. Inside one subnet, machines deliver to each other directly (one ARP, one frame, no router). Across subnets, every packet must pass through a router, where it can be filtered, logged, NATed, or refused. "Same subnet or not?" is therefore the first question the OS asks for every single packet — the next section is exactly how it asks it.

8. The local-or-remote decision — the first hop is decided on your laptop

Your code calls fetch("http://10.0.21.5:5432") or opens a connection to 142.250.183.78. Before anything touches a wire, the operating system must answer one question: can I deliver this directly, or do I need a router? The algorithm is three AND operations and a comparison:

  1. Compute my network: my IP AND my mask.
  2. Compute the destination's network as I would see it: destination IP AND my mask.
  3. Equal? → destination is on my subnet: deliver directly (ARP for the destination's own MAC, frame it, done). Not equal? → destination is remote: hand the packet to my default gateway (ARP for the gateway's MAC instead — section 12 makes a big deal of this distinction, because everyone gets it wrong).

   my IP   AND mask:  192.168.1.7   AND 255.255.255.0  =  192.168.1.0
   dest    AND mask:  192.168.1.20  AND 255.255.255.0  =  192.168.1.0
                                                          ════════════
                                              SAME network → LOCAL
                  → ARP for 192.168.1.20's MAC, send frame directly
                    (the packet never touches a router)

   ───────────────────────────────────────────────────────────────────

   CASE 2: GET https://google.com (142.250.183.78)

   my IP   AND mask:  192.168.1.7    AND 255.255.255.0  =  192.168.1.0
   dest    AND mask:  142.250.183.78 AND 255.255.255.0  =  142.250.183.0
                                                           ═════════════

Notice what the laptop does not do: it does not know, or care, where 142.250.183.78 actually is, how many hops away, or which path leads there. Its entire worldview is binary — "mine" or "not mine, the gateway's problem." All the intelligence about the rest of the world lives in routers. This delegation is what lets a $300 laptop participate in a planet-scale network: it needs exactly one routing decision and one configured address (the gateway) to reach all 4.3 billion destinations.

🧪 Real example — the bug a wrong mask causes

Misconfigure the mask as 255.255.0.0 (/16) on a machine that is really on a /24, and the machine believes all of 192.168.x.x is local. Packets to 192.168.2.9 (actually a different subnet behind the router) are no longer sent to the gateway — the machine ARPs directly for 192.168.2.9 on the local wire, nobody answers, and the connection times out. The symptom is maddeningly selective: "I can reach some machines but not others, and ping to the Internet still works." When you hit selective unreachability, check the mask before you check the cables.

9.2 Longest-prefix match — the one rule of routing

What if a destination matches several entries? It usually does — 0.0.0.0/0 matches everything by definition. The rule, the only rule: the most specific match wins — the entry with the longest prefix. Work this example until it is reflex:

Why most-specific? Because specificity is knowledge. A /24 route says "I know exactly where this small neighborhood is"; the default route says "I know nothing — send it upstream." Trusting precise information over vague is the only sane policy — postal sorting again: a parcel for Kaiserstraße 17 goes on the Kaiserstraße truck, not the generic "Germany somewhere" plane, even though both technically match. The default route 0.0.0.0/0 is simply the zero-knowledge entry that matches everything. Your laptop has one (pointing at the home router); your home router has one (pointing at the ISP); small ISPs point at bigger carriers. Only the largest backbone networks run default-free: their routers hold a route for every announced prefix on Earth — about one million entries — and CIDR aggregation is the only reason that number is not a hundred million.

9.3 Gateways — and what your home "router" actually is

A gateway is just a router seen from inside a subnet: the local exit door. "Default gateway" = "the router interface on my subnet that my default route points at." It must be on your subnet — it is the one router you can reach directly with a frame, which is what section 8's algorithm depends on.

🟢 Beginner — say it simply

A router connects networks and decides where each packet goes next using a routing table — rows of "addresses like X → send that way." If several rows match, the most specific wins; the catch-all row (the default route) sends everything unknown toward the wider Internet. Your gateway is simply the nearest router — your network's exit door.

🟡 Intermediate — the mechanics

A route = prefix + next hop (or directly-attached interface) + metric. Lookup = longest-prefix match; metric breaks ties between equal prefixes only. Hosts hold a handful of routes (local subnet, docker0, VPN, default); core routers hold ~1M. Each forwarded packet gets new L2 framing, TTL−1, and a recomputed header checksum; the IP endpoints are untouched. Routers learn remote prefixes from each other via routing protocols — OSPF (Open Shortest Path First) inside an organization, BGP (Border Gateway Protocol) between organizations (Part 1's advanced note).

🔴 Advanced — what experts know

Longest-prefix match is also a traffic-engineering and failover primitive: inject a more specific route and you steal traffic from the covering prefix — used deliberately (VPN split tunneling; cloud route tables sending 10.0.21.0/24 through a firewall appliance) and maliciously (BGP more-specific hijacks). In AWS, every subnet is associated with a route table you write yourself — "0.0.0.0/0 → internet gateway" is literally what makes a subnet public, and its absence is what makes one private (Part 11). When a Kubernetes pod can't reach the Internet, the debugging skill is identical: walk the route tables hop by hop and find who lacks a matching prefix or a return route.

10. DHCP — how your laptop got its address in the first place

📍 An application-layer service (over UDP) that configures Layer 3 — the stack bootstrapping itself
🧭 Why this exists

Sections 5–9 assumed your laptop somehow already knows four values: its IP, the subnet mask, the default gateway, and a DNS server. Where did they come from? You never typed them. In the 1980s you did type them — every machine was configured by hand from an office spreadsheet of who owns which address. Hand-managed addressing fails exactly as you would predict: duplicate addresses (two machines fighting — see the interview questions), typo'd gateways, stale spreadsheets, and zero support for devices that move — a laptop carried from home to office needs entirely different values in each place. DHCP (Dynamic Host Configuration Protocol, 1993, evolved from the older BOOTP) automates it: plug in, broadcast "somebody configure me!", receive a time-limited lease on an address plus all the settings, renew while you stay, release when you leave.

The exchange is four packets, remembered as DORA — Discover, Offer, Request, Acknowledge. Note the chicken-and-egg problem it solves: the laptop must send packets in order to get an address, while having none. The escape hatch is broadcast — source 0.0.0.0 ("I am nobody"), destination 255.255.255.255 ("everyone on this wire," section 11):

That layering is worth noticing: the network stack is bootstrapped by an application, one of several places the tidy OSI tower bends in practice, like ARP just below it.

Static vs dynamic is an operational decision you will make constantly: servers get stable addresses — configured statically or, better, via a DHCP reservation (the server always hands the same address to that MAC) — because other machines must find them at a known address. Clients get dynamic addresses, because nobody connects to a laptop, and churn makes static bookkeeping absurd. The cloud repeats the pattern: EC2 instances get their private addresses from the VPC's own DHCP (Part 11), databases get fixed endpoints, and Kubernetes pods get deliberately ephemeral addresses because something else — Services, Part 12 — solves "known address" for them.

🔑 Key point

Routers do not forward broadcasts. A broadcast reaches every host on its own subnet and dies at the router — by design: if broadcasts crossed routers, one chattering NIC could cascade across the entire Internet, billions of machines interrupted by every ARP request on Earth. The subnet is therefore also called a broadcast domain, and this single rule quietly explains several things at once: why ARP and DHCP (both broadcast-based) work only within the local subnet, why every subnet needs its own DHCP server or relay, and why section 7's "blast radius" was not a metaphor. Anycast is the opposite trick — not a packet type but a routing arrangement: announce the same prefix from twenty cities, and longest-prefix matching automatically steers every client to the nearest copy, no client code changed. The Internet itself becomes your load balancer. (IPv6, incidentally, abolished broadcast entirely; multicast does the job more politely.)

12. ARP — the glue between IP and MAC

📍 Straddles OSI Layers 2–3 — resolves L3 addresses, but rides directly inside L2 frames
🧭 Why this exists

Sections 8–9 keep saying "then ARP for the MAC." Here is the gap it fills. The routing decision produced a next-hop IP — say, the gateway 192.168.1.1. But Part 2 taught you that what actually goes on the wire is an Ethernet frame, and frames are addressed by MAC. The OS now holds an IP it must reach and needs the matching MAC — and nothing in an IP address encodes it; the two namespaces are unrelated (postal address vs fingerprint). ARP (Address Resolution Protocol, RFC 826, 1982) is the missing translation: shout the question to everyone on the wire, let the owner answer. Without it you would have perfect routes and no way to take even one hop.

The exchange is one broadcast question and one unicast answer. Watch the frame addressing carefully:

🔑 Key point — ARP only ever resolves the NEXT HOP

This is the single most-missed point in networking interviews, so read it twice. ARP never crosses a router, and you never ARP for a remote machine. When your laptop sends to 142.250.183.78, it does NOT ask "who has 142.250.183.78?" — that broadcast would die at the subnet edge (section 11), and Google is not on your wire to hear it. The local-or-remote decision (section 8) already chose the next hop — the gateway — so the laptop ARPs for 192.168.1.1 and builds a frame whose destination MAC is the router's while the destination IP remains Google's. Every later hop repeats the same trick for its next hop. MAC = this hop; IP = final destination. If you keep one sentence from this chapter for interviews, keep this one.

And the badge above deserves its honesty note: people argue about ARP's layer because it genuinely straddles. Its purpose is Layer-3 bookkeeping (mapping IP addresses), but its packets are not IP packets — they are raw Ethernet payloads (EtherType 0x0806), unroutable by construction. Call it "the L2/L3 glue" and any interviewer will nod. IPv6 replaced it with NDP (Neighbor Discovery Protocol), which does ride inside IPv6 itself using multicast instead of broadcast — same job, tidier layering.

🟢 Beginner — say it simply

IP addresses plan the journey; MAC addresses move the frame one step. ARP converts one into the other: "who has this IP? tell me your MAC," shouted to the local network and answered by the owner, with answers remembered in a small cache. For anything beyond your own subnet, you ask for the router's MAC — never the far machine's.

🟡 Intermediate — the mechanics

Request = broadcast frame (dst ff:ff:ff:ff:ff:ff, EtherType 0x0806) carrying sender IP+MAC and target IP; reply = unicast carrying the mapping. Cached with short TTLs (REACHABLE → STALE → re-probe on Linux). Gratuitous ARP announces or updates a mapping unprompted (conflict detection, virtual-IP failover). Resolution is always next-hop-scoped: routing decides first, ARP resolves what routing chose, never the reverse.

🔴 Advanced — what experts know

ARP has no authentication — any host may answer any request or gratuitously claim any IP. That is ARP spoofing: poison a victim's cache so "the gateway" resolves to your MAC and you become a man-in-the-middle on the LAN, silently relaying and reading traffic. It is why coffee-shop Wi-Fi is hostile territory, why TLS (Part 8) must protect you even from your own LAN, and why enterprise switches ship Dynamic ARP Inspection. Clouds sidestep the whole class: an AWS VPC answers ARP from the hypervisor and ignores guest spoofing — one of many ways cloud networking is software impersonating Ethernet (Part 11).

13. NAT — how billions of machines hide behind millions of addresses

📍 OSI Layer 3 — Network (with one foot in Layer 4, as Part 5 will make precise)
🧭 Why this exists

Count your home: laptops, phones, TV, console, doorbell — a dozen devices, easily. Your ISP gave you one public IPv4 address. Section 4's arithmetic (4.3 billion addresses, far more devices) forced exactly this; most machines hold only private RFC 1918 addresses (section 5), which the public Internet refuses to route. So how does 192.168.1.7 ever fetch google.com? NAT (Network Address Translation, RFC 1631, 1994): the border router rewrites each outgoing packet's source to its own public address, keeps a note of who the conversation really belongs to, and reverses the rewrite on replies. Proposed as a short-term stopgap until IPv6 arrived; thirty years later it is load-bearing infrastructure for most of the planet — the most consequential "temporary" hack in networking history.

🌍 Analogy — the office mailroom

A company's 500 employees all send letters with the return address "1 Corporate Plaza" — the building's single public address. The mailroom keeps a ledger: "outgoing letter ref #30001 was really from desk 51234." When a reply arrives addressed "1 Corporate Plaza, ref #30001," the ledger routes it back to the right desk. Outsiders never learn desk numbers, the company needs only one public address — and, crucially, nobody outside can write to a desk first: a letter with no ledger entry has no desk to go to, and lands in the bin. Every property of NAT, good and bad, is already in this picture.

The ledger is real — it is the NAT translation table in your router. The common form is technically PAT (Port Address Translation, a.k.a. NAT overload): it uses port numbers — per-conversation numbers you will study properly in Part 5; for now, think "an ID the router assigns each conversation" — to tell flows apart, which is what lets thousands of private machines share ONE public address simultaneously:

13.1 The consequences — NAT explains half your weird networking days

  • Inbound connections are dead by default. An unsolicited packet from the Internet matches no table row and is dropped. This is why your laptop, running a perfectly good Spring Boot server on port 8080, is unreachable from the Internet — and, given every unpatched smart bulb in the world, it is also a blessing.
  • Webhooks cannot reach you. Stripe or GitHub trying to POST to your dev machine hits the NAT wall. Hence tunneling tools: ngrok works by having your machine dial out to its public relay (outbound creates a ledger entry!) and then feeding inbound webhooks down that pre-opened pipe. Part 1's "the client always initiates" rule, weaponized.
  • P2P needs gymnastics. Two laptops, both behind NAT, neither able to accept inbound — who calls whom? This is Part 1's peer-to-peer operability problem made concrete. WebRTC (Web Real-Time Communication) video calls solve it with STUN and TURN servers (Session Traversal Utilities for NAT; Traversal Using Relays around NAT), which help both sides discover their public mappings or, failing that, relay the media outright.
  • Servers see one address for a whole building. Rate-limit "by IP" and one enthusiastic office — or an entire mobile carrier behind CGNAT (section 5) — becomes one "user." Per-IP quotas, abuse detection, and analytics all inherit the blur.
  • Port forwarding is the manual override: a permanent hand-written ledger row — "anything arriving at 203.0.113.5:8080 → 192.168.1.7:8080" — how home servers get exposed, and what game consoles are begging for when they complain about "NAT type."
  • The end-to-end principle takes a dent. The address the server sees is not the address the client holds, so protocols that embed IPs inside their payloads (classic FTP, SIP telephony) break outright and need protocol-aware NAT helpers.

Cloud postscript: AWS sells this exact machinery as a managed NAT Gateway — it is how instances in your private subnets (section 7) reach the Internet for apt update while remaining unreachable from it. You will wire one up in Part 11 already knowing precisely what it does.

🟢 Beginner — say it simply

NAT lets your whole house share one public address. The router swaps each outgoing packet's private return address for its own public one and keeps a ledger; replies are looked up and passed back to the right device. Side effect: outsiders cannot start conversations with your machines — replies get in, cold calls are dropped.

🟡 Intermediate — the mechanics

PAT multiplexes many private (IP, port) pairs onto one public IP by allocating a distinct public port per flow and rewriting headers in both directions (checksums recomputed). State is created only by outbound traffic; inbound-without-state is dropped — a stateful firewall for free. Port forwarding pre-seeds static entries. ngrok-style tunnels, STUN/TURN, and webhook relays all exist to route around the no-inbound rule.

🔴 Advanced — what experts know

NAT state is a capacity and failure dimension: tables overflow (CGNAT boxes juggle millions of entries), idle entries expire (long-quiet TCP connections — database pools, Kafka consumers — die mysteriously unless keepalives chirp; Part 4), and a rebooted NAT orphans every live conversation. NAT also shaped modern architecture by accident: because inbound-to-clients is impossible, the industry standardized on client-initiated everything — polling, WebSockets, push services — and public-facing endpoints concentrated behind load balancers holding real public IPs (Part 9). IPv6 removes the scarcity that justified NAT, yet the drop-unsolicited-inbound behavior survives as explicit firewall policy, because by now the whole ecosystem assumes it.

Step 6 — The home router NATs and forwards (sections 9 and 13)

The router unwraps the frame, reads the IP destination, and runs its own longest-prefix match: 142.250.183.78 matches only 0.0.0.0/0 via 203.0.113.1 — upstream. Before forwarding, two rewrites:

  • NAT: source 192.168.1.7:51234 becomes 203.0.113.5:30001; the ledger row from Fig 3.16 is written. From here on, the Internet believes this conversation belongs to 203.0.113.5.
  • TTL: 64 → 63; header checksum recomputed.

Then the router does exactly what the laptop did one hop earlier: it ARPs on its WAN segment for its own next hop (203.0.113.1 → 00:1a:2b:3c:4d:5e) and wraps the packet in a brand-new frame. The old frame no longer exists — frames live for exactly one hop.

🔑 Key point — the whole chapter in one breath

DHCP gave identity → DNS gave the number → the mask-AND said "remote" → ARP found the gateway's MAC → frame to the gateway, packet to Google → NAT swapped private for public and wrote the ledger → routers longest-prefix-matched it hop by hop, burning TTL and re-framing every link → the reply retraced, the ledger un-swapped, the LAN delivered. Ten technologies, one keystroke, roughly 25 ms. And notice what is still missing: nothing yet guarantees all the bytes arrived, in order, exactly once — and nothing yet says which program on the machine gets them. Those are Parts 4 and 5.

🟢 Beginner — say it simply

Your laptop looks up Google's number, sees it is far away, and hands the packet to the home router using the router's MAC address. The router swaps your private address for its public one and sends the packet upstream, where routers pass it along like postal sorting centers, each reading only the destination. 🟡 Intermediate — the mechanics

Sequence: DHCP-provided config → DNS resolution → subnet comparison (IP AND mask) → ARP for the next hop → L2 frame to the gateway carrying the L3 packet to the destination → PAT rewrite plus state entry at the border → per-hop longest-prefix match, TTL decrement, re-framing → possibly asymmetric return → NAT state lookup → local delivery. MACs change per link; IPs change only at NAT; TTL decrements at every router.

🔴 Advanced — what experts know

Run this narrative as a debugging checklist and most "the network is broken" tickets fall out of it: no DHCP (169.254.x.x?), DNS resolves but route missing (name lookup works, ping fails), wrong mask (selective reachability, section 8), dead gateway (everything off-subnet fails), NAT table exhaustion (new connections fail under load while old ones live), TTL anomalies (routing loops — traceroute shows ping-ponging hops), asymmetric returns dropped by stateful firewalls. Wireshark on hop 1 plus traceroute outward localizes most connectivity faults to a layer and a device — which is the actual professional value of being able to tell this story unprompted.

16. Interview questions

🎤 Try answering out loud before you click
Why do we need both MAC and IP addresses? Isn't one unique identifier enough?

They answer different questions at different scopes. MAC addresses are flat, manufacturer-assigned identifiers — perfect for "which device on this wire" but carrying no location information, so they cannot be aggregated: routing the Internet by MAC would require every router to track every device on Earth individually. IP addresses are hierarchical and assigned by network location, so routers can summarize millions of machines behind one prefix — that aggregation is the only reason routing tables fit in memory. Mechanically, IP plans the end-to-end journey while MAC executes each single hop: frames and their MACs are rewritten at every router, while the packet's IPs stay constant end to end. ARP converts the next-hop IP into a MAC at each link. One system flat and local, one hierarchical and global — both necessary, glued by ARP.

Subnet math: a host is 10.0.5.130/26. Give the network address, broadcast address, and usable range.

A /26 leaves 6 host bits → blocks of 64 addresses, so the last octet partitions into 0–63, 64–127, 128–191, 192–255. The value 130 falls in the 128–191 block. Verify with the AND: 130 = 10000010, mask last octet 192 = 11000000, AND = 10000000 = 128. Therefore: network address 10.0.5.128, broadcast 10.0.5.191 (all host bits set), usable hosts 10.0.5.129 through 10.0.5.190 — 2⁶ − 2 = 62 of them. A strong answer narrates the block-size shortcut (256 − 192 = 64, so blocks step by 64) instead of grinding pure binary, and remembers the −2 is the network and broadcast addresses.

What happens if two devices on the same network have the same IP address?

Chaos, mediated by ARP. Both devices answer ARP requests for the address, so neighbors' caches flap between two MACs depending on who answered last; traffic is delivered to whichever device most recently won. The symptom is intermittent connectivity that "fixes itself" and breaks again — connections resetting as frames alternate targets mid-conversation. Modern operating systems probe at configuration time (gratuitous ARP: announce the address, listen for an objection) and log "IP address conflict." DHCP prevents most cases by leasing from a single pool; real-world conflicts usually come from a static assignment colliding with the DHCP range. In clouds the hypervisor controls ARP answers, making the disease nearly impossible — one of several LAN problems virtualization simply deleted.

Explain NAT. Why does it exist, and what are its downsides?

NAT (Network Address Translation) lets many privately-addressed machines share few public IPv4 addresses — the practical response to address exhaustion. The border router rewrites each outbound packet's source (private IP and port → its public IP and an allocated port), records the mapping in a translation table, and reverses the rewrite on replies; the common many-to-one form is PAT (Port Address Translation). Downsides: unsolicited inbound is impossible (no table entry → drop), breaking home servers, webhooks, and peer-to-peer — hence ngrok-style tunnels and STUN/TURN for WebRTC; it breaks the end-to-end principle, so protocols embedding addresses in payloads (FTP, SIP) need special helpers; it blurs identity (an office or a whole carrier appears as one IP, wrecking per-IP rate limits and analytics); the state table can exhaust under load and is lost on reboot, killing live connections; and idle long-lived connections die when entries expire — why database pools need keepalives. Its one beloved side effect: dropping unsolicited inbound makes it an accidental firewall.

What does the TTL field in the IP header actually do?

TTL (Time To Live) is an 8-bit hop budget preventing packets from looping forever. The sender sets it (commonly 64 or 128); every router decrements it by one; a router decrementing it to zero drops the packet and returns an ICMP Time Exceeded to the source. Despite the name, it counts router hops, not seconds — the name is a fossil from an early design. Two practical uses: traceroute maps paths by sending probes with TTL = 1, 2, 3… and collecting the Time Exceeded senders; and observed reply TTLs reveal hop counts (a reply arriving at TTL 116 likely left a 128-default host twelve hops away). Don't confuse it with DNS TTL, which genuinely is seconds — same name, unrelated mechanism.

Your laptop (192.168.1.7/24) sends a request to a server on another continent. Whose MAC goes in the frame, and why?

The default gateway's — never the remote server's. The laptop ANDs both its own address and the destination with its subnet mask, sees different networks, and selects its gateway as the next hop. It ARPs for the gateway's MAC (ARP is broadcast-based and cannot cross a router anyway) and emits a frame whose destination MAC is the gateway's while the destination IP remains the remote server's. Every subsequent router repeats the pattern toward its own next hop. MAC addresses are per-link; IP addresses are end-to-end. Interviewers use this exact question to separate people who memorized layer names from people who understand what the layers do.

What are the RFC 1918 private ranges, and what makes an address "private"?

10.0.0.0/8 (16.7 million addresses), 172.16.0.0/12 (about a million — includes Docker's default 172.17.0.0/16), and 192.168.0.0/16 (65,536 — home networks). "Private" means Internet routers will not carry these prefixes: anyone may use them internally without registration, and millions of networks reuse them simultaneously without collision because they never meet — until VPNs, VPC peering, or company mergers make them meet, which is why address planning matters. Private hosts reach the Internet only through NAT. Worth volunteering as a bonus: 127.0.0.0/8 loopback, 169.254.0.0/16 link-local/APIPA ("DHCP failed"), 100.64.0.0/10 carrier-grade NAT, and 0.0.0.0 as the all-interfaces bind wildcard.

What is a default gateway, and what exactly breaks if it's missing or wrong?

The default gateway is the router interface on your own subnet that your default route (0.0.0.0/0) points at — the next hop for every destination lacking a more specific route. It must be on your subnet, because it is the one router you can reach directly at Layer 2. If it is missing or wrong, the failure signature is surgical: everything on the local subnet keeps working (direct delivery needs no router) while everything beyond fails — no Internet, no other subnets. DNS often appears broken too, if the resolver is off-subnet, which lures people into debugging the wrong layer. "Local works, remote doesn't" should send you straight to the gateway setting, then to ARP for the gateway.

A router has routes 0.0.0.0/0 via A, 10.0.0.0/16 via B, and 10.0.1.0/24 via C. Where does a packet for 10.0.1.99 go, and why?

Via C. All three routes match 10.0.1.99 — the default matches everything, and 10.0.1.99 lies inside both 10.0.0.0/16 and 10.0.1.0/24 — and IP forwarding always selects the longest matching prefix: /24 beats /16 beats /0. The rationale: specificity is knowledge — a route covering 256 addresses carries more precise information about the destination than one covering 65,536 or the entire Internet. Follow-ups to expect: 10.0.7.9 goes via B (now /16 is the longest match), 8.8.8.8 via A (only the default matches), and metrics break ties only between routes of equal prefix length.

Walk through DHCP. What happens if no DHCP server responds?

DORA. The client broadcasts a Discover from source 0.0.0.0 to 255.255.255.255 — it has no address yet, so broadcast is its only option. Each available server replies with an Offer: proposed IP, mask, gateway, DNS, lease duration. The client broadcasts a Request formally accepting one offer — broadcast so losing servers can reclaim theirs — and the chosen server confirms with an Acknowledge. The client self-configures and renews quietly (unicast) at about half the lease. If no server ever answers, the OS self-assigns a random link-local address in 169.254.0.0/16 (APIPA), allowing same-subnet traffic only — which is why a 169.254.x.x in ipconfig is the canonical "DHCP failed" diagnostic. And because Discover is a broadcast, which routers do not forward, every subnet needs its own DHCP server or a relay agent.

Compare broadcast, multicast, and anycast. Why don't routers forward broadcasts?

Broadcast delivers to every host on the local subnet (255.255.255.255, or the subnet broadcast such as 192.168.1.255), wanted or not — ARP and DHCP depend on it. Multicast (224.0.0.0/4) delivers only to hosts that joined a group via IGMP — routing protocols, IPTV, market data. Anycast is not a packet type but a routing arrangement: the same ordinary unicast prefix is announced from many locations, and longest-prefix routing carries each client to the nearest instance — 8.8.8.8, the DNS root servers, and CDNs run this way. Routers drop broadcasts because forwarding them would let any host interrupt every machine on Earth; local noise must stay local (the subnet = the broadcast domain), and LAN-scale broadcast storms are destructive enough without global reach. IPv6 removed broadcast entirely in favor of multicast.

What is the difference between binding a server to 127.0.0.1 and to 0.0.0.0?

Binding selects which interfaces accept connections. 127.0.0.1 binds only loopback — packets that never leave the OS — so only same-machine clients can connect: right for local-only tools. 0.0.0.0 is the wildcard: listen on every interface the machine has (Wi-Fi, Ethernet, docker0…) — required for anything reachable from outside. The classic Docker bug: an app inside a container binds 127.0.0.1, the published port forwards traffic to the container's other interface, and every external request is refused while curl localhost inside the container works perfectly. Bind 0.0.0.0 inside containers; bind 127.0.0.1 on your laptop when you'd rather the coffee-shop LAN not browse your dev server. Ports and sockets get their full treatment in Part 5.

17. Common misconceptions

❌ Myths engineers actually believe

❌ "An IP address identifies a machine."
✅ It identifies an interface. One machine has several — loopback, Wi-Fi, Ethernet, docker0, VPN tunnels — each with its own address; and thanks to NAT, one public address can front hundreds of machines. "What is this machine's IP?" is often a malformed question; "which interface, seen from where?" is the real one.

❌ "192.168.x.x is my address on the Internet."
✅ RFC 1918 addresses never appear on the public Internet — millions of homes are using yours right now. The world sees only your router's public address (or your ISP's CGNAT address above that). This is exactly why ipconfig and "what is my IP" websites disagree: one shows the private interface address, the other shows the post-NAT public source that actually reached the website.

❌ "TTL is measured in seconds."
✅ In the IP header it counts router hops: minus one per router, dropped at zero. The name is a fossil of an abandoned design. Confusingly, DNS TTL (Part 6) really is seconds — establishing which TTL a colleague means is half the conversation.

❌ "ARP finds the MAC address of the destination server, wherever it is."
✅ ARP is broadcast-based, and broadcasts die at the router: it can only resolve addresses on your own subnet. For any remote destination you ARP for your gateway's MAC and frame the packet to it, with the IP inside still addressed to the far machine. You will never know google.com's MAC address — and nothing about your request needs it.

❌ "IPv6 is just IPv4 with longer addresses."
✅ Length is the headline, not the story: IPv6 also abolishes broadcast (multicast replaces it), replaces ARP with NDP, lets hosts autoconfigure without DHCP (SLAAC), simplifies the header (no in-network fragmentation, no hop-by-hop checksum), and — by ending scarcity — removes the need for NAT, restoring end-to-end addressing. Treating it as "the same network with wider numbers" is how dual-stack deployments end up with IPv6 paths nobody remembered to firewall.

❌ "The subnet mask hides or secures part of my network."
✅ The mask is pure arithmetic: it tells hosts and routers where the network/host split falls so the local-or-remote decision can be made. It hides nothing and blocks nothing — isolation comes from routing policy and firewalls. The mask just draws the map those tools enforce.

❌ "The IP header checksum protects my data."
✅ It covers the 20-byte header only — and is recomputed at every hop anyway, since TTL changes. Payload integrity belongs to the transport layer (TCP/UDP checksums, Part 4), and real end-to-end assurance to TLS (Part 8). IP promises best-effort delivery of a possibly-lost, possibly-duplicated, possibly-reordered datagram — by deliberate design.

❌ "My machine has one IP address."
✅ Run ip addr and count: loopback 127.0.0.1, the LAN address, Docker's bridge at 172.17.0.1, an IPv6 link-local per interface, maybe a VPN tunnel. A developer laptop routinely holds five or more, and which one a given connection uses depends on the routing table — why "works from my machine" sometimes literally depends on which interface the OS picked.

Looking back: Part 2 gave you the layer map and the promise that frames are hop-scoped while packets travel end-to-end; this part built the entire Layer 3 machinery that makes the promise real — hierarchical addresses (because Part 2's flat MACs cannot aggregate), subnets and CIDR, routers and longest-prefix match, ARP as the L2/L3 glue, and NAT at the border.
