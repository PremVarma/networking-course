Reverse Proxies — The Gateway in Front of Your App

In Part 9 you put a load balancer in front of three Spring Boot instances and watched it spread traffic across them. But that box was doing more than spreading load — it was terminating TLS, rewriting headers, and presenting one hostname to the world. That broader role has a name: reverse proxy. This is the single most useful piece of infrastructure a backend engineer can understand, because it is the box that turns "my app on localhost:8080" into "a real service on the Internet."

1. What is a proxy (in general)?

Before "forward" or "reverse," before Nginx or HAProxy, there is one root idea. Strip away every adjective and a proxy is this:

🔑 Key point

A proxy is an intermediary that sits between two parties and relays their communication, speaking on behalf of one side. Party A thinks it is talking to party B, but it is really talking to the proxy; the proxy then talks to B. The word itself means "an agent authorized to act for another" — a proxy vote is a vote someone casts on your behalf.

That sounds almost too simple to be worth a chapter. The power is not in the relaying — it is in where the intermediary sits. The moment every message between A and B must pass through one box, that box becomes a single control point. And a single control point is the most valuable real estate in all of systems engineering, because at one place — without changing A or B — you can:

  • Observe — log every request, measure latency, count errors, trace a request across services.
  • Transform — rewrite headers, compress bodies, change paths, convert HTTP/2 to HTTP/1.1.
  • Secure — terminate TLS, check authentication, block malicious payloads, rate-limit abusers.
  • Cache — remember a response and serve the next identical request without bothering the backend.
  • Route — send /api to one place and /images to another; pick a healthy server out of many.
🧭 Why intermediaries are powerful

Suppose you have 40 microservices and you want every one of them to log requests, enforce TLS, and reject oversized uploads. You could write that code 40 times, in five languages, and re-test it on every deploy — or you could insert one box that every request already flows through and configure it once. Cross-cutting concerns (the things every service needs but none of them is really about) belong at a choke point, not scattered through application code. The proxy is that choke point. This is the same instinct that put a switch in the middle of a network back in Part 1, Fig 1.2: don't wire everything to everything — route it all through one smart relay.

🌍 Analogy — the front desk and the personal assistant

Picture a large office building. Visitors don't wander the corridors knocking on doors; they stop at the front desk. The desk checks their ID, logs them in, tells them which floor to go to, and may refuse them entry. To the visitor, the desk is the company — it speaks for everyone behind it. That is a reverse proxy: it represents the servers to the outside world.

Now picture an executive too busy to handle their own mail. They hire a personal assistant who sends letters on their behalf, screens replies, and signs for packages. To the post office, the assistant is the executive — the outside world never sees the real person. That is a forward proxy: it represents the client to the outside world. Same idea — an agent who speaks for someone — pointed in opposite directions. Hold this image; the whole chapter hangs on it.

The postal vocabulary from Part 1 maps perfectly: a proxy is the trusted middle-person who receives mail addressed to one party, reads or stamps it, and forwards it on. We will define both directions next, forward first, because once you see the forward proxy clearly, the reverse proxy is just the mirror image — and that symmetry is the single thing most engineers never quite get straight.

2. The forward proxy — an agent for the client

A forward proxy sits in front of clients, on the client's side of the conversation. The client is deliberately configured to send all its outbound requests through the proxy instead of directly to the destination. The proxy then makes those requests on the client's behalf and passes the responses back.

OSI Layer 7 (Application) — reads HTTP · can also do Layer 4 (TCP CONNECT tunnelling for HTTPS)
Fig 10.1 — A forward proxy sits in front of the clients
   CLIENT SIDE (e.g. a corporate office)              THE INTERNET
  ┌──────────────────────────────────────┐
  │   laptop A ──┐                        │
  │              │                        │            ┌──────────────┐
  │   laptop B ──┼──►  ┌───────────────┐  │            │  example.com │
  │              │     │ FORWARD PROXY │ ─┼──────────► │    server    │
  │   laptop C ──┘     │ (squid, etc.) │  │            └──────────────┘

  │   point HERE                          │      the server sees the PROXY's
  └──────────────────────────────────────┘      IP as the client, NOT laptop A

The defining detail — say it out loud — is in that last annotation: the destination server sees the proxy as the client, not the real user. When example.com logs the request, it records the proxy's IP address (Part 3). The real laptop is hidden behind it. The client knows the proxy exists (it was configured to use it); the server does not know which actual machine is behind it.

2.1 What forward proxies are used for

  • Corporate egress filtering / ACLs. A company routes all employee web traffic through a forward proxy and applies an ACL (Access Control List — a list of allow/deny rules). The proxy blocks facebook.com during work hours, denies known-malware domains, and permits the rest. Because every request flows through one box, the policy lives in one place.
  • Caching for many users. If 500 employees all download the same 80 MB installer, a caching forward proxy fetches it once and serves the other 499 from local disk — saving the expensive Internet uplink. This was the original reason the famous Squid proxy existed in the 1990s, when bandwidth was scarce.
  • Anonymity / hiding client IPs. Because the server only ever sees the proxy's address, the real clients are masked. Whole networks can present a single outward identity.
  • Access control & logging. Who went where, when? The proxy is the audit log for all outbound traffic — useful for compliance, security forensics, and "why is our bandwidth bill so high?"
  • Bypassing geo-restrictions. A client in one country routes through a forward proxy in another country; the destination sees the proxy's location and serves region-locked content accordingly.
📜 What came before — and where the VPN fits

In the early Internet, bandwidth was the bottleneck, not compute. The forward proxy was born as a caching device: CERN's httpd proxy (1994) and then Squid (1996) let a university or company share one slow, expensive Internet link among hundreds of machines by remembering popular pages. Over time the emphasis shifted from saving bandwidth to control — filtering, logging, policy enforcement — which is why corporate forward proxies are common today even though bandwidth is cheap.

A VPN (Virtual Private Network) is a close cousin worth one paragraph here. Like a forward proxy, it routes your traffic through an intermediary so the destination sees the intermediary's IP, not yours. The difference is the layer (the OSI model from Part 2): a classic forward proxy is an application-layer (L7) HTTP relay you configure per-application, whereas a VPN operates lower down (L3, the IP layer) and tunnels all of a machine's traffic — every protocol, not just HTTP — through an encrypted pipe. Both hide the client; the VPN just does it for the whole machine and adds encryption by default. Mentally file the VPN as "a forward proxy for your entire network stack."

🔑 Key point — who configures it

A forward proxy is configured by the client or the client's administrator. Your laptop, your browser, or your IT department points outbound traffic at it on purpose. Nobody on the server side sets it up or even knows it is there. Remember this — it is the exact opposite of a reverse proxy, and the contrast is the whole point of the next section.

🟢 Beginner — say it simply

A forward proxy is a middle-person your computer is told to send all its outgoing requests through. It acts on your behalf — like a personal assistant who mails your letters for you. The website you visit sees the assistant's address, not yours.

🟡 Intermediate — the mechanics

Clients are explicitly configured (browser proxy settings, system http_proxy env var, or a PAC file) to route requests to the forward proxy. For plain HTTP the proxy reads and can rewrite the request; for HTTPS the client issues an HTTP CONNECT and the proxy opens a blind L4 tunnel it cannot read (because TLS, Part 8, is end-to-end). The destination's access logs show the proxy's source IP.

🔴 Advanced — what experts know

Forward proxies are an egress control plane. In zero-trust and SASE (Secure Access Service Edge) architectures they enforce DLP (Data Loss Prevention), TLS inspection via a corporate root CA, and per-app policy. The CONNECT-tunnel blindness is deliberately broken in "TLS-inspecting" proxies by minting a certificate for the destination on the fly — which only works because the corporate CA is pre-installed on managed devices. This is the same machinery that, misused, is a man-in-the-middle attack; trust anchors are everything.

3. The reverse proxy — an agent for the servers

Now flip the picture. A reverse proxy sits in front of servers, on the server's side of the conversation. Clients connect to it thinking it is the real server — they have no idea it exists as a separate thing. It receives every inbound request, decides what to do with it, and forwards it to one of the real backend servers behind it. It represents the servers to the Internet.

OSI Layer 7 (Application) — reads & rewrites HTTP · OR Layer 4 (Transport) — blind TCP/UDP stream proxy

One-line motto"For the client.""For the server."

That DNS row is the practical heart of it, and it ties straight back to Part 6. Clients are never configured to use a reverse proxy. Nobody edits browser settings to reach your API. Instead, you publish a DNS A record — api.shop.com → 203.0.113.10 — and 203.0.113.10 is the reverse proxy's public IP. The browser resolves the name, connects to that address, and is talking to the proxy without ever knowing the difference. Your three Spring Boot instances live on private addresses (10.0.x.x) that DNS never mentions and the browser can never reach. The proxy is the only public face; the app is invisible.

🌍 Analogy — the front desk speaks for the whole company

You call a company's main number and a receptionist answers: "Acme Corp, how can I help?" You think you've reached "Acme." You haven't reached any particular person — you've reached the front desk, which then routes you to whoever can help, screens you if you're a spammer, and takes a message if everyone's busy. You never learn the direct extensions of the people in the back, and you don't need to. The reverse proxy is that receptionist: one public point of contact that represents a whole building of servers you'll never address directly. The visitor (client) didn't arrange this — the company (server operator) did.

🟢 Beginner — say it simply

A reverse proxy is a middle-person sitting in front of your servers. Visitors think they're talking to your app, but they're really talking to the proxy, which passes their request to the real server behind it — like a receptionist who answers for the whole company. Visitors don't set this up; you do, and DNS sends them to it.

🟡 Intermediate — the mechanics

The public DNS record for your service resolves to the reverse proxy's IP. It accepts the client's TCP/TLS connection, reads the HTTP request (L7) or just the byte stream (L4), selects a backend, opens its own connection to that backend, and pipes data through — rewriting headers and adding X-Forwarded-* along the way (Part 9). Backends bind to private addresses unreachable from the Internet.

🔴 Advanced — what experts know

A reverse proxy splits one logical connection into two independent ones — client↔proxy and proxy↔backend — each with its own TCP state, congestion window, and (for L7) keepalive pool. This decoupling is why a reverse proxy can speak HTTP/3 to clients while speaking HTTP/1.1 to a legacy app, buffer a slow client without tying up a backend thread, and reuse a small pool of warm upstream connections for thousands of cold client ones. The proxy is a protocol-translating, connection-multiplexing membrane, not a passthrough wire.

4. Why reverse proxies exist — what breaks without them

This is the spine of the chapter. Imagine you skip the proxy entirely: you take your Spring Boot app, bind it to a public IP on port 8080, point DNS at it, and call it production. It will work — for about a day. Then reality arrives. Below is the master list of everything a reverse proxy does, each with the one-line reason it exists and a mini-example of what breaks without it. Every later section of this chapter is just one of these expanded.

🧭 Why reverse proxies exist — the seven jobs
  1. (a) TLS termination. Why: one place to hold certificates and do the expensive crypto, so every app behind it can speak simple plaintext HTTP (Part 8). Without it: all 40 services must each load certs, renew them, and implement TLS correctly — 40 chances to leak a private key.
  2. (b) Load balancing / distribution. Why: spread requests across many app instances and route around dead ones (Part 9). Without it: one instance, one point of failure, no way to scale horizontally. An L7 load balancer simply is a reverse proxy — more on this in §6.
  3. (c) Serving static content & caching. Why: let a tiny C program (Nginx) serve your React build's files and cache responses, so the heavyweight JVM never wastes a thread handing out a logo. Without it: Spring Boot serves main.abc123.js on every page load, burning app threads on work a file server does for free.
  4. (d) Single entry point / unified domain. Why: put many backend services behind one hostname using path routing — /api to orders, /auth to login, / to the SPA. Without it: the frontend juggles five hostnames and five sets of CORS rules. (This is the seed of the API gateway — Part 13.)
  5. (e) Security shield. Why: hide internal topology, ports, and server software; centralize a WAF (Web Application Firewall — filters malicious requests), rate-limiting, and IP allowlisting; only the proxy is exposed to the Internet. Without it: your app's version banner, open ports, and stack traces are all public attack surface. (In Part 11 the proxy lives in a public subnet and the app in a private one — the proxy is the only door.)
  6. (f) Protocol & payload handling at the edge. Why: do compression, header manipulation, and request buffering to protect a slow app from slow clients (the classic slowloris attack drips bytes to exhaust threads); speak modern HTTP/2 and HTTP/3 to clients while the app speaks plain HTTP/1.1 (Part 7's versions). Without it: a handful of slow clients can pin every one of your app's request threads and take you down with almost no bandwidth.
  7. (g) Cross-cutting concerns moved out of app code. Why: authentication checks, access logging, request IDs, and observability belong at the choke point, configured once, not reimplemented in every service. Without it: every team rebuilds logging and auth, slightly differently, forever.

Read that list again and notice the through-line: every item moves work out of your application and into one operationally-managed box. The app gets to be simple — plain HTTP, one job, no certs, no CORS gymnastics, no DDoS handling — because the proxy absorbed all the messy edge concerns. That is the entire value proposition. Let's now build the canonical example that ties (a) through (g) together.

🧪 Real example — the "it worked for a day" outage

A team ships a FastAPI service straight to the Internet on 0.0.0.0:8000, no proxy. Day one is fine. Day two: a scraper opens 2,000 connections that each send one header byte per second (slowloris) — uvicorn's workers are all stuck waiting, legitimate users get timeouts. Day three: the Let's Encrypt cert they hand-installed expires and every browser shows a security warning. Day four: an attacker reads the Server: uvicorn header, looks up a known CVE, and probes it. Every single one of those failures is something a reverse proxy in front would have absorbed — buffering, central cert renewal, banner hiding. The proxy isn't a luxury; it's the part of "production" that the framework tutorial left out.

5. The canonical pattern — Browser → Nginx → Spring Boot

Here is the arrangement you will deploy more than any other in your career, and the one you specifically need: a React single-page app and a Spring Boot API, fronted by Nginx, served over HTTPS on one domain. Nginx terminates TLS, serves the React build's static files directly, and proxies /api to Spring Boot on localhost:8080. Let's build it directive by directive.

And here is the Nginx configuration that implements exactly that picture. Every line is annotated; we walk a single request through all of it immediately after.

# /etc/nginx/sites-available/shop.com
# ----------------------------------------------------------------
# Block 1: redirect all plain HTTP to HTTPS (Part 8 — never serve :80)
server {
    listen 80;
    server_name shop.com www.shop.com;
    return 301 https://$host$request_uri;     # 301 = permanent redirect (Part 7)
}

# Block 2: the real server — HTTPS, static files, and the API proxy
server {
    listen 443 ssl http2;                     # 443 = HTTPS; speak HTTP/2 to clients
    server_name shop.com www.shop.com;

    # --- TLS termination happens HERE (Part 8) ---
    ssl_certificate     /etc/letsencrypt/live/shop.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/shop.com/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;      # disable old, broken versions
    add_header Strict-Transport-Security "max-age=63072000" always;  # HSTS

    gzip on;                                  # compress text responses (Part 7)
    gzip_types text/css application/javascript application/json;

    # --- Serve the React build's static files for everything else ---
    root /var/www/react-build;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;     # SPA fallback: unknown paths go to index.html
    }

    # --- Proxy /api/ to Spring Boot on plain HTTP, port 8080 ---
    location /api/ {
        proxy_pass http://127.0.0.1:8080;     # the backend; note: same machine, private

        proxy_set_header Host              $host;              # preserve "shop.com"
        proxy_set_header X-Real-IP         $remote_addr;       # the client's true IP
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;  # XFF chain (Part 9)
        proxy_set_header X-Forwarded-Proto $scheme;            # tell Spring "https"
        proxy_set_header X-Forwarded-Host  $host;
    }

    # --- A WebSocket endpoint (Part 7) needs the Upgrade dance ---
    location /ws/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;                              # required for upgrade
        proxy_set_header Upgrade    $http_upgrade;           # carry the Upgrade header
        proxy_set_header Connection "upgrade";               # keep the connection open
        proxy_set_header Host       $host;
        proxy_read_timeout 3600s;                            # long-lived: don't time out
    }
}

5.1 Walking one request through every directive

A user clicks "View orders" in the React app. The browser issues GET https://shop.com/api/orders. Follow it through the config above:

  1. DNS & connection (Part 6). shop.com resolves to 203.0.113.10 — the Nginx box. The browser opens a TCP connection to port 443.
  2. TLS handshake (Part 8) — terminated at Nginx. Nginx presents fullchain.pem, completes the handshake, and from here on holds the decrypted plaintext. The crypto cost is paid once, here. Spring Boot will never see a byte of TLS.
  3. Path matching. The path is /api/orders. Nginx checks its location blocks: it matches location /api/, not location /. (Had the path been /dashboard, the location / block would serve index.html from disk and Spring Boot would never be involved — that is rule (c), static serving, in action.)
  4. The proxy_pass. Nginx opens its own plaintext HTTP/1.1 connection to 127.0.0.1:8080 and replays the request there. Two separate connections now exist: browser↔Nginx (HTTPS/HTTP-2) and Nginx↔Spring (plain HTTP/1.1).
  5. The headers — why each line exists:
    • Host: $host — without this, the backend would see Host: 127.0.0.1 and any code that builds absolute URLs or does virtual-hosting would break. We forward the original shop.com.
    • X-Real-IP: $remote_addr — the single true client IP, handed to the app cleanly.
    • X-Forwarded-For: $proxy_add_x_forwarded_for — appends the client IP to any existing XFF (X-Forwarded-For) chain (Part 9). Spring sees 198.51.100.7, not 127.0.0.1. This is the answer to "how do I get the real client IP behind a proxy" — it does not happen by default; you must forward it.
    • X-Forwarded-Proto: $scheme — tells Spring the original scheme was https, even though the proxy↔app hop is plain http. Without it, Spring thinks the request was HTTP and builds http:// redirect URLs — which then break in the HTTPS browser.
  6. Response back. Spring returns 200 OK + JSON over the plaintext hop. Nginx re-encrypts it into the TLS session and (because gzip on) compresses it. The browser receives encrypted, compressed JSON. It never knew Spring Boot, port 8080, or 127.0.0.1 existed.
🔑 Key point — make Spring trust the forwarded headers

Forwarding X-Forwarded-Proto is only half the fix. By default Spring Boot ignores those headers for safety (a client could forge them). You must opt in so the framework rebuilds correct https:// URLs and reports the real client IP. One line in application.properties:

# application.properties — trust the proxy's forwarded headers
server.forward-headers-strategy=framework
# (use FRAMEWORK behind your own Nginx; use NATIVE behind a cloud LB/Tomcat valve)

With this set, ServletUriComponentsBuilder, OAuth2 redirect URIs, and request.getRemoteAddr() all reflect the original https://shop.com request instead of the internal http://127.0.0.1:8080 hop. Forgetting this is the single most common "my OAuth login redirects to http:// and breaks" bug behind a reverse proxy.

🧪 Real example — this dissolves CORS entirely

Recall the CORS pain from Part 7: a React app on https://shop.com calling an API on https://api.shop.com:8443 is cross-origin (different host/port), so the browser demands preflight OPTIONS requests and Access-Control-Allow-Origin headers. With this reverse proxy, the React app and the API are served from the same origin — https://shop.com for the page, https://shop.com/api/... for the calls. Same scheme, same host, same port. The browser's same-origin policy is satisfied, no preflight fires, and you can delete all your CORS configuration. The reverse proxy didn't "allow" CORS — it made the request not cross-origin in the first place. Verify it from the terminal:

# Both come from the same origin now — no CORS headers needed
$ curl -I https://shop.com/                 # → 200, serves index.html (React)
$ curl -s https://shop.com/api/orders | jq  # → JSON from Spring Boot, same origin
# What the browser cannot do — reach the backend directly:
$ curl http://203.0.113.10:8080/api/orders  # → connection refused (app binds 127.0.0.1)
🟢 Beginner — say it simply

Nginx sits in front. It handles the padlock (HTTPS), hands out your React files directly, and forwards only the /api calls to Spring Boot. The browser sees one secure website; Spring Boot sees a simple plain-HTTP request next door. Because everything is on one address, the CORS headache disappears.

🟡 Intermediate — the mechanics

location blocks route by path: / serves the SPA from root with an index.html fallback; /api/ uses proxy_pass to the backend. TLS terminates at listen 443 ssl. proxy_set_header injects Host and X-Forwarded-* so the app reconstructs the original request, and server.forward-headers-strategy tells Spring to trust them.

🔴 Advanced — what experts know

The trailing slash semantics of proxy_pass matter: proxy_pass http://host:8080; (no URI) passes the full original path; proxy_pass http://host:8080/; (with URI) strips the matched location prefix. X-Forwarded-Proto trust must be paired with stripping any client-supplied X-Forwarded-* at the edge, or a malicious client spoofs its own source IP and scheme. HTTP/2 to the client plus HTTP/1.1 keepalive to the upstream is the standard high-throughput shape.

6. Upstream pools — the proxy and the load balancer are one box

So far the proxy forwarded to a single backend, 127.0.0.1:8080. Real systems run several app instances. Nginx's upstream block defines a pool, and suddenly your reverse proxy is also a load balancer — because it is choosing, per request, which healthy backend to forward to. These were never two different boxes; they are two hats on the same box.

# Define a pool of Spring Boot instances, then proxy to the pool by name
upstream spring_backend {
    least_conn;                       # algorithm (Part 9): fewest active conns wins
    # default is round-robin; ip_hash gives sticky sessions by client IP

    server 10.0.1.11:8080 max_fails=3 fail_timeout=15s;   # passive health check
    server 10.0.1.12:8080 max_fails=3 fail_timeout=15s;
    server 10.0.1.13:8080 max_fails=3 fail_timeout=15s;

    keepalive 32;                     # reuse up to 32 warm conns to upstreams (Parts 4/7)
}

server {
    listen 443 ssl http2;
    server_name shop.com;
    # ... ssl + static config as before ...

    location /api/ {
        proxy_pass http://spring_backend;     # forward to the POOL, not one host
        proxy_http_version 1.1;               # required to actually reuse keepalive
        proxy_set_header Connection "";        # clear "close" so the conn is reused
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Three things in that block map directly onto Part 9:

  • The algorithm. least_conn sends each request to the instance with the fewest active connections; the default is round robin (rotate evenly); ip_hash routes a given client IP to the same backend (sticky sessions). These are the exact L7 algorithms from Part 9 — because this is an L7 load balancer.
  • Health checks. Open-source Nginx does passive health checks: if a backend fails max_fails times within fail_timeout, Nginx stops sending to it for a while. It notices failures only by trying. Active health checks (Nginx proactively pinging a /health endpoint on a timer — the Part 9 ideal) require Nginx Plus (paid) or a tool like HAProxy.
  • Keepalive to upstreams. keepalive 32 holds a pool of warm TCP connections to the backends so Nginx doesn't pay a fresh TCP handshake (Part 4) on every forwarded request — the connection-reuse idea from Parts 4 and 7, applied to the proxy↔app hop. This alone can dramatically cut backend latency under load.
🔑 Key point — say it plainly

A reverse proxy and a load balancer are the same box wearing two hats. "Load balancer" emphasizes the distribution-and-health job; "reverse proxy" is the broader gateway role (TLS, caching, routing, headers, security) that includes distribution. An L7 load balancer is a reverse proxy that happens to be configured mainly to spread load. The same Nginx does both at once. Part 9 and Part 10 describe one piece of infrastructure from two angles, not two separate things you bolt together.

7. The three tools — Nginx, HAProxy, Traefik

Three reverse proxies dominate the backend world, each with a distinct personality. Knowing which to reach for — and why — is a real interview signal. Here's a character sketch, config style, and snippet for each.

7.1 Nginx — the default workhorse

Character: written in C, event-driven (one process handles thousands of connections without a thread each), and battle-tested since 2004. Nginx is simultaneously a web server, a reverse proxy, a load balancer, and a static-file server — which is exactly why it's the default front for almost everything. Its configuration is declarative: you write server / location / upstream blocks in a file and reload them atomically with nginx -s reload (no dropped connections).

Nginx is also the standard front for Node and Python apps. A FastAPI app runs under an ASGI (Asynchronous Server Gateway Interface) server like uvicorn; a Flask/Django app runs under a WSGI (Web Server Gateway Interface) server like gunicorn; Node/Express listens on a port directly. In every case Nginx sits in front and proxies to it:

# FastAPI behind Nginx:  uvicorn runs the ASGI app on 8000, Nginx fronts it
#   $ uvicorn main:app --host 127.0.0.1 --port 8000 --workers 4
location /api/ {
    proxy_pass http://127.0.0.1:8000;          # FastAPI/uvicorn (or Node/Express, or gunicorn)
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

Strengths: ubiquitous, fast, sips memory, superb at static files and TLS termination, endless documentation. Weaknesses: config is static (a reload is needed when backends change — painful in dynamic container worlds), active health checks and rich metrics are paywalled in Nginx Plus, and complex routing logic gets verbose.

7.2 HAProxy — the load-balancing specialist

Character: HAProxy (High Availability Proxy) is the surgeon of pure load balancing and proxying. It is exceptional at both L4 (raw TCP) and L7 (HTTP), has the best-in-class health checking and a famously detailed real-time stats page, and is what you reach for when distribution and observability are the whole point. Its config model is frontend (what to listen on) / backend (where to send) / acl (rules), and it reads top-to-bottom like a routing program:

# /etc/haproxy/haproxy.cfg  — path routing with an ACL
frontend https_in
    bind *:443 ssl crt /etc/haproxy/certs/shop.pem      # TLS termination here too
    acl is_api path_beg /api                            # ACL: does path start with /api ?
    use_backend spring_api if is_api                    # if so, send to API pool
    default_backend react_static                        # otherwise, the static pool

backend spring_api
    balance leastconn                                   # algorithm (Part 9)
    option httpchk GET /actuator/health                 # ACTIVE health check — HAProxy's strength
    server app1 10.0.1.11:8080 check                    # 'check' = actively probe this server
    server app2 10.0.1.12:8080 check
    server app3 10.0.1.13:8080 check

backend react_static
    server web1 10.0.1.20:80 check

Where it shines: high-performance pure load balancing, TCP (L4) proxying of non-HTTP protocols (database connections, message brokers), and environments that demand precise health checking and deep traffic metrics out of the box — all free in the open-source version, unlike Nginx. Trade-off: it is purely a proxy/LB — it does not serve static files itself, so you still need something behind it for that.

7.3 Traefik — the cloud-native, dynamic one

Character: Traefik was built for the container era. Its superpower is dynamic service discovery: instead of you editing a static config file and reloading, Traefik watches your platform — Docker, or Kubernetes (Part 12) — and auto-configures itself from labels and metadata as containers come and go. Start a new container with the right labels and Traefik is routing to it seconds later, no reload, no file edit. It also does automatic HTTPS: point it at Let's Encrypt and it obtains and renews certificates via ACME (Automatic Certificate Management Environment) on its own (Part 8).

# docker-compose.yml — Traefik configures itself FROM these labels (no static file)
services:
  traefik:
    image: traefik:v3.0
    command:
      - "--providers.docker=true"                       # watch Docker for services
      - "--entrypoints.websecure.address=:443"
      - "--certificatesresolvers.le.acme.email=ops@shop.com"
      - "--certificatesresolvers.le.acme.tlschallenge=true"   # auto Let's Encrypt
    ports: ["443:443"]
    volumes: ["/var/run/docker.sock:/var/run/docker.sock:ro"]

  api:
    image: shop/spring-api:latest                       # your Spring Boot service
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.api.rule=Host(`shop.com`) && PathPrefix(`/api`)"
      - "traefik.http.routers.api.tls.certresolver=le"  # auto-HTTPS for this route
      - "traefik.http.services.api.loadbalancer.server.port=8080"

Why it fits containers: in Docker/Kubernetes, backends are ephemeral — they scale up, scale down, and get new IPs constantly. A static Nginx file can't keep up; Traefik's whole design is to track that churn automatically. Trade-off: for a fixed fleet of long-lived servers, that dynamism is overhead you don't need, and Nginx/HAProxy are leaner and more predictable.

7.4 The others, in one line each

  • Envoy — modern, programmable (configured by a control plane via API, not files); the high-performance data plane of service meshes. You'll meet it as the sidecar proxy in Part 13.
  • Caddy — automatic HTTPS by default with the simplest config of all; great for small deployments and hobby projects.
  • Apache httpd — the original web server (1995); still widespread, especially in legacy and PHP shops, but largely superseded by Nginx for new reverse-proxy work.

Nginx is the go-to all-rounder — web server and proxy in one. HAProxy is the specialist for spreading load and watching server health. Traefik is the one that auto-configures itself when you use Docker/Kubernetes, so you don't hand-edit files as containers start and stop.

🟡 Intermediate — the mechanics

🔴 Advanced — what experts know

The real axis is static vs dynamic configuration. Static (Nginx/HAProxy) is simpler to reason about and audit but needs external automation to track ephemeral backends. Dynamic (Traefik/Envoy) trades that for a moving config surface and a control plane to secure. In Kubernetes the Ingress controller is often Nginx or Traefik generating config from the API (Part 12), and the mesh sidecar is Envoy fed by Istio's control plane (Part 13) — same proxies, different config sources.

8. Reverse proxy vs load balancer vs API gateway vs CDN

Here is the disambiguation table every engineer wants, because these four words get used interchangeably and it drives people mad. The honest truth, stated up front: all four are reverse-proxy-shaped intermediaries. They are the same fundamental thing — a box that fronts servers and relays traffic — specialized toward different emphases. The words describe intent, not incompatible hardware.

Read the table as a stack of increasing scope. A load balancer is a reverse proxy that emphasizes spreading load across a pool and routing around dead instances — the Part 9 view. An API gateway is a reverse proxy that adds per-API smarts: it authenticates the caller, enforces a rate limit, maybe rewrites the request, maybe fans one request out to three backend services and stitches the responses together (aggregation) — Part 13 builds this. A CDN (Content Delivery Network) is a geographically distributed fleet of caching reverse proxies sitting at the edge, close to users, so a request from Mumbai is served from a Mumbai cache instead of crossing an ocean — Part 14, and the latency payoff ties straight back to Part 1.

🔑 Key point — one box can be all four at once

A single Nginx instance can simultaneously be a reverse proxy (fronting your app), a load balancer (upstream with three backends), an API gateway (checking an auth header and rate-limiting), and an edge cache (proxy_cache) — see the next section. The four words are not four boxes you buy and chain together; they are four jobs the same proxy-shaped box can do. When someone asks "is this a load balancer or a reverse proxy?", the honest answer is "yes" — it depends which job you're emphasizing. The terms describe what you're using it for, not mutually exclusive product categories.

🌍 Analogy — the front desk's many duties

Back to the building's front desk. The same receptionist distributes visitors to whoever's free (load balancing), checks IDs and enforces the visitor policy (API gateway), and keeps a stack of the most-requested brochures right on the counter so they don't fetch them from the back each time (caching). Open a branch office in every city and station a receptionist at each, all sharing the brochures — now you have a CDN. It was one role — "the front desk" — all along; we just named its sub-duties.

9. Caching at the proxy

One of the proxy's most valuable jobs deserves its own section: caching. Because every response already passes through the proxy, it is the natural place to remember a response and serve the next identical request without ever bothering the backend. This is both a latency weapon (Part 1) and an origin-protection weapon (it shields your app from load), and it's the conceptual bridge to the CDN in Part 14.

# Define a cache zone, then turn it on for a location
proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=api_cache:50m
                 max_size=2g inactive=10m;

server {
    listen 443 ssl http2;
    server_name shop.com;

    location /api/products {
        proxy_pass http://spring_backend;
        proxy_cache api_cache;
        proxy_cache_key "$scheme$host$request_uri";        # what makes a response unique
        proxy_cache_valid 200 60s;                          # cache 200 OK for 60 seconds
        proxy_cache_use_stale error timeout updating;       # serve stale if backend is down
        add_header X-Cache-Status $upstream_cache_status;   # HIT / MISS / EXPIRED (debugging)
    }
}

The moving parts, each tied to an earlier chapter:

  • Cache-Control respect (Part 7). By default Nginx honours the origin's Cache-Control and Expires headers — if Spring Boot says Cache-Control: no-store, the proxy won't cache it. The HTTP caching headers from Part 7 are the contract; the proxy is one of the parties that obeys them.
  • The cache key. proxy_cache_key defines what makes two requests "the same." By default scheme + host + URI. Get this wrong (e.g. ignore a query param that changes the response) and you serve user A's data to user B — caching's classic footgun.
  • stale-while-revalidate. proxy_cache_use_stale ... updating lets the proxy serve a slightly-stale cached copy instantly while it refreshes the entry in the background — users never wait for a slow origin, and the origin sees only one refresh request instead of a stampede.
  • Micro-caching. Even a 1-second cache (proxy_cache_valid 200 1s) on a hot, mostly-read endpoint can collapse thousands of requests per second down to one hit on the backend per second. Tiny TTLs, enormous origin relief — a favourite trick for traffic spikes.
🔑 Key point — caching is a latency AND a load weapon

A cache hit is served from the proxy's RAM/disk in microseconds, skipping the backend, the database, and any cross-service calls — the full Part 1 latency story, collapsed to nearly zero. Simultaneously, every hit is a request your app and database never see, which is origin protection. Push that cache geographically close to users and you have a CDN (Part 14): caching reverse proxies at the edge, attacking distance itself.

10. Security & ops realities

The reverse proxy is the natural home for every cross-cutting concern — the choke point from §1, now wearing a security hat. Because it is the only thing exposed to the Internet, hardening it hardens everything behind it.

10.1 Hide the app — bind it to localhost

The most important security move is also the simplest, and it calls straight back to Part 5's bind-address discussion. Your app should bind to 127.0.0.1 (loopback), not 0.0.0.0 (all interfaces). Then the only way to reach it is through the proxy on the same machine — it is literally unreachable from the network.

# Spring Boot — bind to loopback only; nothing on the network can reach 8080
server.address=127.0.0.1
server.port=8080
# Now: curl from another machine to this host:8080  yields  connection refused.
# The reverse proxy on 127.0.0.1 is the ONLY thing that can talk to the app.

10.2 The rest of the proxy's security toolkit

# Rate limiting + request size limits + header hygiene, all at the edge
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=10r/s;   # 10 req/s per client IP

server {
    listen 443 ssl http2;
    server_name shop.com;

    client_max_body_size 5m;                  # reject uploads over 5 MB (block abuse)
    server_tokens off;                        # hide "nginx/1.25.3" version banner
    add_header Strict-Transport-Security "max-age=63072000" always;   # HSTS (Part 8)

    location /api/ {
        limit_req zone=api_limit burst=20 nodelay;          # enforce the rate limit
        proxy_pass http://spring_backend;
        proxy_set_header X-Request-Id $request_id;          # tag every request (Part 7)
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
  • Rate limiting (limit_req) — cap how fast any one client IP can hit you, blunting brute-force and abuse before it reaches the app.
  • Request size limits (client_max_body_size) — reject oversized bodies at the door instead of letting the app buffer a 2 GB upload into memory.
  • Header sanitization — server_tokens off hides your software version; the proxy can strip dangerous inbound headers and the app's leaky outbound ones.
  • TLS policy & HSTS centralization (Part 8) — cipher suites, TLS versions, and the Strict-Transport-Security header are set in one place and apply to every service behind the proxy. Upgrade your TLS posture once, for everyone.
  • Centralized access logs with request IDs (Part 7) — X-Request-Id generated at the edge flows through every downstream service, so one ID traces a request across your whole architecture (this is the seed of distributed tracing, Part 13).
  • Request buffering — Nginx absorbs a slow client's dribbled bytes and only forwards the request to the app once it's complete, so slow clients (slowloris) can't tie up scarce backend threads.
🧪 Real example — one request ID, end to end

A user reports "my checkout failed at 14:32." With X-Request-Id set at the proxy, that request carried req-7f3a9c through Nginx → orders-service → payment-service → the database. You grep that one ID across all log streams and reconstruct the entire path of the failed request in seconds, instead of guessing which of millions of log lines belong together. The proxy minted the ID at the one place every request passes through — exactly why cross-cutting concerns live there.

🟢 Beginner — say it simply

Only the proxy faces the Internet; the app hides on 127.0.0.1 where no outsider can reach it. The proxy is also where you block abusers (rate limits), reject giant uploads, hide your software version, and stamp each request with an ID so you can trace it later.

🟡 Intermediate — the mechanics

Binding the app to loopback removes it from the network entirely; the proxy on the same host is its only reachable peer. At the edge, limit_req, client_max_body_size, server_tokens off, centralized TLS/HSTS, and an injected X-Request-Id implement rate-limiting, size caps, banner hiding, uniform crypto policy, and traceability once for all backends.

🔴 Advanced — what experts know

The proxy is the trust boundary: it must strip client-supplied X-Forwarded-* and X-Request-Id on ingress (or an attacker spoofs source IPs and trace IDs) and re-inject its own. Buffering decouples client and upstream timelines, defeating slowloris but adding memory pressure under load — tunable via proxy_request_buffering. Layering a WAF (ModSecurity, cloud WAF) here gives one place to enforce OWASP rules; the cost is that the proxy becomes a high-value target and a potential bottleneck, so it must itself be made redundant (Part 9's "who balances the balancer" — usually DNS or anycast).

12. Interview questions

🎤 Try answering out loud before you click
What is the difference between a forward proxy and a reverse proxy? Give an example of each.

Both are intermediaries that relay traffic, but they sit on opposite sides and act for opposite parties. A forward proxy sits in front of clients, is configured by the client/its admin, and represents the client to the Internet — the destination server sees the proxy's IP, not the real user. Example: a corporate egress proxy (Squid) that filters and logs employee web traffic. A reverse proxy sits in front of servers, is set up by the server operator, and represents the servers to the Internet — clients think they're talking to the real server but reach the proxy, which forwards to a hidden backend. Example: Nginx in front of Spring Boot. One-liner: forward = "for the client, hides the client"; reverse = "for the server, hides the servers." Crucially, clients are configured for a forward proxy but reach a reverse proxy simply because DNS points the hostname at it.

Why would you put Nginx in front of a Spring Boot app?

To move every messy edge concern out of the app: (1) TLS termination — Nginx holds the cert and does the crypto once, so Spring speaks plain HTTP; (2) serve static content — Nginx hands out the React build directly instead of burning JVM threads on files; (3) load balancing across multiple Spring instances via an upstream pool; (4) one origin / unified domain — the SPA at / and the API at /api share a host, which dissolves CORS; (5) security — hide the app on 127.0.0.1, rate-limit, cap body size, hide the version banner; (6) buffering to protect the app from slow clients; (7) centralized logging, request IDs, gzip, and HTTP/2 at the edge. The app stays simple; the proxy absorbs the production concerns.

How does a reverse proxy relate to a load balancer? Are they different things?

They are the same box wearing two hats, not different boxes. A load balancer emphasizes one job — distributing requests across a pool of instances and routing around unhealthy ones. A reverse proxy is the broader gateway role (TLS, routing, caching, header manipulation, security) that includes distribution. An L7 load balancer is a reverse proxy configured mainly to spread load; one Nginx with an upstream block is doing both simultaneously. They describe emphasis, not mutually exclusive products. (An L4 load balancer is a thinner case — it proxies the TCP stream without reading HTTP, so it's a "reverse proxy" in the loosest sense but doesn't do the L7 gateway work.)

How do you preserve the real client IP through a reverse proxy?

It does not happen automatically — by default the backend sees the proxy's IP (e.g. 127.0.0.1), because the proxy opened a fresh connection to it. You must forward the original IP in a header: proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; (appends to the XFF chain) and/or X-Real-IP. Then the application must be told to trust those headers — in Spring Boot, server.forward-headers-strategy=framework — so getRemoteAddr(), logging, and rate-limiting see the true client. Security note: the edge proxy must strip any client-supplied X-Forwarded-For first, or a client can spoof its own IP.

How does putting the app behind a reverse proxy solve CORS?

It doesn't "allow" CORS — it removes the cross-origin situation entirely. CORS only triggers when the browser page and the API are on different origins (scheme/host/port). If Nginx serves the React app at https://shop.com/ and proxies the API at https://shop.com/api/, both are the same origin — same scheme, host, and port. The browser's same-origin policy is satisfied, no preflight OPTIONS fires, and you can delete all CORS headers and config. Path-based routing through one proxy hostname is the cleanest way to make a SPA and its API same-origin.

How does TLS termination at the proxy work, and what does the backend see?

The reverse proxy holds the TLS certificate and private key and is the endpoint of the client's TLS handshake (Part 8). It decrypts incoming requests and re-encrypts outgoing responses. From there it forwards requests to the backend over plain HTTP (often on a private network or loopback), so the backend never does any crypto and never holds a cert. Benefits: certificates live in one place, the expensive crypto is centralized (and can be hardware-accelerated), and TLS policy is uniform. The proxy adds X-Forwarded-Proto: https so the app knows the original request was HTTPS. The hop between proxy and backend is plaintext, which is fine inside a trusted network; "re-encrypt" / mutual-TLS modes exist when that hop must also be secured.

How does a reverse proxy proxy a WebSocket connection?

A WebSocket (Part 7) starts as an HTTP request with Upgrade: websocket and Connection: Upgrade headers, then switches the TCP connection to the WebSocket protocol. A reverse proxy must explicitly support this: in Nginx you set proxy_http_version 1.1;, forward proxy_set_header Upgrade $http_upgrade; and proxy_set_header Connection "upgrade";, and raise proxy_read_timeout because the connection is long-lived and otherwise idle. With those, the proxy passes the upgrade handshake through and then relays the bidirectional frames transparently. Forget them and the upgrade fails or the socket drops after the default idle timeout.

Nginx vs HAProxy vs Traefik — when do you pick each?

Nginx: the default all-rounder — web server, reverse proxy, static file server, and L7/L4 proxy in one, with declarative config; pick it as the standard front for almost any app, especially when you also need to serve static files and terminate TLS. HAProxy: the load-balancing/proxy specialist with the best free active health checks, a great stats page, and strong L4 (TCP) proxying; pick it for high-performance pure load balancing or proxying non-HTTP protocols. Traefik: cloud-native with dynamic service discovery from Docker/Kubernetes labels and automatic Let's Encrypt; pick it in container environments where backends constantly come and go and you don't want to hand-edit config. (Bonus: Envoy for service meshes; Caddy for dead-simple auto-HTTPS.)

Why does a reverse proxy usually make things faster, not slower?

Although it adds a hop, the net effect is almost always faster because: (1) caching serves hits in microseconds without touching the backend; (2) TLS offload moves expensive crypto off the app and can use optimized/accelerated libraries; (3) upstream keepalive reuses warm connections to backends, skipping repeated TCP/TLS handshakes; (4) buffering frees backend threads from slow clients; (5) compression and HTTP/2/3 at the edge cut bytes and round trips. The extra in-data-center hop costs sub-millisecond latency (Part 1), dwarfed by these savings. It slows things only if badly misconfigured (e.g. caching disabled, no keepalive, or itself under-provisioned).

What does X-Forwarded-Proto do and why does Spring Boot need it?

It tells the backend the scheme of the original client request. Since TLS terminates at the proxy, the proxy↔app hop is plain http; without this header the app believes the whole request was HTTP and builds http:// redirect and absolute URLs — which then break in the user's HTTPS browser (mixed-content errors, broken OAuth redirects). The proxy sends X-Forwarded-Proto: https, and once Spring is configured to trust it (server.forward-headers-strategy=framework), ServletUriComponentsBuilder and redirect logic correctly emit https://. It's the standard fix for "my login redirects to http and fails behind a proxy."

Reverse proxy, API gateway, and CDN — how do they differ?

All three are reverse-proxy-shaped; they differ by emphasis and scope. A reverse proxy is the general single-front-door role (TLS, routing, headers, caching). An API gateway (Part 13) is a reverse proxy specialized for APIs — it adds authentication, rate-limiting, request/response transformation, aggregation across services, and per-route policy. A CDN (Part 14) is a globally distributed fleet of caching reverse proxies placed near users, so content is served from a nearby edge instead of the distant origin — attacking latency via geography. One Nginx can act as all three at small scale; at large scale you use purpose-built products, but the underlying pattern is identical.

Clients must be configured to use a reverse proxy — true or false?

False — that's the forward-proxy property. Clients are not configured for a reverse proxy and usually don't know it exists. They simply resolve the service's hostname via DNS (Part 6), and that DNS record points at the reverse proxy's IP. The client connects to what it believes is the real server. The configuration burden is entirely on the server operator. (Contrast: a forward proxy requires client configuration — browser proxy settings, system env vars, or a PAC file.)

13. Common misconceptions

❌ Myths engineers actually believe

❌ "A proxy and a reverse proxy are the same thing."
✅ "Proxy" alone usually means a forward proxy — it sits in front of clients and acts for the client. A reverse proxy sits in front of servers and acts for the servers. They're mirror images on opposite ends of the conversation: one hides the client from the server, the other hides the servers from the client. Same mechanism (relaying), opposite direction and opposite beneficiary.

❌ "A reverse proxy and a load balancer are different boxes you chain together."
✅ They're the same box wearing two hats. An L7 load balancer is a reverse proxy whose emphasis is distributing load; a reverse proxy with an upstream pool is load balancing. One Nginx does both at once. The words describe which job you're highlighting, not separate appliances. They are not mutually exclusive.

❌ "Clients must be configured to use a reverse proxy."
✅ Clients are never configured for it and usually don't know it's there. DNS points the hostname at the proxy's IP, the client connects believing it's the real server, and the proxy forwards to a hidden backend. Client configuration is a forward-proxy thing.

❌ "Adding a reverse proxy slows everything down — it's an extra hop."
✅ It almost always speeds things up. Caching serves hits in microseconds, TLS offload and upstream keepalive cut handshake costs, buffering frees backend threads, and edge compression/HTTP-2 reduce bytes and round trips. The in-data-center hop it adds is sub-millisecond — dwarfed by those savings. It's slow only when misconfigured.

❌ "Nginx can't load-balance — that's only for AWS ALB / hardware boxes."
✅ Nginx (and HAProxy, Traefik, Envoy) are full L4/L7 load balancers via their upstream/ backend pools, with round-robin, least-connections, and IP-hash algorithms and health checks. An ALB is just a managed reverse proxy AWS runs for you; software proxies do the identical job, often on your own EC2 box (Part 11).

❌ "The app server sees the real client's IP through a proxy by default."
✅ By default it sees the proxy's IP, because the proxy opened a new connection to it. You must forward the original IP via X-Forwarded-For/X-Real-IP and tell the app to trust those headers (server.forward-headers-strategy in Spring). Forgetting this is why "all my users appear to come from 127.0.0.1" in the logs.

❌ "The backend still does TLS — the proxy just passes encryption through."
✅ With TLS termination (the common setup), the proxy decrypts at the edge and talks plain HTTP to the backend, which holds no certificate and does no crypto. (Passthrough and re-encrypt modes exist, but the default reason to use a proxy is precisely to remove TLS from the app.)

❌ "A reverse proxy is only needed for big, multi-server systems."
✅ Even a single app on one server benefits enormously: HTTPS termination, static serving, security shielding (bind app to 127.0.0.1), buffering, gzip, and one clean origin. The reverse proxy is "the missing half of production" the framework tutorial skipped — useful from instance number one.
