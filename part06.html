DNS — The Internet's Phonebook

Part 3 gave every machine an address. Part 5 gave every program a port. Yet you have never typed an IP address to reach Google — you type names. This part is about DNS, the system that turns google.com into 142.250.183.78 trillions of times a day: the oldest and most successful distributed database ever built, and the reason the most repeated sentence in operations is "it's always DNS."

📍 OSI Layer 7 — Application

First, place DNS (Domain Name System) on Part 2's map. It feels like infrastructure — it serves every other protocol — so engineers are surprised that it sits at Layer 7, the application layer. But look at what it is: a client process sends a small request to a server process listening on well-known port 53 (Part 5), and gets a response. Request–response between two programs, with its own message format, riding on UDP or TCP (Part 4) — the definition of an application protocol. Layers 1–4 neither know nor care that this particular datagram is "special." DNS is infrastructure sociologically, not technically: an ordinary application that every other application happens to call first.

1. Why DNS exists

Count the names in your own stack: registry.npmjs.org, github.com, postgres in a Compose file, kafka1:9092, orders-service in a Kubernetes manifest, api.shop.example.com in a frontend .env. You work in names all day — yet Part 3 was emphatic that machines route by IP addresses and nothing else. Someone is translating constantly. Why does that translation layer deserve to exist?

🧭 Why DNS exists — four reasons, in increasing order of importance
  1. (a) Humans cannot memorize IPs. 142.250.183.78 is hostile to memory and marketing; google.com is not. With IPv6 it gets hopeless — nobody dictates 2001:db8:85a3::8a2e:370:7334 over the phone.
  2. (b) IPs change; names persist. The professionally important reason. Relaunch an EC2 instance: new IP. Fail a database over to its replica: new IP. A name is a stable identity over an unstable address — indirection — so you can redeploy, migrate, and fail over without telling your users anything.
  3. (c) One name → many IPs. google.com cannot be one machine. One name resolving to many addresses spreads load across a fleet and routes users to a nearby region (section 12).
  4. (d) Many names → one IP. blog.example.com, shop.example.com, and docs.example.com can share one server running one nginx, serving a different site per requested name — virtual hosting. It works because the name arrives inside the request itself: the Host header, explained first thing in Part 7.

Now the counterfactual. Suppose DNS vanished and everything used raw IPs: your application.yml holds IPs for the database, Redis, and Kafka; partners hardcoded your API's IP into their systems; mobile apps shipped with it baked in. Now migrate clouds. Every copy must change at the same instant — including ones in other companies' codebases and on phones that will never update. Every migration is a coordinated catastrophe. DNS puts the mapping in one place you control, consulted (freshly enough — see TTL, section 7) by everyone.

🔑 Key point

Names are the API; IP addresses are the implementation. DNS is the indirection layer that lets the implementation change without breaking callers — the reason you code against interfaces in Java. Most traffic tricks later in this course (blue-green, canaries, failover, CDNs) are someone editing what a name resolves to.

🌍 Analogy — the phonebook, but genuinely better

The classic analogy: DNS is the Internet's phonebook — know the name, look up the number. Good start — but DNS beats it in four ways. A phonebook is printed once; DNS is live-edited by millions of owners, each maintaining only their own page (delegation, section 3). A phonebook is one volume; the DNS "book" exists nowhere in full — it is assembled on demand from servers each holding a fragment (distribution). You look up a phonebook yourself; in DNS a librarian makes the calls for you and remembers recent answers on sticky notes (recursion and caching, sections 5 and 7). And a phonebook gives everyone the same answer; DNS may deliberately answer by location and health (section 11). Where the analogy honestly breaks: a phone number identifies a person and rarely changes, so a stale phonebook stays useful for years. An IP identifies a network location and changes routinely — so DNS entries are built to expire, each stamped with a freshness deadline (TTL). The phonebook quietly rots; DNS made rot a managed, configurable feature.

2. Before DNS: one text file for the whole Internet

📜 What came before

In the ARPANET era (Part 1), name-to-address mapping was one text file, HOSTS.TXT, maintained by hand at the Network Information Center at SRI (Stanford Research Institute) — "NIC," colliding with Part 1's network interface card; this NIC was an office with people in it. Every host periodically downloaded the whole file over FTP (File Transfer Protocol). A new hostname meant contacting the NIC, waiting for a human to edit the file, then waiting for everyone to re-download. It collapsed for four reasons: scale (file size and fetch traffic grew with every host on Earth); update lag (your mapping was invisible until each host re-downloaded — days of staleness); name collisions (one flat, first-come namespace — two sites could not both be mail); and a single bottleneck (one organization, one master file, one point of failure). In 1983 Paul Mockapetris designed the replacement (RFC 882/883): a database that is distributed (no single copy), hierarchical (a tree — no collisions), delegated (each organization edits its own branch, instantly), and cached (answers remembered near the askers). Each property negates one HOSTS.TXT failure.

The delightful part: HOSTS.TXT never died. Every OS carries a local descendant and consults it before asking DNS anything: /etc/hosts on Linux/macOS, C:\Windows\System32\drivers\etc\hosts on Windows. The fossil is load-bearing — and a precision tool:

🧪 Real example — using the hosts file to test before a DNS cutover

You are about to repoint shop.example.com to 198.51.100.20 and want to verify the new box serves correctly under its real name (TLS certificates and virtual hosting both care — Parts 7–8). Override DNS for your machine only:

# Linux / macOS: sudo nano /etc/hosts
# Windows:       notepad (run as Administrator)
#                C:\Windows\System32\drivers\etc\hosts

127.0.0.1       localhost              # the classics, already there
::1             localhost

# temporary override — THIS machine only:
198.51.100.20   shop.example.com       # staging box. REMOVE after cutover!

Your browser and code now resolve shop.example.com to staging while the world gets production. Flush the OS cache to apply (ipconfig /flushdns on Windows, sudo dscacheutil -flushcache on macOS). Two warnings: remove the line afterwards (a forgotten entry is a classic "works only on my machine" generator), and some tools bypass the file — dig speaks DNS directly (section 8), as does Node's dns.resolve() (section 11).

  • The root is the unnamed top, written as a single dot .
  • A TLD (Top-Level Domain) is a direct child of the root: com, org, country codes like in, plus the newer wave (io, dev). TLDs are administrative real estate — .io is technically a country code, .dev is run by Google — each operated under rules set by ICANN (the Internet Corporation for Assigned Names and Numbers).
  • A second-level domain is what you buy: example.com.
  • Subdomains are everything you create below it — free, instant, no permission needed: shop.example.com, api.shop.example.com, as deep as you like.

3.1 FQDNs and the secret trailing dot

An FQDN (Fully Qualified Domain Name) is the complete path from leaf to root — and written pedantically it ends with a dot: api.shop.example.com. The final dot is the root, and it is not a typo: it marks the name absolute. A name without it is technically relative, and resolvers may complete it from a configured search list — exactly like relative vs absolute filesystem paths. Sounds like trivia until Kubernetes (section 11), where the search list is the entire trick behind short names like orders resolving at all. Browsers hide the dot; zone files and dig do not.

3.2 Zones and delegation — the design that makes it scale

🧭 Why a delegated tree, not one big database

The genius is not the tree — it is who runs each part. A zone is a contiguous region of the tree managed by one party on its own servers: the root zone (root operators), com (Verisign), example.com (you, via whoever you choose). The tree is stitched by delegation: a parent zone holds NS (Name Server) records saying "for everything under this name, ask those servers." NS records are the glue of the whole system — how com hands example.com to you. The payoff: edit a record in your zone and it is live on your servers immediately, with zero coordination with Verisign or ICANN — the exact opposite of emailing the NIC. Scale, autonomy, and instant updates all fall out of one idea: every owner runs their own page of the phonebook.

🌍 Analogy — delegation is an org chart, not an encyclopedia

Ask a CEO "who owns the payments retry logic?" — a good CEO does not know, but knows which VP owns payments; the VP knows the team lead; the lead knows the engineer. Nobody knows everything; everyone knows one level of "who to ask next," and each manager staffs their own slice without filing paperwork upward. DNS is exactly this: root knows only TLD servers; com knows only each domain's nameservers; yours know your records. The weak spot: a company's chain takes days — DNS referrals complete in milliseconds, and caching means the chain is rarely walked at all (section 7).

  • The stub resolver — a small client inside your OS (what getaddrinfo() calls). Deliberately dumb: it checks the hosts file and a local cache, then forwards everything to one configured recursive resolver. Who configured that address? DHCP (Dynamic Host Configuration Protocol) — the same Part 3 handshake that leased your IP also handed you a DNS server.
  • The recursive resolver — the workhorse. It accepts your question and takes on the obligation to find the full answer, walking the hierarchy and caching everything it learns. Run by your ISP (Internet Service Provider) by default, or a public operator: 8.8.8.8 (Google), 1.1.1.1 (Cloudflare), 9.9.9.9 (Quad9). Clouds run their own (Part 11).
  • The root servers — the entry point. They know one thing: where each TLD's servers are. There are 13 named identities, a.root-servers.net through m.root-servers.net, run by 12 organizations (Verisign runs two) — emphatically not 13 machines (history box below).
  • The TLD nameservers — run by each TLD's registry. Verisign's .com servers (a.gtld-servers.net and friends) hold NS delegations for ~160 million domains. They do not know your A records; they know who does.
  • The authoritative nameservers — hold your zone's records and answer with authority: Route 53, Cloudflare DNS, or your own ns1.example.com. The only place shop.example.com → 203.0.113.80 truly lives; everything else is referral or cache.
📜 Why exactly 13 root servers — a 512-byte fossil

Early DNS over UDP capped messages at 512 bytes (section 10), and the full list of root servers — names plus IPs — had to fit in one such message so a resolver could bootstrap with a single query. Thirteen entries fit. The number stuck; the constraint did not: each identity is now announced via anycast (Part 3 — one IP advertised from many places, routing delivers you to the nearest) from well over 1,700 physical instances worldwide. Query a.root-servers.net (198.41.0.4) from Mumbai and you reach a machine near India, not a bunker in the US.

5. Recursive vs iterative queries

Two query styles coexist in every resolution, and interviewers love the distinction:

  • A recursive query says: "give me the final answer; I'll wait while you do whatever it takes." Your stub sends exactly this to the resolver — one question out, one finished answer back. The stub never meets the hierarchy.
  • An iterative query says: "tell me what you know; I'll take it from there." The resolver asks root, TLD, and authoritative servers iteratively — and the first two reply with referrals: "I don't know, but ask them; here are their addresses." The resolver follows the trail itself.

🌍 Analogy — the hotel concierge

You ask a concierge for "a table tonight at the best sushi place." You don't care that they called three restaurants and chased two "try our other branch" referrals — you asked once and got a finished result: your stub's recursive query. Each restaurant behaved iteratively, answering only with what it knew, never making calls on the concierge's behalf. A good concierge also writes the answer down — the next guest gets it from memory. Where the analogy bends: the resolver's notes carry a contractual obligation to forget after TTL seconds — on the Internet, restaurants change buildings constantly.

🔑 Key point

The split is load engineering: root and TLD servers stay fast by refusing recursion — stateless referrals only — while the patient, cache-heavy work concentrates in resolvers near users. The contract is visible in the protocol: the stub sets the rd flag (recursion desired); the resolver's reply sets ra (recursion available). Section 8 shows both.

6. The full journey: you type https://google.com and press Enter

The centerpiece. Before a single byte of HTTP can exist — before TCP can even attempt its three-way handshake (Part 4) — the browser needs an IP. Here is the complete resolution story, assuming the worst case: every cache cold. (Section 7 shows why the worst case is rare.)

  1. Step 0 — browser cache. The browser keeps its own small DNS cache (Chrome's is visible at chrome://net-internals/#dns; entries capped around a minute). Hit? Done, ~0 ms. Miss? Continue.
  2. Step 1 — OS cache and hosts file. The browser calls getaddrinfo(), landing in the stub resolver, which checks the hosts file first (section 2's fossil), then the OS cache (ipconfig /displaydns shows it on Windows). Hit? Under a millisecond. Miss? Continue.
  3. Step 2 — stub asks the configured resolver. One UDP datagram to port 53 (Part 5's well-known port) of the recursive resolver, rd flag set. Who configured the resolver's address? DHCP did, back in Part 3, in the same lease that assigned your IP.
  4. Step 3 — resolver cache miss. The resolver checks its enormous shared cache. For google.com a miss is nearly impossible in real life — but we said cold, so it walks the tree, iteratively.
  5. Step 4 — ask the root. "A record for google.com?" The root (reached via anycast, Part 3) answers with a referral: "I only know TLDs. For com, ask these servers — here are their names AND their IPs." Including the IPs is the small-but-crucial idea of glue records: without them, resolving the nameserver's own name would itself require DNS — chicken-and-egg. Glue is the egg supplied with the chicken.
  6. Step 5 — ask the .com TLD. Same question. Referral again: "google.com is delegated to ns1–ns4.google.com — addresses attached (glue again, since those nameservers live inside the zone they serve)."
  7. Step 6 — ask Google's authoritative server. ns1.google.com owns the zone and returns the real thing, flagged authoritative: google.com. 300 IN A 142.250.183.78. (Possibly a different IP than a friend abroad gets — big operators answer by query origin; sections 11–12.)
  8. Step 7 — the answer flows back and is cached at every level. Resolver caches it (for TTL seconds — 300 here), stub caches it, browser caches it. The next asker on that resolver skips steps 4–6 entirely.
  9. Step 8 — the browser hands the IP to TCP. Resolution over; networking begins. TCP three-way handshake to 142.250.183.78:443 (Part 4), then TLS (Part 8), then HTTP. The story continues in Part 7.

🔑 Key point

All of this happens before any TCP connection to Google can exist — Part 4's SYN packet needs a destination IP, and until DNS answers there isn't one. DNS latency is a tax on connection setup, paid before TLS and HTTP add their own round trips. Hence DNS prefetching and connection reuse (no new connection, no lookup) — and "every request does a DNS lookup" lands on section 15's misconception list.

🟢 Beginner — say it simply

Your computer checks its own notes first (browser cache, hosts file, OS cache). If unknown, it asks its resolver, which asks the root ("who handles .com?"), then .com ("who handles google.com?"), then Google's own server, which gives the IP. Everyone remembers the answer for next time; only then does the browser connect.

🟡 Intermediate — the mechanics

Stub → resolver (recursive, rd set) → iterative walk: root refers to TLD with glue; TLD refers to the domain's NS with glue; authoritative answers with the record, TTL, and aa flag. Caching at resolver, OS, browser. Cold ≈ 20–120 ms; warm ≈ sub-millisecond. Resolution strictly precedes the handshake: time-to-first-byte = DNS + TCP + TLS + HTTP.

🔴 Advanced — what experts know

Real resolvers parallelize and short-circuit: hot TLD referral sets (two-day TTLs), racing multiple authoritative servers, qname minimization (RFC 9156 — asking the root only "com.?" for privacy). Failure modes live in stub timeout/retry behavior (~5 s timeouts make a flaky resolver feel like "the whole Internet is down") — why node-local DNS caches exist in Kubernetes (Part 12). And cached answers carry a decremented TTL, so two clients of one resolver see different remaining lifetimes — the diagnostic trick in section 8.

7. Caching and TTL — the craft of going stale gracefully

The cold walk is rare; the cache hit is the norm. The whole economy of DNS — its speed and its biggest operational gotcha — is governed by one number on every record: the TTL (Time To Live), in seconds.

🔑 Key point — two unrelated things are both called TTL (Part 3 callback)

Part 3's IP header has a TTL: a hop counter routers decrement to kill looping packets (the field traceroute exploits). DNS TTL is a cache lifetime in wall-clock seconds: "you may reuse this answer for this long." Same name, zero relationship.

You can watch TTL working — ask twice and the resolver hands back the same cached answer with the remaining lifetime counting down:

$ dig +noall +answer shop.example.com
shop.example.com.   300   IN   A   203.0.113.80    ← fresh from authoritative: full TTL 300

$ dig +noall +answer shop.example.com    # ~20 seconds later, same resolver
shop.example.com.   280   IN   A   203.0.113.80    ← cached copy: 280 s of life left

$ dig +noall +answer shop.example.com    # after the countdown hits zero
shop.example.com.   300   IN   A   203.0.113.80    ← expired → re-fetched → fresh TTL
🌍 Analogy — expiry dates, not announcements

Every cached answer is a carton of milk with a best-before date. When you change a record you cannot send a recall notice to every fridge on Earth — there is no list of fridges. You just start handing out new cartons, and old ones expire wherever they sit, on their own schedules. So the universal phrase "waiting for DNS to propagate" is wrong about the mechanism: nothing propagates outward; cached answers expire independently and fresh queries fetch the new truth. The analogy also carries the trade: shorter dates = fresher milk but constant trips to the store (query load, cache-miss latency); longer dates = cheap and fast but stale after a change.

7.1 The operational craft: the pre-migration TTL playbook

TTL is a dial you are expected to turn. Repointing shop.example.com to a new IP:

  1. At least one full old-TTL before the cutover (a day ahead if TTL is 86,400), lower the TTL to ~60. Why so early? Caches serve the old TTL until it runs out — you cannot shorten a promise already made.
  2. Cut over: change the A record. Worst-case staleness is now ~60 seconds.
  3. Verify (dig @8.8.8.8, dig @ns1… at the authoritative — section 8); keep the old box alive until its traffic drains.
  4. Raise the TTL back (300–3600) to stop paying the query-load tax for agility you no longer need.
Low TTL (30–60 s)High TTL (1–24 h)

7.2 Negative caching — even "no" gets remembered

Resolvers also cache NXDOMAIN ("non-existent domain") answers, for a duration set by your zone's SOA (Start of Authority) record — its last field, historically called minimum, repurposed by RFC 2308 as the negative-caching TTL. The classic sting: you hit api.shop.example.com before creating the record, get NXDOMAIN, and your resolver caches that "no" for, say, 300 seconds. You then add the record — correct and live at the authoritative servers — and your machine keeps saying the name doesn't exist until the negative cache expires. The typo'd record that "stays broken" briefly after you fix it is the same effect. Not haunted; RFC 2308.

🟢 Beginner — say it simply

Every answer carries a use-by time in seconds. Browsers, your OS, and resolvers remember answers until expiry — that's why DNS is usually instant, and why changes take time to be seen: old answers expire on their own; nothing pushes updates. Even "that name doesn't exist" gets remembered for a while.

🟡 Intermediate — the mechanics

The zone owner sets TTL per record; caches serve answers with the remaining TTL counting down. Playbook: drop TTL one old-TTL early, cut over, verify, raise. Negative answers cache per the SOA minimum (RFC 2308). The trade is freshness vs query load, latency, cost, and mistake blast-radius — and the protocol has no push invalidation, period.

🔴 Advanced — what experts know

TTL is a contract not everyone honors: some resolvers clamp very low TTLs upward, the JVM ignores DNS TTLs entirely (section 11), and serve-stale resolvers (RFC 8767) deliberately answer with expired data when authoritative servers are down — availability over correctness. Treat TTL as a probabilistic convergence horizon, never a deadline: anything that must flip atomically belongs behind a load balancer (Part 9), not a DNS change.

9. The record types that matter

A zone is, concretely, a set of typed resource records. Zone files (the classic BIND text format) remain the lingua franca even when your "zone file" is a Route 53 console or Terraform. Here is example.com with one of everything; then the types one at a time:

$ORIGIN example.com.        ; names below not ending in "." get this appended
$TTL 3600                   ; default TTL: 1 hour

; name            TTL    class  type    value

                                          2026061201 ; serial  (bump on every edit)
                                          7200       ; refresh   (secondary sync)
                                          900        ; retry
                                          1209600    ; expire
                                          300 )      ; minimum → NEGATIVE-cache TTL (§7.2)
@                 3600   IN     NS      ns1.exampledns.net.    ; who serves this zone
@                 3600   IN     NS      ns2.exampledns.net.    ; (always at least two)
@                 300    IN     A       203.0.113.42           ; the apex: example.com itself
@                 300    IN     AAAA    2001:db8:f00d::42      ; same, IPv6

shop              300    IN     A       203.0.113.80
api.shop          60     IN     A       203.0.113.81           ; = api.shop.example.com.
@                 3600   IN     MX      10 mail1.example.com.  ; mail, priority 10 (preferred)
@                 3600   IN     MX      20 mail2.example.com.  ; backup mail host
@                 3600   IN     TXT     "v=spf1 include:_spf.example.net -all"

; "@" = the zone apex (the bare name example.com itself)
; trailing dots matter: "mail1.example.com." is absolute

9.1 A — name to IPv4

The workhorse: name → 32-bit IPv4 address (Part 3). You touch it for every "point this domain at that server" moment and every migration. Multiple A records on one name = round-robin (section 12).

9.2 AAAA — name to IPv6

The same mapping for IPv6 — "quad-A" because IPv6 addresses are 128 bits, four times an A record's 32 (Part 3 callback). IPv6-capable clients ask for A and AAAA in parallel and prefer AAAA. You touch it when enabling IPv6 on an ALB/CloudFront, and when debugging "works on 4G (IPv6), fails on office Wi-Fi (IPv4)" mysteries.

9.3 CNAME — an alias to another NAME (never an IP)

A CNAME (Canonical Name) record says "this name is an alias; the canonical name is over there — go resolve that." It points to a name, never an IP:

www.example.com.    3600  IN  CNAME  example.com.
shop.example.com.   300   IN  CNAME  my-alb-1234567890.ap-south-1.elb.amazonaws.com.
                                     ; ▲ the classic backend use: alias onto an AWS load
                                     ;   balancer's hostname — its fleet of IPs changes
                                     ;   constantly; you could never maintain A records

Two iron rules, the second of which spawned an AWS feature:

  • Rule 1 — a CNAME'd name can hold no other records. "This name is really that name" is an exclusive claim; an A or MX alongside would contradict it.
  • Rule 2 — no CNAME at the zone apex. The apex (example.com itself) is required to hold SOA and NS records — and rule 1 forbids roommates. So the bare domain cannot be a CNAME… yet the thing you most want at the apex is an alias to an ALB hostname. This collision is why Route 53 invented the ALIAS record (section 11): CNAME-like behavior resolved server-side, answered to clients as plain A records — legal at the apex. (The ALB behind it: Parts 9 and 11.)
🌍 Analogy — "see other entry," with a cost

A CNAME is the index entry "Sockets — see Ports & Sockets." Useful indirection: the real entry moves, every cross-reference stays valid. But each "see…" sends the reader on another lookup — and CNAME chains do that to resolvers: a → CNAME → b → CNAME → c → A can cost extra resolutions on a cold cache (resolvers bundle what they can, but cross-zone chains routinely add round trips). One alias is a tool; three is a smell — "CNAME chains are free" is on section 15's list.

9.4 MX — where this domain's mail goes

An MX (Mail eXchanger) record names the host accepting email for the domain, with a priority — lower wins; higher values are backups. Why not just use the A record? Because mail should not have to go to the machine serving the website: example.com's web traffic goes to your servers while its mail goes to Google Workspace, neither knowing about the other. MX is DNS doing service-specific routing — and the record you break once in your career while "cleaning up" a zone.

example.com.   3600  IN  MX  1   aspmx.l.google.com.         ; primary (Google Workspace)
example.com.   3600  IN  MX  5   alt1.aspmx.l.google.com.    ; backups, tried in order
example.com.   3600  IN  MX  10  alt2.aspmx.l.google.com.

9.5 TXT — free-form proof and policy

A TXT record holds arbitrary text — the duct tape of DNS, with two big uses. Proof of control: services verify domain ownership by asking you to publish a token only the owner could — Google's google-site-verification=…, AWS ACM (AWS Certificate Manager) validation records before issuing a certificate. Part 8 reuses exactly this trick: certificate authorities accept a DNS TXT challenge (_acme-challenge) as proof you control a domain. Email policy: the anti-spoofing trio lives in TXT — SPF (Sender Policy Framework: which servers may send mail as you), DKIM (DomainKeys Identified Mail: a public key verifying mail signatures), DMARC (Domain-based Message Authentication, Reporting & Conformance: what receivers do with failures).

example.com.            3600  IN  TXT  "v=spf1 include:amazonses.com -all"
selector1._domainkey    3600  IN  TXT  "v=DKIM1; k=rsa; p=MIIBIjANBgkq...key"
_dmarc                  3600  IN  TXT  "v=DMARC1; p=quarantine; rua=mailto:dmarc@example.com"

9.6 NS — the delegation glue

NS (Name Server) records are section 3's delegation made flesh — the records that make the tree a tree. They live in two places: the parent zone (the .com servers holding example.com. NS ns1.exampledns.net. — that is the delegation) and your own zone. You touch them when changing DNS hosts — at the registrar, because the operative copies live in the parent zone, not yours.

9.7 PTR — reverse DNS: IP back to name

A PTR (Pointer) record answers the inverse question: which name belongs to 203.0.113.80? Reverse lookups reuse the ordinary tree via a special domain, in-addr.arpa, with the IP's octets reversed so the tree's broad-to-specific order matches the address:

; forward: name → IP    (lives in example.com's zone — the DOMAIN owner controls it)
shop.example.com.            300  IN  A    203.0.113.80

; reverse: IP → name    (lives under in-addr.arpa — the IP BLOCK's owner controls it)
80.113.0.203.in-addr.arpa.   300  IN  PTR  shop.example.com.
;  ▲ octets reversed: 203.0.113.80 → 80.113.0.203   (IPv6: same idea under ip6.arpa)

Who controls PTR? Not you — the reverse tree is delegated along address-block ownership, down to whoever owns the IP range: your cloud or ISP (you file a request with AWS for a PTR on your Elastic IP; in-addr.arpa is not your zone). Who uses it: mail servers, heavily — receivers distrust senders whose PTR doesn't match their name (forward-confirmed reverse DNS), making PTR table stakes for deliverability — plus logging pipelines and traceroute, which decorate IPs with names.

9.8 Briefly: SRV and CAA

SRV (Service) records generalize MX to any service: _service._proto.name maps to a priority, weight, port, and target host — name and port discovery in one query (DNS otherwise never tells you ports — Part 5's problem). The web ignored SRV, but the idea won inside infrastructure: Kubernetes publishes SRV records for named service ports, and Consul's DNS interface serves them for service discovery (Parts 12–13). CAA (Certification Authority Authorization) records whitelist which certificate authorities may issue certificates for your domain — 0 issue "letsencrypt.org" means everyone else must refuse. One line of hygiene against mis-issuance; the certificate story is Part 8's.

The type system is where DNS politics shows: SRV solved name+port discovery in 2000 and the web ignored it — ossification, the same story Part 4 told about middleboxes. And the CNAME-at-apex saga is standards archaeology: vendors shipped proprietary fixes (ALIAS, CNAME flattening) because amending a 1987 rule would break four decades of deployed resolvers. When a rule looks absurd, check what year it made perfect sense.

10. Transport: why UDP, when TCP, and who's reading your queries

🧭 Why DNS chose UDP port 53

Run Part 4's arithmetic. A DNS exchange is tiny: a question of a few dozen bytes, an answer classically under 512. Over UDP that is one datagram out, one back — one round trip, total. Over TCP, the same exchange pays the three-way handshake first (a full RTT before any data), then the query/answer trip, then teardown — at least double the latency, plus connection state on servers answering millions of queries a second. For a one-shot, idempotent question, reliability machinery is dead weight: if a datagram is lost, the resolver simply asks again — the retry is the recovery protocol. UDP gives DNS exactly the Part 4 trade it wants.

But TCP was never optional — port 53 is reserved on both transports (Part 5), and DNS switches to TCP in defined cases:

  • Truncation. Classic DNS-over-UDP capped messages at 512 bytes (the limit that froze the root count at 13). An answer that doesn't fit is sent truncated with the TC flag set — the client's instruction to retry over TCP. EDNS0 (Extension Mechanisms for DNS, version 0) defused most of this by letting clients advertise bigger UDP buffers — the EDNS: … udp: 1232 line in section 8's dig output — but large answers (many records, DNSSEC signatures) still overflow into TCP.
  • Zone transfers. AXFR (a full zone copy, syncing primary and secondary nameservers) is bulk data needing reliability: always TCP.

One paragraph on the modern privacy layer: classic DNS is plaintext — everyone between your stub and the resolver (coffee-shop Wi-Fi, your ISP) can read and log every name you look up, a remarkably complete diary of your life. DoT (DNS over TLS, port 853) and DoH (DNS over HTTPS, port 443 — queries hidden inside ordinary-looking HTTPS) encrypt the stub-to-resolver leg; Firefox and Chrome can speak DoH directly to Cloudflare or Google, bypassing the OS stub. Be precise about the gain: the local network and ISP can no longer read your queries, but the resolver still sees everything — you have not eliminated trust, you have chosen whom to trust. (And a browser doing DoH ignores your hosts file — a debugging gotcha already arriving in real tickets.)

11.4 The JVM gotcha — a war story

🧪 War story — the Spring service that kept calling a dead IP

2:10 a.m. A payments provider fails over; their API's DNS flips to a standby region, TTL 60, textbook playbook (§7.1). Everything in your company recovers within minutes — except one Spring Boot service, which keeps timing out for hours. 2:40 a.m. On-call SSHes in: curl https://api.payments-partner.example works perfectly from the same box. The service still fails. 3:05 a.m. Someone restarts the JVM. Instantly healthy. Nobody sleeps well — restarts are not explanations.

The explanation: Java does not honor DNS TTLs. InetAddress keeps its own cache, with historical defaults: with a SecurityManager installed, successful lookups are cached FOREVER (a 1990s applet-era defense), 30 seconds otherwise — and plenty of app servers and copy-pasted "hardening" configs ran in cache-forever mode. The service resolved the partner's name once at startup; that IP was now a corpse. curl does a fresh lookup per invocation; the JVM had decided it already knew. The restart "fixed" it by emptying the cache.

# the dials — JVM security properties, $JAVA_HOME/conf/security/java.security:
networkaddress.cache.ttl=60            # seconds to cache SUCCESSFUL lookups
                                       # (-1 = forever — the SecurityManager-era default)
networkaddress.cache.negative.ttl=10   # seconds to cache FAILURES (never set -1)

# or at startup (legacy but widely used system property):
java -Dsun.net.inetaddr.ttl=60 -jar app.jar

# AWS's standing guidance for exactly this failure: JVM TTL ≈ 60 s, because
# ALB / RDS / ElastiCache endpoints rotate IPs as a matter of routine.

The lesson, bigger than Java: your platform has a resolver too. The OS stub is only the bottom layer — JVMs, HTTP clients, and sidecars each cache under their own policies. (Its twin: a connection pool holding keep-alive connections to the old IP re-resolves nothing — DNS was fine, the pool was the cache. Part 9.) When traffic follows a corpse after failover, audit every layer that remembers.

11.5 Node.js — two resolvers in one runtime

Node ships two lookalike APIs that are not interchangeable. dns.lookup() — the default inside http.get() and fetch — calls the OS resolver (getaddrinfo), so it honors the hosts file and OS cache; but the call is blocking C code on libuv's worker threadpool (default size 4), so lookup bursts or one slow resolver queue behind file I/O — mysterious latency. dns.resolve4() and family are a pure DNS client (c-ares): true async network I/O, no threadpool — but they skip the hosts file and OS cache entirely. Rule of thumb: lookup = "resolve like the OS would"; resolve = "speak DNS itself." And Node itself caches nothing — the mirror image of the JVM's cache-forever sin.

11.6 Kafka — bootstrap is just DNS

bootstrap.servers=kafka1.example.com:9092,kafka2.example.com:9092 is a DNS exercise: the client resolves a bootstrap name, connects, and fetches cluster metadata — which returns every broker's advertised listener: more names, also resolved before connecting to partition leaders. Hence the classic failure: works inside the broker network, dies from your laptop with UnknownHostException, because brokers advertised internal-only names. The bootstrap list opens the door; the advertised names must resolve from wherever the client lives. (Being a JVM client, 11.4 applies on top.)

🟢 Beginner — say it simply

Your tools are full of hidden DNS: Route 53 hosts records and can answer by region or health; Kubernetes and Compose give services names so containers find each other; Java caches lookups by its own rules (sometimes forever — the famous "restart fixed it"); Node has one API that asks the OS and one that speaks DNS directly; Kafka clients find brokers by resolving names.

🟡 Intermediate — the mechanics

Route 53: hosted zones, health-checked weighted/latency/failover/geo policies, ALIAS for apex-to-ALB. K8s: CoreDNS + resolv.conf search lists implement service.namespace.svc.cluster.local. Compose: embedded resolver at 127.0.0.11. JVM: networkaddress.cache.ttl / sun.net.inetaddr.ttl override DNS TTLs — set ~60 s for cloud targets. Node: dns.lookup (OS, threadpool) vs dns.resolve (c-ares). Kafka: bootstrap and advertised listeners are two separate resolution steps.

🔴 Advanced — what experts know

The theme is resolver pluralism: any real deployment runs four-plus resolvers (OS stub, runtime, cluster DNS, VPC resolver) with different caches and search paths, and most "DNS is flaky" tickets are two of them disagreeing. Debug by asking each layer the same question and diffing: dig (pure DNS), getent hosts (OS view, hosts file included), the runtime API, the cluster resolver directly. In K8s, ndots:5 means external names like api.stripe.com first try several doomed in-cluster suffixes — an NXDOMAIN tax that node-local caching and trailing-dot FQDNs (§3.1!) both mitigate.

Why it is weak load balancing — four structural reasons:

  • No health awareness. Plain DNS serves a dead server's IP until the zone is edited and caches expire — TTL seconds of failed requests, minimum. Health-checked policies (§11.1) patch resolution time only; already-cached answers stay broken.
  • Cache stickiness. Rotation happens per resolver query, not per request. One office resolver caches one ordering and pins everyone behind it for the TTL — and a JVM (§11.4) pins itself far longer.
  • Uneven client distribution. One cached answer may stand for one user — or an ISP resolver serving half a city. Equal rotation of answers is nothing like equal distribution of load.
  • No request awareness. DNS sees a name and answers an IP. It cannot see connection counts, latency, CPU, or the difference between a health ping and a 4 GB upload — it cannot balance; it can only spread blindfolded.
🔑 Key point — and the handoff

DNS distributes name resolutions; a load balancer distributes requests. Resolutions are cached, client-controlled, and health-blind — so DNS-level spreading is the coarse outer layer (steering users to a region), never the fine-grained one. Part 9 picks up exactly here: a device holding the single stable IP your DNS points at, seeing every request and every backend's health in real time, balancing for real.

13. Security touches: poisoning, DNSSEC, and hygiene

Three things every backend engineer should know exist — one paragraph each, no depth required today.

Cache poisoning. A DNS answer is matched to its question by a 16-bit ID (section 8's id:), over connectionless UDP — no handshake proves who is talking (Part 4). An attacker who can guess the ID can race the real answer: fire forged responses at a resolver just after it asks, and if a fake with the right ID arrives first, the resolver caches the attacker's IP for bank.example.com — poisoning every downstream user for the TTL. Dan Kaminsky showed this practical at scale in 2008, and the fixes are entropy patches you can still see in packet captures: source-port randomization (queries leave from random ephemeral ports — Part 5 — adding ~16 bits to guess) and 0x20 encoding (the resolver randomizes letter case, bAnK.eXamPLe.cOm, and requires the answer to echo it exactly — yes, really). Together they make blind forgery a lottery with hundreds of millions of losing tickets.

DNSSEC (DNS Security Extensions) is the principled fix: zone owners sign records, parents publish children's key fingerprints, and a chain of trust runs from the root down — so any resolver can verify an answer is authentic regardless of who delivered it. Know two things: it provides authenticity and integrity, not confidentiality (signed, not encrypted — DoH is the privacy tool), and adoption remains a minority of domains after two decades: signing is operationally fussy (botched key rollovers have taken major sites offline), responses balloon past UDP limits, and validation failure means SERVFAIL for everyone. It exists; it matters for high-value zones; you are not behind for never deploying it.

Hygiene one-liners. Typosquatting: attackers register examp1e.com to harvest typos — defensive registrations are cheap insurance. Dangling-CNAME subdomain takeover: you decommission an S3 site or Heroku app but leave promo.example.com CNAME old-bucket.s3.amazonaws.com in the zone; an attacker claims the now-free bucket name and serves content (and harvests cookies — Part 7) on your subdomain. The rule: DNS records are inventory — when infrastructure dies, its records die with it. Decommissioning checklists end with a zone audit.

14. Interview questions

🎤 Try answering out loud before you click
Walk me through everything DNS does when you type https://shop.example.com into a browser.

Caches first: browser, then the OS stub — hosts file, then OS cache. On miss, the stub sends a recursive query (UDP, port 53, rd flag) to its DHCP-assigned resolver. The resolver checks its cache, then iterates: root → referral to the .com TLD servers (with glue IPs); TLD → referral to the domain's authoritative nameservers; authoritative → the A record with TTL, flagged aa. The answer is cached at resolver, OS, and browser, then handed to the app — which only now can open TCP (the SYN needs a destination IP). Cold ≈ 20–120 ms; warm under 1 ms. Bonus: mention negative caching and that answers may legitimately differ by geography/policy.

Recursive vs iterative queries — who does which, and why is the split designed that way?

The stub sends a recursive query: "get me the final answer, however long it takes." The resolver queries root, TLD, and authoritative servers iteratively — each answers only with what it knows: a referral ("not mine — ask them") or the final record. The split is load engineering: root/TLD servers stay fast by being stateless and refusing recursion; patient, cache-heavy work concentrates in resolvers near users. Visible in the protocol as the rd and ra flags in dig output.

CNAME vs A record — and why can't I put a CNAME at the zone apex?

A maps a name to an IPv4 address; CNAME maps a name to another name, which must then be resolved. CNAME rules: the aliased name may hold no other records, and the apex must hold SOA and NS — so the bare domain can't be a CNAME. Painful in the cloud, where load balancers are hostnames with unstable IPs — hence Route 53 ALIAS (and Cloudflare CNAME flattening): alias behavior resolved server-side, answered as plain A records, legal at the apex, auto-tracking the ALB. Also worth saying: CNAME chains cost extra lookups.

Why does DNS use UDP? When does it use TCP?

The exchange is one tiny question, one small answer — UDP does it in a single round trip with no connection state, while TCP's handshake alone would double the latency and force state onto servers doing millions of queries per second. Lost datagram? Re-ask — queries are idempotent. TCP is used when answers exceed the UDP budget (classically 512 bytes; the TC truncation flag means "retry over TCP"; EDNS0 raised typical budgets to ~1232), for DNSSEC-sized responses, and always for AXFR zone transfers. Port 53 on both.

What are the TTL trade-offs, and what's your pre-migration playbook?

Low TTL: fast convergence and failover, but more cache misses — more query load, cost, and lookup latency. High TTL: cheap and fast steady-state, but changes and mistakes stay visible for hours. Playbook: at least one full old-TTL before cutover, lower the TTL (86400 → 60) — early, because caches honor the TTL they fetched and you cannot shorten a promise already made; change the record; verify with dig @8.8.8.8 and dig @authoritative; drain the old target; raise the TTL back.

You fixed a wrong DNS record an hour ago but some users still hit the old IP. Is it "still propagating"?

Nothing propagates — DNS has no push channel. The authoritative servers answered correctly the moment you saved; what persists is caching: every resolver that fetched the old record serves it until its copy's TTL expires, plus OS/browser layers, plus a JVM that may cache far beyond any TTL. If the bad state was NXDOMAIN, negative caching (SOA minimum) keeps "doesn't exist" alive too. Diagnose by diffing dig @authoritative (truth) against dig @8.8.8.8 and the local cache, watching the remaining-TTL countdown.

How does Kubernetes service discovery relate to DNS?

Kubernetes uses plain DNS for discovery: CoreDNS runs in-cluster, and every Service gets service.namespace.svc.cluster.local, resolving to the Service's stable cluster IP. Pods' /etc/resolv.conf points at CoreDNS and carries a search-domain list — which is why the short name orders works in-namespace: it is a relative name completed by the search list. Named ports even get SRV records. So "calling a microservice by name" in K8s is ordinary DNS against a cluster-local authoritative server — with section 1's indirection payoff: pods churn, IPs change, the name holds.

After a failover, one Java service kept calling the dead IP for hours while curl on the same host worked. Why?

The JVM's InetAddress cache ignores DNS TTLs: historically it caches successful lookups forever with a SecurityManager (30 seconds otherwise), governed by networkaddress.cache.ttl in java.security or the legacy sun.net.inetaddr.ttl property. The service resolved once at startup and never again; curl does a fresh lookup per invocation. Fix: set the JVM TTL to ~60 s (AWS's standing recommendation — ALB/RDS IPs rotate routinely), and check the twin culprit: connection pools holding keep-alive connections to the old IP never re-resolve until those connections close.

Registrar, registry, DNS hosting provider — who does what?

Registrar: where you buy and renew the name (Namecheap, GoDaddy, Cloudflare, Route 53-as-registrar); ICANN-accredited; submits your nameserver choices upward. Registry: operates the TLD — Verisign runs .com's servers and database; NIXI runs .in. DNS host: runs the authoritative servers for your zone's records (Route 53, Cloudflare DNS, your own BIND). Fully mixable — and the corollary: switching DNS hosts means changing NS records at the registrar, because the operative delegation lives in the parent zone.

What is negative caching, and when does it bite?

Resolvers cache NXDOMAIN answers, for a duration set by the zone's SOA minimum field (repurposed by RFC 2308 as the negative-cache TTL). It bites when you query a name before creating its record — a pre-deploy health check, an eager retry loop — caching the "no," so the name stays dead on that resolver even after you add the record; and when a fixed typo "stays broken" briefly for the same reason. Mitigate with patience, targeted cache flushes, and a modest SOA minimum (e.g., 300) so mistakes age out fast.

How does round-robin DNS distribute load, and why isn't it a real load balancer?

Multiple A records on one name; resolvers return the set and rotate the order; most clients take the first — statistically spreading connections. It fails as load balancing on four axes: no health awareness (a dead IP keeps being served until the zone changes and TTLs expire), cache stickiness (one resolver's cached ordering pins all its users), uneven client weight (one cached answer may represent an entire ISP), and request-blindness (DNS can't see connections, load, or latency). It spreads resolutions, not requests — coarse geographic steering at best. Dedicated load balancers (Part 9) close exactly that gap.

Are there really only 13 root servers? What happens if they "go down"?

Thirteen root server identities (a–m.root-servers.net, 12 operators) — a relic of fitting the list plus IPs into one 512-byte UDP answer — but each is anycast from many sites: 1,700+ physical instances worldwide, with routing (Part 3) delivering you to a nearby one. "Taking down the roots" means defeating hundreds of independent sites simultaneously — and resolvers cache the TLD referral set for ~two days, so the Internet would coast on caches while operators responded.

15. Common misconceptions

❌ Myths engineers actually believe

❌ "After a DNS change, the update propagates across the Internet like a wave."
✅ Nothing is pushed anywhere — there is no propagation channel. Your authoritative servers answer with the new value instantly; everyone else holds caches that expire on their own TTL schedules and then re-fetch. "Waiting for propagation" is really "waiting for independently distributed cache expiries" — which is why the fix for stragglers is lowering TTLs before the change, not waiting harder after it.

❌ "There are 13 root server machines."
✅ Thirteen named identities (a 512-byte-UDP-era artifact), each anycast from many locations — 1,700+ physical instances operated by 12 organizations. Your "root query" is usually answered within your own region.

❌ "Every HTTP request does a DNS lookup."
✅ Lookups are heavily amortized: browser, OS, and resolver caches answer most in microseconds, and connection reuse (keep-alive, pools — Parts 7 and 9) means most requests ride an existing connection and trigger no resolution at all. A busy JVM service might resolve a downstream name once a minute — or, misconfigured, once per process lifetime (§11.4).

❌ "CNAME chains are free — it's just an alias."
✅ Each link is another name to resolve: cold-cache chains add real round trips, every link is one more record to misconfigure, and a dangling link is a takeover risk (§13). Plus the hard rules: no coexisting records, never at the apex. Alias once, deliberately — not thrice, accidentally.

❌ "DNS returns the same answer for everyone."
✅ Modern DNS answers depend on who asks, from where, and what's healthy: geolocation, latency-based routing, weighted canaries, failover health checks (§11.1) — plus anycast (Part 3) handing you a different server instance per region. Two engineers diffing dig outputs across continents may both be seeing correct, intended behavior.

❌ "The trailing dot in example.com. is a typo."
✅ The dot is the root of the tree: it marks the name fully qualified (absolute). Without it a name is technically relative and may be completed by search lists — the very mechanism Kubernetes uses to turn orders into orders.shop.svc.cluster.local. Zone files and dig print it because, at this layer, precision is load-bearing.

❌ "DNS only uses UDP."
✅ DNS is specified on both transports, port 53 each: UDP for the common case, TCP for truncated/oversized answers (TC flag, DNSSEC) and always for AXFR zone transfers — plus DoT (853) and DoH (443). A firewall that "helpfully" blocks TCP/53 causes the weirdest partial outage: everything works except the big answers.

❌ "My laptop walks the DNS tree itself."
✅ Your machine runs only a stub: hosts file, small cache, and one configured recursive resolver (courtesy of DHCP) that does the walking and the heavy caching. That split is why "change your DNS server" is a thing users can do — and why one broken resolver makes the whole Internet "go down" for an office while every cable stays lit.
