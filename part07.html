HTTP — The Language of the Web

Six parts of plumbing brought us here. DNS (Part 6) turned api.shop.example.com into an IP address; TCP (Part 4) opened a reliable byte pipe to port 443 (Part 5). But a pipe full of bytes means nothing until both sides agree what the bytes say. That agreement — the one you live inside every working day, the one behind every @GetMapping, every fetch(), every axios.post() — is HTTP. This is the chapter where the course arrives at your day job.

📍 OSI Layer 7 — Application

HTTP (HyperText Transfer Protocol) lives at Layer 7 because it defines the meaning of the messages — methods, paths, headers, bodies — riding on top of the raw, meaning-free byte stream that Layer 4's TCP delivers (Parts 2 and 4: problem #8, "what do these bytes say?").

1. Why HTTP was invented

🧭 Why a universal document/API protocol must exist

Imagine 2026 without one. Every company invents its own request format: to fetch data from Amazon you install the Amazon client speaking the Amazon protocol; for your bank, the bank's client and the bank's protocol; your React app cannot call your FastAPI service without a bespoke adapter for each pairing. Integration cost grows with every pair of vendors — the same n×(n−1)/2 explosion that full-mesh cabling had in Part 1, but at the application layer. HTTP collapses that to n: one client (any browser, any HTTP library) can talk to every server ever written, and one server can serve every client ever written. That single property — universal interoperability of request and response — is why HTTP outgrew documents and became the default carrier for APIs, webhooks, video, package managers, and most of Part 13's microservice traffic.

📜 What came before — CERN, 1989

HTTP has a precise birthplace. CERN, the European particle-physics laboratory near Geneva, late 1980s: thousands of visiting physicists, every experiment documenting itself on different computers, in different formats, on different institutional networks. Finding "the calibration notes that reference the detector spec" meant emails, phone calls, and FTP hunts across incompatible systems. In March 1989 a British software engineer there, Tim Berners-Lee, wrote a memo — "Information Management: A Proposal" — sketching documents that link directly to each other across machines. His boss scribbled the most consequential performance review in computing history on it: "vague, but exciting." By the end of 1990 Berners-Lee had built the first web server, the first browser, and the protocol between them; in 1991 it left CERN, and in April 1993 CERN put the technology in the public domain — free for anyone, forever.

Why invent something new? Each existing tool failed the "linked documents across institutions" test:

  • FTP (File Transfer Protocol, 1971) moved whole files over a stateful, login-based session: connect, authenticate, navigate directories, transfer, quit. Heavyweight for "show me that one page," and a file fetched by FTP had no way to point at another file on another server — no linking.
  • Gopher (University of Minnesota, 1991) organized documents into rigid menu trees — closer, and briefly more popular than the web. But menus are not links-in-text, and in 1993 the university announced it might charge licensing fees for server implementations. The mere scare stampeded everyone toward the explicitly free web. Gopher never recovered.
  • Email is store-and-forward: a message wanders mailbox to mailbox and arrives whenever it arrives. Fine for letters, useless for "click, see the document now" — not interactive.

Berners-Lee's genius was shipping three inventions as one system, each useless alone: the URL (Uniform Resource Locator) — a universal address for any document on any server; HTML (HyperText Markup Language) — a document format whose superpower is embedding those addresses as clickable links; and HTTP — a deliberately dead-simple protocol to fetch the document at an address. The first version, later named HTTP/0.9, was one line of ASCII (American Standard Code for Information Interchange) text: the word GET, a space, a path. The server replied with the document and closed the connection. No headers, no status codes, no versions. Everything in the rest of this chapter is patches on that one-line idea — and the one-line idea still shows through.

🌍 Analogy — HTTP is the standardized order form

Before standardized shipping paperwork, every trading company had its own order forms, in its own language, with its own filing rules — trading with ten partners meant mastering ten bureaucracies. Then everyone adopted one form layout: what you want on the first line, details in labeled fields below, goods attached behind. Suddenly any clerk on Earth could process any order from any company. HTTP is that form for software: first line says what you want (GET /v1/orders/1042), labeled fields follow (headers), goods attached behind (body). The form does not care whether the "goods" are HTML, JSON (JavaScript Object Notation), a JPEG, or a video chunk — which is exactly why the web's document protocol became the API protocol too.

2. URL anatomy — every character has a job

Before sending a request you must say where — and the URL packs five different protocols' worth of addressing into one string. Take a realistic one from your e-commerce backend and dissect it completely:

Walking left to right:

  • Scheme — which protocol the client should speak: http, https, but also ws (WebSocket), ftp, postgres, redis. The scheme implies a default port (Part 5's well-known ports): http → 80, https → 443. That is why you never type :443 — the browser fills it in.
  • Host — api.shop.example.com. The browser hands this to DNS (Part 6) and gets back an IP address such as 203.0.113.40. The hostname also travels inside the request as the Host header — a crucial detail we hit in section 8.
  • Port — :8443 overrides the scheme's default. You do this daily: localhost:8080 is "scheme default be damned, talk to port 8080."
  • Path — /v1/orders: which resource on that server. This is the part your @GetMapping("/v1/orders") or @app.get("/v1/orders") matches against.
  • Query string — everything after ?: named parameters as key=value pairs joined by &. Your framework parses them into @RequestParam String status or FastAPI function arguments. Convention: the path identifies the resource, the query filters or paginates it.
  • Fragment — #section. Here is the trap: the fragment is never sent to the server. It is a purely client-side instruction ("after loading, scroll to the element with this id" — or, in React Router's hash mode, the entire client-side route). If your backend logs show the fragment missing, that is not a bug; the browser strips it before the request leaves. Security teams exploit this deliberately: OAuth's implicit flow once put tokens in fragments precisely so they would not hit server logs.

URI vs URL, settled in one paragraph: a URI (Uniform Resource Identifier) is the umbrella term for any string that identifies a resource; a URL is the kind of URI that also tells you where to fetch it and how (scheme + host). Every URL is a URI; some URIs merely name without locating (urn:isbn:0451450523 identifies a book but gives no server to fetch it from). In backend life you may use the terms interchangeably and no one will be hurt — Java's class is even called URI while holding URLs — but in an interview, give the sentence above.

Percent-encoding in one line: characters that have jobs in URL syntax (?, &, =, /, space) must be escaped as % + their hex byte value when they appear in data — a space becomes %20, an & inside a value becomes %26 — which is why URLEncoder.encode() in Java and encodeURIComponent() in JavaScript exist, and why a customer named "Smith & Sons" breaks naive URL string concatenation.

🌍 Analogy — a URL is a complete postal address plus instructions

Part 1's postal system again: the scheme is the service class (regular vs registered mail), the host is the building, the port is the apartment door (Part 5's exact analogy), the path is "the blue folder in the third drawer," the query string is a sticky note with extra instructions ("only pages about OPEN orders, second bundle"), and the fragment is a note to yourself — "read the section on refunds" — which the postal service never sees, because it is about what you do after the package arrives.

3. The request–response model

HTTP's conversational shape is the one you met in Part 1's Fig 1.7, now with its formal rules. There are exactly three:

  1. The client always initiates. (Part 1's defining rule for the client role.)
  2. Exactly one response per request. The client asks once, the server answers once, that exchange is complete and self-contained.
  3. The server cannot speak first. It sits listening on its port (Part 5) and is mute until asked.
Fig 7.2 — The atom of the web: one request, one response
   CLIENT (browser / axios / RestTemplate)        SERVER (Spring Boot :8443)
        │                                               │
        │   request:  GET /v1/orders/1042               │  …listening,
        │ ─────────────────────────────────────────►    │   silent
        │                                               │
        │                                               │  controller runs,
        │                                               │  DB query, JSON built
        │   response: 200 OK + body                     │
        │ ◄─────────────────────────────────────────    │
        │                                               │
        │   exchange over. the server now has NO WAY    │
        │   to send this client anything further        │
        │   until the client asks again.                │

Rule 3 has a consequence that shapes entire product architectures: servers cannot push. When the order status changes in your database, your server has no HTTP verb meaning "hey browser, update yourself." Every real-time feature you have ever used is one of four workarounds, all of which obey the rules by having the client initiate something the server can later exploit:

  • Polling — the client asks "anything new?" every few seconds. Trivially simple, works through every proxy and firewall, and brutally wasteful: 99% of polls return "no." Use it for dashboards refreshing every 30–60 s where staleness is fine and simplicity is king.
  • Long-polling — the client asks, and the server holds the request open (doesn't respond) until it actually has news or a timeout passes; the client immediately re-asks. Each message still costs a full request cycle, but latency drops to near-zero and empty responses vanish. Use it when you need near-real-time but infrastructure (old proxies, strict gateways) blocks fancier options — it is the workhorse fallback inside libraries like SignalR and Socket.IO.
  • SSE (Server-Sent Events) — the client makes one request, and the server responds with a never-ending body of text/event-stream, dribbling out one event at a time over the open connection. One direction only (server → client), auto-reconnecting, plain HTTP. Use it for feeds, notifications, progress bars, LLM token streaming — anywhere the client only listens. In Spring it is SseEmitter; in FastAPI, StreamingResponse; in the browser, EventSource.
  • WebSockets — the client sends a special HTTP request asking to stop speaking HTTP: an Upgrade handshake. If the server agrees, the TCP connection (Part 4) stays open and both sides exchange free-form messages in either direction at any time — full duplex, no request–response shape at all. Use it for chat, multiplayer games, collaborative editors, trading terminals — anywhere both sides genuinely initiate. Your React dev server's hot reload (Part 1's example) is a WebSocket.

🌍 Analogy — a restaurant where the kitchen can't shout

HTTP is a restaurant where waiters (clients) may approach the kitchen (server) anytime, but the kitchen is forbidden from calling out to the dining room. Polling: the waiter walks back every two minutes — "ready yet?" Long-polling: the waiter stands at the counter and waits until a dish appears, delivers it, walks straight back. SSE: the kitchen installs a one-way conveyor belt to the waiter's station. WebSocket: waiter and chef agree to just open a phone line and talk freely — they are no longer doing "restaurant protocol" at all.

4. Raw HTTP messages — read the actual bytes

This is the soul of the chapter. Frameworks hide these bytes behind annotations and promises, but every production debugging session that involves a proxy, a CORS error, a mangled header, or a hanging request ends with someone reading raw HTTP. An HTTP/1.1 message is plain ASCII text with a rigid shape — four parts:

Fig 7.4 — The shape of every HTTP/1.1 message
  ┌──────────────────────────────────────────────────────────────┐
  │ START LINE      one line: what this message is               │
  │                 request:  METHOD SP path SP version CRLF     │
  │                 response: version SP status SP reason CRLF   │
  ├──────────────────────────────────────────────────────────────┤
  │ HEADERS         zero or more lines of  Name: value CRLF      │
  ├──────────────────────────────────────────────────────────────┤
  │ BLANK LINE      a lone CRLF — the sacred boundary            │
  ├──────────────────────────────────────────────────────────────┤
  │ BODY (optional) raw bytes: JSON, HTML, JPEG, anything        │
  └──────────────────────────────────────────────────────────────┘

Two pieces of vocabulary before the real messages. SP is a single space. CRLF (Carriage Return + Line Feed) is the two-byte line ending \r\n — bytes 13 and 10 — inherited from teletype machines, where the print head physically returned to column one (CR) and the paper fed up one line (LF). HTTP mandates CRLF, not the bare \n Unix uses, and hand-rolled HTTP that sends \n is a classic source of "works against my test server, fails against nginx." And the blank line is sacred: a lone CRLF is the only signal separating headers from body. Everything before it is metadata; everything after it is payload.

4.1 A complete GET exchange against a Spring Boot endpoint

Server side, the code you have written a hundred times:

@RestController
@RequestMapping("/v1/orders")
public class OrderController {

    @GetMapping("/{id}")
    public ResponseEntity<OrderDto> getOrder(@PathVariable long id) {
        return ResponseEntity.ok(orderService.find(id));   // 200 + JSON
    }
}

Now the bytes that actually cross the wire when a client calls it. First the request — every line annotated:

Fig 7.5 — A raw GET request, byte for byte
GET /v1/orders/1042 HTTP/1.1          ← request line: METHOD SP path SP version CRLF
Host: api.shop.example.com            ← which site on this IP (mandatory since 1.1, §8)
Accept: application/json              ← "I can digest JSON" (content negotiation, §8)
Accept-Encoding: gzip, br             ← "compress if you like" (§15)
Authorization: Bearer eyJhbGciOi...   ← who I am (§12)
User-Agent: axios/1.7.2               ← what software I am
                                      ← THE BLANK LINE (a lone CRLF): headers end here
                                      ← no body — a GET asks, it does not send

Note what is absent: no IP address (that was Layer 3's job, Part 3), no port (Layer 4, Part 5), no mention of TCP. By the time these bytes exist, all of that is solved plumbing. HTTP only says what is wanted. The response coming back:

Fig 7.6 — The raw response
HTTP/1.1 200 OK                       ← status line: version SP code SP reason-phrase
Content-Type: application/json        ← how to interpret the body bytes
Content-Length: 86                    ← body is EXACTLY 86 bytes — the framing contract (§4.3)
Date: Fri, 12 Jun 2026 09:30:00 GMT   ← server clock, always GMT
Connection: keep-alive                ← let's reuse this TCP connection (§15)
                                      ← the sacred blank line again
{"id":1042,"status":"OPEN","total":2499.00,"currency":"INR","customerId":77001}

That JSON line is the 86 bytes Content-Length promised. Spring serialized your OrderDto with Jackson, counted the bytes, and wrote the header for you. Your ResponseEntity.ok(...) is the status line; your return value is the body; @RestController is the Content-Type: application/json header. The annotations are a thin skin over this text.

Forget Content-Type and Spring answers 415 Unsupported Media Type before your controller ever runs; forget Content-Length (or its alternative, below) and the server cannot know where your JSON ends. Which brings us to the deepest idea in this section.

4.3 The framing insight: why Content-Length must exist

Recall Part 4's most important lesson: TCP is a byte stream with no message boundaries. TCP guarantees the bytes arrive complete and in order, but it deliberately knows nothing about where one application message ends and the next begins. If the client sends two requests back-to-back on one connection, the server's socket just fills with one long run of bytes. So HTTP must solve the framing problem itself, and it has exactly three tools:

  1. Content-Length: N — "the body is exactly N bytes; after byte N, the next thing you read is the start of a new message." Requires knowing the size up front.
  2. Transfer-Encoding: chunked — for bodies whose size is unknown while sending (streaming a large query result, generating a report on the fly). The body becomes a series of chunks, each prefixed by its size in hexadecimal, terminated by a zero-length chunk:

                                      ← final CRLF closes the message
  1. Connection close — the HTTP/1.0 fossil: "the body ends when I hang up." It works, but it destroys connection reuse (§15) and cannot distinguish "message complete" from "server crashed mid-body."
🔑 Key point

When an interviewer asks "how does the server know where the request body ends?" they are testing whether you know HTTP rides a boundary-less byte stream (Part 4). The answer: the headers end at the first blank line (lone CRLF); the body's end is declared by Content-Length, or by chunked transfer encoding's zero-chunk, or — legacy — by closing the connection. Get this wrong in code and you get the two classic pathologies: a hanging request (server waits forever for promised bytes that never come) or request smuggling (a front proxy and a back server disagree about where one message ends and the attacker hides a second request in the gap — the marquee modern HTTP vulnerability).

🟢 Beginner — say it simply

An HTTP message is a text letter with a strict layout: one line saying what you want (or what the answer is), then labeled header lines, then an empty line, then the attachment (body). The empty line is the separator, and a header like Content-Length: 86 tells the receiver exactly how many bytes of attachment to read.

🟡 Intermediate — the mechanics

Request = request-line (METHOD SP path SP version CRLF) + headers + CRLF + optional body; response = status line + headers + CRLF + body. Because TCP provides no message boundaries, HTTP self-frames: headers end at the first empty line, bodies end per Content-Length, chunked encoding (hex-sized chunks, zero-chunk terminator), or connection close. Frameworks (Spring's ResponseEntity, FastAPI's response model) are code-level veneers over exactly these lines.

🔴 Advanced — what experts know

Framing ambiguity is an attack surface: if a proxy honors Content-Length while the origin honors Transfer-Encoding (or they parse duplicated/obfuscated headers differently), an attacker can smuggle a hidden second request inside the first (CL.TE/TE.CL request smuggling) — poisoning caches and hijacking other users' requests. This is why HTTP/2 (§14) abandoned text framing for binary length-prefixed frames, why proxies normalize messages, and why you should never write a "quick" HTTP parser with string splits in production.

5. Statelessness — the design decision that built the modern web

Here is the protocol's deepest design decision, stated bluntly: HTTP remembers nothing. Each request–response pair stands completely alone. The server is not told "this is request #5 from that same person" — by default it cannot know. Once the response is sent, the protocol's memory of the exchange is gone.

🌍 Analogy — the clerk with perfect amnesia

HTTP's server is a counter clerk who forgets you the instant you step away — even if you step right back. Every visit, you must re-introduce yourself and re-state all context: "I am customer 77001, here is my ID, I want to see order 1042." Infuriating? Look at the upside: any clerk at any of fifty counters can serve you, because no clerk holds anything in their head that another lacks. If your previous clerk goes to lunch — or drops dead — you walk to the next counter and lose nothing. Now rename the clerks "servers" and the counters "instances behind a load balancer," and you have understood horizontal scaling.

🧭 Why design it forgetful — two reasons, 35 years apart

The 1991 reason: simplicity. Berners-Lee needed a server an undergraduate could implement in a weekend: accept connection, read one request, send one document, forget everything. No session tables, no cleanup of abandoned conversations, no "what if the client vanishes mid-dialogue" — the protocol cannot leak per-client state because it holds none.

The 2026 reason: horizontal scaling. If no request depends on server-side memory of a previous one, then any server can answer any request. Put twenty identical Spring Boot instances behind a load balancer and spray requests across them randomly — it just works. Instance dies? Requests flow to the others; no user notices, because nothing they needed lived in it. Traffic doubles? Start ten more instances — no migration, no warm-up of per-user state. This single protocol property is why "stateless service" is the first commandment of cloud architecture, and it is the load balancer's best friend — Part 9 is built on this paragraph.

Statelessness has a price, and you pay it on every request: no conversation. The server cannot remember that you logged in two seconds ago — so authentication must somehow accompany every single request. It cannot remember your cart, your language, your dark-mode preference. The web patched this hole three ways, and they are the next three sections after the protocol fundamentals:

  • Cookies (§10) — the server hands the client a note; the client's browser automatically attaches it to every later request. State lives on the client, replayed each time.
  • Sessions (§11) — the cookie carries only a random ID; the real state lives on the server (or in a shared store), looked up per request.
  • Tokens (§12) — the client carries a signed, self-describing credential (a JWT) and presents it per request; the server verifies the signature instead of remembering anything.
🔑 Key point

Stateless protocol, stateful applications. Your application obviously has state — carts, logins, preferences. Statelessness just means HTTP refuses to carry it for you, so the state has to live somewhere you choose deliberately: on the client (cookies, tokens), in one server's memory (sessions — beware, this quietly breaks horizontal scaling, §11), or in a shared store everyone can reach (Redis, the database). Every architecture debate about sessions vs JWTs is really the question "where should the state live?"

🟢 Beginner — say it simply

HTTP servers forget each request the moment it is answered. That sounds bad, but it means any copy of your server can handle any request — which is how websites scale to millions of users. Features that need memory (staying logged in, carts) are added back with cookies, sessions, or tokens.

🟡 Intermediate — the mechanics

No protocol-level state spans requests: each must carry everything needed to process it (auth credentials, context). Benefits: trivially replaceable servers, random load distribution, crash-tolerance. Costs: per-request re-authentication and re-sent context (cookie/token bytes on every call). The state relocates: client-side (cookie payloads, JWTs), server memory (HttpSession), or shared stores (Spring Session + Redis).

🔴 Advanced — what experts know

"Stateless" is a spectrum in production: TCP connections, TLS sessions, and connection pools are all state that load balancers must manage even for "stateless" apps (Part 9's sticky-session and connection-draining sections). True statelessness is also what makes serverless (Lambda) viable, what lets Kubernetes kill and reschedule pods freely (Part 12), and what makes retries safe to attempt — though only idempotency (§6) makes them safe to complete. Experts design state placement first and APIs second.

6. Methods — verbs with contracts

The first word of every request is its method: what kind of action this is. The genius of standard methods is not the names — it is the contracts attached to them, which every cache, proxy, load balancer, and retry library on Earth relies on. Master table first, contracts after:

  • Safe = the request does not change server state at all. A safe request may be repeated, prefetched, cached, or crawled by a bot with zero consequences. GET, HEAD, OPTIONS are safe. (A GET endpoint that deletes rows is not "pragmatic," it is a landmine: one day a prefetcher or link-preview bot will fire it.)
  • Idempotent = doing it N times leaves the server in the same state as doing it once. The response may differ (second DELETE returns 404), but the state does not. All safe methods are idempotent; PUT and DELETE are idempotent without being safe.

Why the retry lens: networks fail ambiguously (Part 4 — a timeout cannot tell you whether the request died on the way in or the response died on the way out). When a client, proxy, or load balancer hits that ambiguity, may it just send the request again? For idempotent methods, yes — retrying is harmless by contract. For POST, no.

  • PUT is idempotent because it is a full replacement. PUT /v1/orders/1042/address with body {"city":"Pune"} sets the address to Pune. Send it five times: the address is Pune. Same final state — replay-proof, like setting a thermostat to 21° repeatedly.
  • PATCH may not be, because it is a delta. {"op":"replace","path":"/city","value":"Pune"} happens to be idempotent; {"op":"increment","path":"/loyaltyPoints","by":50} is not — five replays, +250 points. The method makes no promise; your payload decides. Retry logic must therefore treat PATCH as unsafe to replay unless you know otherwise.
  • POST double-submit is the canonical disaster: "place order" times out on the response leg, the user (or the retry interceptor) fires again → two orders, two charges. Every "I was billed twice" story you have read is this paragraph.

The industrial fix is the idempotency key (Stripe made it famous): the client generates a unique key per logical operation — Idempotency-Key: ord-77001-a8f3c2 — and sends it as a header on the POST. The server stores each processed key with its result; a replay with a seen key returns the stored response instead of re-executing. POST becomes effectively idempotent at the application layer. Plant this concept deep: it returns in Part 9 (when load balancers and gateways retry on your behalf, sometimes without asking) and in Part 13 (message brokers deliver at-least-once, so consumers face exactly the same replay problem with a different costume).

In your frameworks, methods are routing annotations — one mapping per verb:

// Spring Boot — the method IS the annotation
@GetMapping("/v1/orders/{id}")            // GET    → read

@PostMapping("/v1/orders")                // POST   → create (201 + Location, §7)

REST in two sentences: REST (Representational State Transfer) — as practiced — is the style of modeling your API as nouns (resources at URLs: /v1/orders/1042) acted on by HTTP's standard verbs, instead of inventing verb-paths like /getOrder?id=1042 or RPC (Remote Procedure Call) method names. Note carefully: REST does not require JSON — it predates JSON's dominance, and a REST API can serve XML (Extensible Markup Language), CSV, or images; JSON is merely today's favorite representation.

🟢 Beginner — say it simply

The method is the verb: GET reads, POST creates, PUT replaces, PATCH edits a part, DELETE removes. GET must never change anything. PUT and DELETE are safe to accidentally repeat; POST is not — repeating "place order" places two orders.

🟡 Intermediate — the mechanics

Safe = no state change (GET/HEAD/OPTIONS); idempotent = N executions ≡ 1 execution (safe methods + PUT + DELETE). These contracts are machine-honored: caches cache safe methods, retry layers auto-retry idempotent ones. PUT's idempotency comes from absolute replacement; PATCH's deltas and POST's creations make replays dangerous, hence idempotency keys for POST. Frameworks bind verbs via @GetMapping… @DeleteMapping / @app.get…@app.delete.

🔴 Advanced — what experts know

The contracts are who-may-retry rules for the whole infrastructure chain: browsers replay idempotent requests on dropped keep-alive connections, nginx's proxy_next_upstream and most service-mesh retry policies default to idempotent-only, and AWS SDKs retry GETs freely. An idempotency-key store needs the same properties as a dedup store in Part 13: atomic insert-if-absent (Redis SET NX or a unique index), a TTL window, and storage of the original response, not just the key — otherwise replays during processing race you into the very duplicate you were preventing.

8. Headers — the metadata that runs the web

Headers are the labeled fields on the order form: Name: value lines, case-insensitive names, one per line. They carry everything that is about the message rather than in it. A grouped tour of the ones that matter, starting with the universal crew that appears on nearly every message in both directions:

TCP delivered bytes to an IP and port; only this header tells the server which site the client meant. 🌍 Analogy — headers are the envelope and the customs forms

The body is the gift inside the parcel; headers are everything stuck to the outside: the address label (Host), the "FRAGILE — THIS WAY UP" handling instructions (Cache-Control), the customs declaration of contents and weight (Content-Type, Content-Length), the sender's ID check (Authorization), and the chain of postmark stamps each sorting facility adds (X-Forwarded-For). Sorting facilities route entire parcels without ever opening them — exactly like load balancers routing on headers without parsing bodies (Part 9).

9. CORS — the error every junior meets first

You build a Spring Boot API on localhost:8080. You build a React app on localhost:5173. The React app calls fetch("http://localhost:8080/v1/orders") — and the browser console explodes with red text about a missing Access-Control-Allow-Origin header. Meanwhile the same URL works perfectly in curl and Postman. Welcome to the most misunderstood mechanism in web development. Let's understand it properly, because the fix-by-Stack-Overflow approach produces security holes.

Start with the rule that CORS relaxes. The same-origin policy is a browser rule: JavaScript running on one origin may not read responses from a different origin. An origin is exactly the triple scheme + host + port — all three must match:

Page at https://app.shop.example.comCalls…Same origin?
scheme+host+port identicalhttps://app.shop.example.com/profile✅ yes
different subdomain (host)https://api.shop.example.com/v1/orders❌ no — cross-origin
different schemehttp://app.shop.example.com/…❌ no
different porthttps://app.shop.example.com:8443/…❌ no
🧭 Why the BROWSER enforces this — and whom it protects

Remember §10's coming fact: browsers attach cookies automatically to every request to a site — including requests triggered by some other site's JavaScript. You are logged into bank.example.com in tab one. In tab two you visit evil.example.net, whose JavaScript runs fetch("https://bank.example.com/api/balance"). Your browser would attach your real banking cookies — it always does — and without the same-origin policy, evil.example.net's script could read your balance and ship it home. The policy exists to protect users and their ambient credentials (the cookies and logged-in state the browser carries everywhere) from malicious websites.

Now the asymmetry that confuses everyone: curl has no cookies of yours, no logged-in state, no victim to exploit — so it enforces nothing. CORS is not a server-side firewall and provides zero protection against attackers calling your API directly:

# same endpoint, no browser, no CORS, works instantly:
curl https://api.shop.example.com/v1/orders        # 200 OK
# CORS never protected the server. It protects BROWSER USERS.

CORS (Cross-Origin Resource Sharing) is the controlled relaxation: a way for your API to tell browsers "these specific foreign origins are allowed to read my responses." The browser sends an Origin header identifying the calling page; the server answers with Access-Control-Allow-Origin; the browser compares and either releases the response to JavaScript or blocks it. Two paths exist:

  • Simple requests — GET, HEAD, or POST with only form-style content types and basic headers. These existed before CORS (an HTML form could always submit cross-origin), so the browser sends them immediately and merely checks the response's allow-header before handing it to your code.
  • Preflighted requests — everything modern: JSON bodies, Authorization headers, PUT/PATCH/DELETE. The browser first asks permission with an OPTIONS request (the preflight) and only sends your real request if the answers check out:

(That is why "but it works in Postman!" — of course it does.) Access-Control-Max-Age lets the browser cache the permission so it doesn't preflight every call. The fix belongs on the server, declared once:

// Spring Boot — global CORS via WebMvcConfigurer
@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/v1/**")
                .allowedOrigins("http://localhost:5173",
                                "https://app.shop.example.com")
                .allowedMethods("GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS")
                .allowedHeaders("Authorization", "Content-Type")
                .allowCredentials(true)
                .maxAge(3600);
    }
}
// (with Spring Security in play, also wire http.cors(...) so the
//  preflight OPTIONS isn't rejected by the filter chain first)
# FastAPI — the equivalent middleware
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:5173",
                   "https://app.shop.example.com"],
    allow_methods=["GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"],
    allow_headers=["Authorization", "Content-Type"],
    allow_credentials=True,
    max_age=3600,
)

Two rules that prevent the classic copy-paste hole. First: Allow-Origin: * plus credentials is forbidden — browsers hard-reject the combination, because "any site on the Internet may make cookie-carrying requests to me and read the answers" would re-create exactly the attack the same-origin policy exists to stop. If your API uses cookies or allowCredentials(true), you must list explicit origins (and add Vary: Origin, which the frameworks above do for you). Second: in development you can sidestep CORS entirely with a dev proxy — Vite's server.proxy forwards /v1/* from localhost:5173 to localhost:8080 server-side, so the browser only ever sees same-origin requests and no CORS happens at all. That is also a preview of how production often works: one domain, with a reverse proxy (Part 10) routing /api to the backend.

🌍 Analogy — the overprotective butler

Your browser is a butler who carries all your keyrings and ID cards (cookies) and automatically shows the right ID at every door he visits on your behalf. Any stranger (a website) can hand the butler a letter to deliver anywhere. The danger is obvious: a con artist could say "deliver this withdrawal slip to her bank — and read me the reply." So the butler has a standing rule: before delivering a stranger's unusual letter to someone else's house, he first rings the doorbell and asks the owner, "do you accept letters written by this stranger?" (the preflight). Only if the owner says "yes, that origin is fine" does he deliver — and read back the reply. A courier you hire yourself (curl) carries none of your IDs, so no such ritual: nothing of yours is at risk.

Last CORS subtlety, because it bites at scale: CORS is only the read gate — it never stopped a request from arriving, so CSRF defenses (§10), authentication, and rate limiting must all assume cross-origin requests reach the server freely. And preflights are real traffic: a chatty SPA (Single Page Application) can double its request count unless Max-Age is generous or the app collapses to same-origin behind a gateway.

10. Cookies — the web's memory implant

The first patch for statelessness (§5) arrived in 1994, invented at Netscape so shopping carts could survive between page loads. The mechanism is two headers. The server says "remember this"; the browser then replays it automatically on every subsequent request to that site — no JavaScript, no effort, forever until expiry:

Decoding the attack behind each attribute, because that is how to remember them. Domain/Path scope the blast radius — a cookie scoped to Domain=example.com would flow to every subdomain, including ones run by other teams or a compromised marketing site. Expires/Max-Age draw the line between a session cookie (browser-lifetime, for logins on shared machines) and a persistent one ("remember me for 30 days"). Secure stops plaintext leakage on the wire — Part 8 shows just how readable un-encrypted HTTP is. HttpOnly blunts XSS (Cross-Site Scripting — an attacker getting their JavaScript to run on your page, e.g. via an unsanitized comment field): the injected script can still act maliciously, but it cannot read and steal the session cookie itself.

SameSite deserves its attack spelled out — CSRF (Cross-Site Request Forgery) in four lines:

  1. You are logged into shop.example.com; your browser holds its session cookie.
  2. You visit evil.example.net, which contains a hidden auto-submitting form targeting https://shop.example.com/v1/account/email with the attacker's new value.
  3. Your browser submits it and — automation doing its job — attaches your real session cookie.
  4. The server sees a perfectly authenticated request and changes your account email. You clicked nothing.

SameSite=Lax (the modern default) withholds the cookie on exactly such cross-site subrequests (allowing it only on top-level navigations like clicking a link); Strict withholds it even then; None restores the old promiscuous behavior and is therefore required to also declare Secure — you opt into it only for legitimate cross-site embedding, paired with CSRF tokens (Spring Security's CsrfFilter issues and checks those).

🔑 Key point

The browser attaches cookies automatically, per site, on every request — and that single automation is simultaneously the convenience and the vulnerability. It is why login works without you writing any client code (convenience), why CSRF exists (the attacker borrows the automation), and why CORS must be strict about credentials (§9). Tokens in an Authorization header (§12) flip the trade: nothing is automatic, so CSRF largely evaporates — but now your JavaScript must store and attach the credential itself, exposing it to XSS instead. There is no free lunch, only a choice of which attack class you'd rather defend.

🌍 Analogy — the festival wristband

At the gate (login) the venue snaps a wristband on you (Set-Cookie). You don't decide to show it — it is on your wrist, visible at every counter automatically (Cookie header). Color codes scope it (Domain/Path: main stage only), it dissolves at midnight (Max-Age), it is waterproof sealed (Secure), it cannot be slipped off and handed to a friend (HttpOnly), and the venue won't honor it if a different festival's staff walks you to the counter (SameSite). CSRF is someone steering your hand — wristband attached — to sign a tab you never read.

11. Sessions — state on the server, claim ticket on the client

A cookie could carry the state itself (Cookie: cart=3xKB-9,1xMSE-2;theme=dark) — but clients can edit their own cookies (never trust role=admin from a client!), cookies ride along on every request (bytes add up), and 4 KB is the ceiling. The classic solution inverts it: store the state server-side, hand the client only a random, meaningless claim ticket:

The catch hides in the question: where exactly does the session store live? The default — in the JVM's heap memory — works beautifully on exactly one server. Run two instances behind a load balancer (Part 9) and a request that lands on instance B carries a JSESSIONID that exists only in instance A's memory: the user is mysteriously logged out, but only sometimes. The bandaid is sticky sessions (the LB pins each user to one instance — Part 9 explains why this undermines the load balancing you bought the LB for); the real fix moves the store out of process into a shared store every instance can reach — almost always Redis, your Part 5 acquaintance on port 6379:

Now any instance can serve any request (statelessness restored at the instance level — the state lives in a shared store, exactly as §5's keypoint demanded). One hygiene rule to know by name: session fixation — always issue a new session ID at the moment of login (Spring Security does this by default), so an attacker cannot pre-plant a known ID in your browser and inherit your session once you authenticate.

12. Token auth and JWT — state that carries itself

The third patch removes the server-side store entirely: let the client carry a credential that describes and proves itself. The dominant format is the JWT (JSON Web Token) — three base64url-encoded segments joined by dots, header.payload.signature:

                     "sub": "77001",                           ← subject: which user
                     "roles": ["CUSTOMER"],

🔑 Key point — signed, NOT encrypted

Base64 is an encoding, not encryption — anyone who obtains a JWT can read every claim in it (paste one into any decoder: there's your user ID, roles, email). The signature does not hide anything; it only proves integrity and origin — that the payload was minted by the holder of the key and not altered since. Change "roles":["CUSTOMER"] to ["ADMIN"] and the signature check fails; read the roles all you like. Therefore: never put secrets (passwords, card numbers, PII you wouldn't show the user) in a JWT, and never accept a JWT without verifying its signature and expiry. (Encrypted tokens exist — JWE, JSON Web Encryption — but the JWTs in your stack are almost certainly just signed JWS.)

The client presents the token on every request in the header you've been seeing all chapter:

GET /v1/orders HTTP/1.1
Host: api.shop.example.com
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJpc3MiOi…

The payoff is stateless verification: the server checks the signature with a key it already holds and reads the claims — no session-store lookup, no Redis round trip, no shared anything. Any of your fifty instances, or a completely different microservice, can verify the same token independently. That is maximally Part 9-friendly (nothing to share, nothing to stick) and why JWTs rule microservice and mobile architectures.

The price is the revocation problem: a session dies when you delete the server entry, but a JWT is valid wherever its signature checks until exp — there is no entry to delete. Steal one, and "log out" doesn't help. The standard mitigation: make access tokens short-lived (5–15 minutes) and pair them with a long-lived refresh token stored carefully (HttpOnly cookie or secure storage) that the client exchanges for fresh access tokens; revocation then means refusing the refresh (which is checked against a store — a little state, reintroduced where it is cheap). Stolen access tokens die in minutes on their own. The trade-offs side by side:

One older scheme to recognize on sight — Basic auth, which is just the username and password, base64-encoded, on every request:

🟢 Beginner — say it simply

A session = the server keeps a notebook and gives you a numbered claim ticket (cookie). A JWT = the server writes your details on a card and signs it; later it just checks the signature instead of a notebook. Anyone can read the card — the signature only stops forgery — so no secrets go on it, and it stays valid until it expires even if stolen, which is why JWTs are kept short-lived.

🟡 Intermediate — the mechanics

JWT = base64url(header).base64url(payload).signature; verify signature + exp + iss on every request — no store lookup, hence horizontal-scale-friendly. Sessions centralize state (instant revocation, tiny cookie) at the cost of a shared store; JWTs decentralize (no store, cross-service) at the cost of revocation and per-request bytes. Production pattern: short-lived access JWT + refresh token; Basic auth = base64(user:password), TLS-only.

🔴 Advanced — what experts know

JWT pitfalls are a genre: alg:none acceptance, HS256/RS256 confusion (verifying an RSA token as HMAC with the public key as secret), missing aud/iss checks letting tokens minted for one service replay against another, and clock skew on exp (allow ~60 s leeway). At scale, prefer asymmetric signatures (RS256/EdDSA): the auth service holds the private key, every other service verifies with published public keys via JWKS (JSON Web Key Set) — no shared secret sprawl, and key rotation via the kid header. Treat the sessions-vs-JWT choice per-boundary: cookies+sessions for the browser edge, JWTs between services, is a common and defensible hybrid.

13. AuthN vs AuthZ — who you are vs what you may do

Two words that look alike and are constantly confused, including by HTTP itself:

  • Authentication (AuthN) — establishing who you are: password, token, certificate, fingerprint. Fails → 401 Unauthorized (yes, the status name says "authorized" while meaning "unauthenticated" — a 30-year-old naming bug you now simply know). A 401 should carry a WWW-Authenticate header announcing the expected scheme, e.g. WWW-Authenticate: Bearer realm="api.shop.example.com" — that header is what makes browsers pop the native Basic-auth dialog when the scheme is Basic.
  • Authorization (AuthZ) — given who you are, deciding what you may do: roles, permissions, ownership ("you can read your orders, not order 1042 which is someone else's"). Fails → 403 Forbidden: identity was fine; permission was not.

The two checks live in different places in your frameworks, and seeing where makes the concepts stick. Spring Security is a chain of servlet filters that runs before your controller: authentication filters first (parse the cookie/JWT, establish the SecurityContext), authorization checks second (match rules against the established identity):

// Spring Security — AuthN and AuthZ in one config sketch
@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    return http
        .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
        .oauth2ResourceServer(o -> o.jwt(withDefaults()))     // AuthN: validate the
                                                              // Bearer JWT, build identity
        .authorizeHttpRequests(auth -> auth                   // AuthZ: per-route rules
            .requestMatchers("/v1/admin/**").hasRole("ADMIN") // wrong role → 403
            .requestMatchers("/v1/**").authenticated()        // no/bad token → 401
            .anyRequest().denyAll())
        .build();
}
# FastAPI — the same split via dependencies
async def current_user(token: str = Depends(oauth2_scheme)) -> User:
    user = decode_and_verify(token)            # AuthN
    if user is None:
        raise HTTPException(401, headers={"WWW-Authenticate": "Bearer"})
    return user

def require_role(role: str):
    async def check(user: User = Depends(current_user)):
        if role not in user.roles:             # AuthZ
            raise HTTPException(403, "insufficient permissions")
        return user
    return check

@app.get("/v1/admin/reports")
async def reports(user: User = Depends(require_role("ADMIN"))): ...

One honest paragraph on the elephant: OAuth2 (Open Authorization 2) is a framework for delegated authorization — letting one application act on your behalf at another, without you handing over your password. Four actors: the resource owner (you), the client (the app wanting access), the authorization server (which authenticates you and mints tokens), and the resource server (the API that accepts them). OIDC (OpenID Connect) is a thin identity layer on top of OAuth2 that standardizes "who is this user" — together they are the machinery behind every "Log in with Google" button, and the reason your Spring config above said oauth2ResourceServer. The flows (authorization code + PKCE, client credentials…), token endpoints, scopes, and consent screens are genuinely a course of their own — here, it is enough to know the actors and that the Bearer tokens of §12 are usually minted by this machinery.

Every HTTP version exists to fix the previous one's performance ceiling, and the whole story is one theme: stop making things wait in line.

1.0's sin was reconnecting per request. Part 4 taught you what a TCP connection costs — a full round trip of SYN / SYN-ACK / ACK before byte one of payload (plus, today, TLS's round trips, Part 8). A 1996 page with 20 images paid that handshake tax 21 times, serially. 1.1's persistent connections (reuse the pipe for request after request) fixed the tax and, with the now-mandatory Host header, enabled the virtual hosting of §8. One asterisk survived, and Part 4 predicted it: TCP-level head-of-line blocking remains. TCP delivers a single ordered byte stream and holds back everything behind a lost packet until retransmission (Part 4's in-order guarantee). Lose one packet carrying frames of stream A, and streams B and C — complete, sitting in buffers — are stalled too, because TCP refuses to release bytes out of order. The streams are independent in HTTP/2's mind but not in TCP's. On clean networks, irrelevant; on lossy mobile links, HTTP/2 can lose to six 1.1 connections (where a loss stalls only one of them).

HTTP/3 fixes that by firing TCP altogether. It runs on QUIC (Quick UDP Internet Connections), which rebuilds reliability per stream, in userspace, on top of UDP — closing the loop on Part 4's "when would anyone choose UDP?": when you want to redesign reliability itself, UDP is the blank canvas. Each QUIC stream retransmits and orders independently, so a lost packet stalls only its own stream. TLS 1.3 is built into the handshake (encryption is not optional — one fewer round trip, 0–1 RTT to first byte for known servers, Part 8 details), and connections are identified by connection IDs instead of the Part 5 four-tuple — so your phone walking from Wi-Fi to 5G (new IP!) migrates the connection without dropping your video call. The cost: ~every middlebox assumption about "web = TCP 80/443" had to change, kernel-bypass CPU overhead, and UDP-hostile networks — hence the gradual rollout, always with TCP fallback.

🧪 Real example — what YOUR app actually speaks

Check your production setup and you will almost certainly find: browsers speak HTTP/2 or 3 to an edge proxy; your Spring/Node/FastAPI app speaks plain HTTP/1.1 behind it. The ALB (Application Load Balancer), Nginx, or CloudFront terminates the fancy protocol (and TLS) and forwards boring 1.1 to your container — you get multiplexing's benefits at the edge where they matter (high-latency public Internet) without your app changing at all (low-latency LAN behind, Part 1's table). This split is Parts 9–10's whole topic. You can enable HTTP/2 in Spring Boot with one line — server.http2.enabled=true — but honestly caveated: browsers only speak h2 over TLS (the cleartext variant, h2c, is for proxies and tooling), so this only matters when your app terminates TLS itself… which is exactly the full story of the next part.

🟢 Beginner — say it simply

1.0 redialed the phone for every sentence. 1.1 kept the call open but you could only say one thing at a time — slow answers blocked quick ones, so browsers opened six lines. HTTP/2 lets many conversations share one line by interleaving labeled pieces. HTTP/3 rebuilds the line itself (QUIC over UDP) so one garbled piece doesn't pause everyone, and your phone can switch networks mid-call without redialing.

🟡 Intermediate — the mechanics

1.1: persistent connections, ordered one-at-a-time responses → HOL blocking → 6 connections/origin + bundling hacks. h2: binary frames, stream IDs, multiplexing, HPACK; TCP's in-order delivery still stalls all streams on one loss. h3/QUIC: per-stream reliability over UDP, integrated TLS 1.3, 0–1 RTT, connection IDs enable migration across networks. Typical deployment: edge proxy speaks 2/3 outside, 1.1 inside.

🔴 Advanced — what experts know

Protocol choice is negotiated, not configured: ALPN (Application-Layer Protocol Negotiation) inside the TLS handshake picks h2 vs http/1.1, and h3 is discovered via the Alt-Svc header or DNS HTTPS records (Part 6). h2 changes capacity math — one connection per client instead of six alters LB connection counts, and gRPC (Part 13) rides h2 streams directly, which is why "gRPC through an L7 proxy that downgrades to 1.1" breaks. QUIC's userspace delivery costs CPU (no kernel offload maturity yet) — at CDN scale that is a real bill, and why some origins still prefer h2 internally.

15. Connection reuse in practice — the pool you forgot to configure

Section 14's lesson in one operational sentence: opening connections is expensive (TCP + TLS round trips, Part 4 + Part 8), so production HTTP is pooled HTTP. First, a disambiguation Part 4 promised: HTTP's Connection: keep-alive ("don't hang up between requests — reuse this connection") is unrelated to TCP keepalive (tiny probe packets verifying an idle peer is still alive). Same word, different layers, different jobs.

Where the pool hides in your stack:

  • RestTemplate — out of the box uses the JDK's primitive connection handling; under concurrency you pay handshakes constantly and have no pool limits, timeouts, or eviction. The standard fix is plugging in Apache HttpClient's pooling: 
    PoolingHttpClientConnectionManager pool = new PoolingHttpClientConnectionManager();
pool.setMaxTotal(200);            // across all hosts
pool.setDefaultMaxPerRoute(50);   // per host — the one that actually bites

RestTemplate rest = new RestTemplate(
    new HttpComponentsClientHttpRequestFactory(
        HttpClients.custom().setConnectionManager(pool).build()));
    Symptoms of skipping this: latency that mysteriously includes a handshake per call, and under load, ephemeral-port or TIME_WAIT exhaustion — Part 5's pathology, self-inflicted.
  • WebClient (Spring WebFlux) — pools by default via Reactor Netty (500 max connections, pending acquisition queue). You tune it with ConnectionProvider; the trap is the opposite one — a full pool manifests as PendingAcquireMaxCount errors, i.e. requests queueing for a connection.
  • Node.js — modern Node's fetch rides undici, which pools per origin automatically. Classic http.request/older axios used a global agent that historically defaulted to keepAlive: false (fixed only in Node 19+) — the one-line upgrade for older services: new http.Agent({ keepAlive: true, maxSockets: 50 }) passed to axios. Countless "why is every axios call 100 ms slower than curl" mysteries are this default.
  • Browsers — manage it for you: up to 6 keep-alive connections per origin for HTTP/1.1 (Fig 7.15's workaround), or one multiplexed connection for h2/h3.

And the other free performance lever — compression negotiation, one request–response pair you can now read fluently:

──► GET /v1/catalog/laptops HTTP/1.1
──► Host: api.shop.example.com
──► Accept-Encoding: gzip, br            ← "I decompress gzip and Brotli"
──►
◄── HTTP/1.1 200 OK
◄── Content-Type: application/json
◄── Content-Encoding: br                 ← "body is Brotli-compressed"
◄── Content-Length: 21744                ← the COMPRESSED size (~170 KB of JSON)
◄── Vary: Accept-Encoding                ← caches: key on the encoding! (§8)
◄──

JSON compresses 5–10×; enabling it (server.compression.enabled=true in Spring, or — better — at the Part 10 reverse proxy) is among the cheapest latency wins available, because fewer bytes means fewer Part 4 round-trip-gated congestion windows. CPU cost is real but small; the usual policy is "compress text above ~1 KB, never re-compress images."

16. Interview questions

🎤 Try answering out loud before you click
PUT vs PATCH vs POST — when do you use each, and why does it matter for retries?

POST creates a subordinate resource or triggers processing — not idempotent: replaying "place order" places two orders. PUT fully replaces the resource at the target URL — idempotent by definition, since setting the same final state twice equals once. PATCH applies a partial delta — idempotency depends on the payload ("set city = Pune" yes; "increment points by 50" no), so infrastructure must assume it is not. The retry consequence: clients, proxies, and load balancers may safely auto-retry idempotent requests after ambiguous failures, but POST needs an application-level guard — an Idempotency-Key header the server deduplicates on, returning the stored response for replays (the Stripe pattern).

401 vs 403 — precisely.

401 Unauthorized actually means unauthenticated: credentials are missing, invalid, or expired — the server does not know who you are; respond with WWW-Authenticate advertising the expected scheme, and the client's correct reaction is to (re)authenticate. 403 Forbidden means authentication succeeded — identity is established — but that identity lacks permission; retrying with the same credentials is pointless. Mapping: AuthN failure → 401, AuthZ failure → 403. Bonus nuance: some APIs deliberately return 404 instead of 403 to avoid confirming a resource exists.

What does "HTTP is stateless" mean, and why does it enable horizontal scaling?

The protocol retains nothing between request–response pairs: each request must carry everything needed to process it, and the server holds no protocol-level memory of previous requests. Consequence: any identical server instance can process any request, so you can put N instances behind a load balancer, distribute traffic arbitrarily, kill or add instances freely — no per-user state pins a client to a machine. Applications re-add state explicitly — cookies (client-side), sessions (server/shared store), tokens (self-contained, signed) — and a strong answer notes that in-memory sessions quietly break the scaling property, fixed by a shared store (Redis) or avoided with JWTs.

Explain CORS end-to-end. What problem does it solve and who enforces it?

Browsers enforce the same-origin policy: scripts on origin A (scheme+host+port) cannot read responses from origin B, because browsers auto-attach cookies/credentials and a malicious page could otherwise act as the logged-in user. CORS is the server-side opt-out: for non-simple cross-origin requests (JSON bodies, Authorization headers, PUT/DELETE) the browser preflights an OPTIONS request carrying Origin and Access-Control-Request-Method/-Headers; the server replies with Access-Control-Allow-Origin/-Methods/-Headers (and -Credentials); if satisfied, the browser sends the real request and releases the response to JavaScript. Enforcement lives entirely in the browser — curl and server-to-server calls ignore it — so CORS protects users' ambient credentials, not your API; and Allow-Origin: * cannot be combined with credentials.

Which Set-Cookie attributes would you set on a session cookie, and what attack does each stop?

Secure — never sent over plaintext HTTP, stopping on-path snooping of the session ID. HttpOnly — invisible to JavaScript, so XSS cannot exfiltrate it. SameSite=Lax (or Strict) — withheld on cross-site subrequests, neutering classic CSRF. Scope tightly: host-only (omit Domain) and Path=/; lifetime via Max-Age per policy (session cookie for shared machines). Strong answers add: rotate the session ID at login (session fixation) and pair SameSite=None scenarios with explicit CSRF tokens.

Walk through the ETag / 304 conditional flow. What does it save?

First GET: server returns 200, the body, and ETag: "v42" (a version fingerprint); the client caches both. Later GETs send If-None-Match: "v42". If the resource is unchanged the server replies 304 Not Modified with no body — saving the body's bandwidth and server serialization, at the cost of one small round trip; if changed, a normal 200 with new body and ETag. Cache-Control: max-age avoids even the round trip while fresh; ETag validation takes over after expiry. The write-side siblings (If-Match → 412) implement optimistic concurrency.

HTTP/1.1 vs HTTP/2 vs HTTP/3 — what did each fix?

1.1 fixed 1.0's connection-per-request handshake tax with persistent connections (and added Host, chunked) — but one ordered response at a time per connection causes head-of-line blocking, worked around with ~6 parallel connections and asset bundling. HTTP/2 multiplexes many streams as binary frames over one connection with HPACK header compression — but TCP's in-order byte stream means one lost packet stalls all streams (transport- level HOL). HTTP/3 runs over QUIC on UDP: reliability is per-stream in userspace, so loss stalls only its stream; TLS 1.3 is integrated (0–1 RTT) and connection IDs survive IP changes (Wi-Fi→cellular migration). Practical note: apps typically speak 1.1 behind an edge proxy speaking 2/3.

How does a server know where a request's body ends?

Because TCP is a boundary-less byte stream, HTTP frames itself: headers end at the first empty line (a lone CRLF). The body's extent is then declared by Content-Length: N (read exactly N bytes), or Transfer-Encoding: chunked (read hex-sized chunks until the zero-length chunk), or — legacy — by connection close. Disagreement between intermediaries about these rules is the root of request-smuggling attacks; HTTP/2 replaced text framing with binary length-prefixed frames partly for this reason.

Sessions vs JWTs — give the trade-offs and a sensible production choice.

Sessions: server/shared-store state keyed by a random cookie ID — instant revocation, tiny per-request cost, nothing readable client-side; but requires a shared store (Redis) or sticky sessions to scale horizontally. JWTs: signed, self-contained claims verified statelessly by any instance or service — perfect for horizontal scale and microservices; but readable by anyone holding them (signed ≠ encrypted), hundreds of bytes per request, and revocation is hard — mitigated with short-lived access tokens plus refresh tokens. A defensible production answer: cookie-based session (or short JWT in an HttpOnly cookie) at the browser edge, JWTs between services.

A payment POST timed out. The gateway retried it and the customer was charged twice. Fix the design.

The timeout was ambiguous (request lost vs response lost — Part 4), and POST is not idempotent, so the retry re-executed the charge. Fix: idempotency keys — the client sends a unique Idempotency-Key per logical operation; the server atomically records the key (unique index / Redis SET NX) with the operation's result, executes once, and answers replays with the stored response. Also: configure gateways/LBs to auto-retry only idempotent methods, and surface 409/processing states for concurrent replays. The same reasoning returns for load-balancer retries (Part 9) and at-least-once message delivery (Part 13).

Your service is healthy in local tests, but users see 502s and 504s. What's the difference and where do you look?

Both come from the proxy/load balancer in front of the app, not from the app's code. 502 Bad Gateway: the proxy reached your backend but got a refused connection or malformed response — look for crashed processes, restarts mid-deploy, wrong upstream port, app answering on a different protocol. 504 Gateway Timeout: the proxy connected and waited, but your app exceeded the proxy's timeout — look for slow queries, exhausted thread/ connection pools (§15), or a proxy timeout shorter than the app's slowest legitimate work. 503 means no healthy backend at all (failing health checks, deploy in flight, overload shedding). 17. Common misconceptions

❌ Myths engineers actually believe

❌ "POST is more secure than GET."
✅ The verb provides zero confidentiality — both travel in the same plaintext (or the same TLS tunnel). Security comes from TLS (Part 8), not the method. The grain of truth that feeds the myth: URLs (with their query strings) leak into browser history, server access logs, and Referer headers, while bodies usually do not — so secrets must never ride in query strings. That is a logging-hygiene argument, not encryption.

❌ "JWTs are encrypted."
✅ Standard JWTs are base64url-encoded and signed — anyone holding one can read every claim in seconds. The signature prevents tampering and forgery, nothing more. Never put secrets in JWT payloads; encrypt the transport (TLS) and, if payload secrecy is truly required, use JWE — which your stack almost certainly doesn't.

❌ "CORS protects my server from attackers."
✅ CORS is enforced by browsers to protect users' ambient credentials from malicious websites. Attackers with curl, scripts, or their own servers bypass it entirely — your API still needs authentication, authorization, rate limiting, and input validation. Tightening CORS does not secure an open endpoint; it only governs which web pages' JavaScript may read responses.

❌ "Cookies are only sent back to the page that set them."
✅ Cookies are scoped to a site (Domain + Path), not a page — and the browser attaches them to every matching request regardless of which page triggered it, including requests initiated by other sites' HTML. That automatic attachment is exactly what CSRF exploits, and why SameSite, CSRF tokens, and CORS-with- credentials rules all exist.

❌ "HTTPS is a different protocol from HTTP."
✅ HTTPS is the same HTTP — identical methods, headers, status codes — running through an encrypted TLS tunnel (and using port 443 by default instead of 80). Everything in this chapter applies unchanged; what changes is that on-path observers see only ciphertext. How that tunnel is built is precisely Part 8.

❌ "REST APIs must use JSON."
✅ REST is resource-and-verb architectural style; it predates JSON's reign and is representation-agnostic — XML, CSV, protobuf, HTML, images are all legitimate. Content negotiation (Accept / Content-Type) exists precisely so one resource can serve multiple representations. JSON is a convention of our era, not a requirement of the style.

❌ "The #fragment is sent to the server."
✅ The fragment never leaves the client — browsers strip it before writing the request line. It addresses content within the retrieved document (or drives client-side routing). If your backend needs it, it must arrive some other way (query param, body) — and its absence from access logs is by design, which OAuth's implicit flow once exploited deliberately.

❌ "Statelessness means my application can't keep state."
✅ Statelessness is a property of the protocol, not your product. Carts, logins, and preferences are fine — the protocol just refuses to store them for you, so you must place them deliberately: on the client (cookies, tokens), in server memory (sessions — careful with scaling), or in a shared store (Redis, DB). "Where does the state live?" is the architecture question hiding inside every auth debate.
