Complete Request Journeys — Every Layer, End to End

Thirteen parts ago you typed localhost:8080 and we promised you would one day know what every character set in motion. This is the payoff. We will not teach a single new concept here — instead we take five real architectures you already half-know and trace one request through each, hop by hop, layer by layer, header by header, from the keystroke to the database row and all the way back. By the end you will be able to answer the most famous systems-design interview question on Earth without pausing for breath.

🧭 Why this chapter exists

Every part so far taught one slice of the stack in isolation: DNS in Part 6, TLS in Part 8, the ALB in Part 11, the Kubernetes Service in Part 12. Isolation is how you learn the pieces, but production is where they all fire at once, in order, in milliseconds. The gap between "I understand TLS" and "I can explain exactly where TLS terminates in our production path and why our app sees http:// in its redirects" is the gap between a mid-level engineer and a senior one. This chapter is pure synthesis: no new vocabulary, just composition. Read it as the assembly instructions for everything you already own.

How to read a journey — the universal phases

Before the five journeys, install one reusable mental template. Every web request — local or global, one hop or six — passes through the same six phases in the same order. The architectures differ only in how many times and at how many machines each phase happens. Memorize the phases and every journey becomes a variation on one theme.

🔑 Key point — architecture only changes the count, never the phases

Journey 1 (localhost) runs each phase once on one machine. Journey 5 (CDN) runs phases 1–4 twice — once between the browser and the edge, once between the edge and the origin — across three continents. The phases are invariant. When you walk into an interview and they sketch any architecture on a whiteboard, silently overlay these six phases and you will never be lost.

🌍 Analogy — five routes, one set of rules of the road

Think of the five journeys as five different routes between your house and a friend's house: walking next door (localhost), driving across town with one toll booth (Nginx), taking the highway through a managed interchange (ALB), navigating a city with a central dispatcher rerouting you live (Kubernetes), and flying internationally with a local connecting hub near each end (CDN). The vehicles, distances, and number of stops differ wildly — but every route obeys the same traffic laws: you still need an address (DNS), you still merge into traffic (TCP), you still show ID at secure checkpoints (TLS), you still speak to whoever greets you (HTTP). Learn the laws once; the routes are just rearrangements.

Journey 1 — Browser → Spring Boot Application (the localhost baseline)

🧭 When you use this — and why you'd choose it

When: local development on your laptop, or a single virtual machine (VM) with the app exposed directly to the world — a hobby project, an internal tool, a demo box. Why choose it: because it is the simplest thing that can possibly work. No load balancer, no proxy, no orchestration, nothing to operate. One process, one port, one machine. This is the baseline every other journey is built on: master this clean single-machine path and every later journey is just "the same thing, but with more middlemen in front." We deliberately walk this one in the most detail, including the full vertical encapsulation diagram, so you see the entire stack once with nothing hidden.

1.a — The topology

Your React app, served by Vite on :3000, makes fetch("http://localhost:8080/api/orders/42"). Spring Boot is running on the same laptop on :8080; PostgreSQL runs in a Docker container publishing :5432. Everything is on one machine — the request never touches a physical cable. 🔑 Key point — localhost is real networking minus the cable

Back in Part 3 we said 127.0.0.1 (and the name localhost) is the loopback address: a virtual network interface the kernel implements in software. A request to localhost:8080 still runs the full Layer 4 / Layer 3 machinery — there is a real TCP three-way handshake, real ports, real sequence numbers — it just never descends to Layer 2/Layer 1 (no Ethernet frame, no NIC, no voltage). That is exactly why port conflicts (Address already in use), connection refusals, and TCP states all happen locally. Local testing genuinely exercises Layers 3–7.

1.b — Step-by-step walkthrough

  1. Keystroke / fetch. The browser's JavaScript engine calls fetch("http://localhost:8080/api/orders/42"). The browser parses the URL: scheme http (so port defaults would be 80, but the URL overrides to 8080), host localhost, path /api/orders/42.
  2. Name resolution (the trivial case). localhost does not go to DNS. The OS checks its hosts file first — on Linux/macOS /etc/hosts, on Windows C:\Windows\System32\drivers\etc\hosts — which maps localhost → 127.0.0.1. Resolution is instant and offline. (This is the Part 6 resolver order: hosts file before DNS.)
  3. TCP three-way handshake. The browser opens a socket from an ephemeral port (say 54312) to 127.0.0.1:8080. The kernel runs the Part 4 handshake against itself: SYN → SYN-ACK → ACK. The connection moves to ESTABLISHED. Over loopback this takes microseconds.
  4. TLS? Usually skipped in dev. The scheme is http, not https, so there is no TLS handshake. Bytes go in the clear. (In dev this is normal and fine — the data never leaves your machine. Part 8's whole threat model is "data crossing networks owned by strangers," which does not apply here.)
  5. HTTP request. The browser writes the raw HTTP/1.1 request bytes into the socket: a request line, host header, and standard headers (Part 7).
  6. Tomcat accepts. Spring Boot's embedded Tomcat has a listening socket on :8080. Its acceptor thread accepts the connection, a worker thread reads the request bytes, and parses them into an HttpServletRequest.
  7. DispatcherServlet routes. Spring's front controller (the DispatcherServlet) matches GET /api/orders/42 against handler mappings and dispatches to OrderController.getOrder(42).
  8. JDBC to PostgreSQL. The controller calls the repository; Hibernate/JDBC issues SELECT * FROM orders WHERE id = 42. This opens (or reuses from the HikariCP pool) a second TCP connection — Spring Boot is now a client — to 127.0.0.1:5432, speaking the PostgreSQL wire protocol (Part 5: another protocol on another port).
  9. Database responds. PostgreSQL executes the query and streams result rows back over the 5432 connection. JDBC maps them into a Java object.
  10. Build the response. The controller returns the order object; Spring serializes it to JSON via Jackson, sets Content-Type: application/json, and Tomcat writes the HTTP response bytes back into the browser's socket.
  11. Render. The browser reads 200 OK, parses the JSON body, and your React component re-renders. Done — typically in single-digit milliseconds because nothing left the machine.

🌍 Analogy — encapsulation is nested envelopes

Your HTTP request is a letter. TCP seals it in an envelope marked "to apartment 8080, from apartment 54312" (ports = apartment numbers). IP seals that in a bigger envelope marked with building addresses (here, both addresses are "this same building," 127.0.0.1). The link layer would put a courier's hand-label on it for the next street. On loopback the courier is the building's internal mailroom: it never steps outside. At the destination each envelope is opened in reverse order until the original letter reaches the right desk (Tomcat). Every later journey adds more envelopes and more couriers — but the letter inside never changes.

1.e — What could break here + how you'd debug it

🛠 Follow the failure (Journey 1)
  • Connection refused instantly → nothing is listening on 8080. Spring Boot did not start, or bound to a different port. The TCP SYN got an immediate RST (Part 4). Debug: nc -vz localhost 8080 or lsof -i :8080 / netstat -ano to see what (if anything) holds the port.
  • Address already in use on startup → a previous run still owns 8080 (Part 5 port binding). Kill the stale process or change the port.
  • App starts but DB calls fail with Connection refused to 5432 → the Postgres container is not running or the -p 5432:5432 publish is missing (Part 12 Docker port mapping). Debug: docker ps, then psql -h localhost -p 5432.
  • Browser shows a CORS error → not a network failure at all. The request succeeded over the wire, but the React app on :3000 called the API on :8080 — a different origin — and the server did not return the right Access-Control-Allow-Origin header (Part 7). Fix it server-side, not in the network.
  • Hangs forever → rare on loopback, but a deadlocked controller or an exhausted HikariCP pool will hold the HTTP connection open with no response. Thread dump the JVM.

Journey 2 — Browser → AWS ALB → ECS → Spring Boot

🧭 When you use this — and why you'd choose it

When: standard production on AWS without Kubernetes — you want managed infrastructure, autoscaling, and zero servers to patch, but you are not ready for the operational weight of an orchestrator. Why choose it: an Application Load Balancer (Part 9) plus ECS (Elastic Container Service, Part 12) running Fargate gives you a public, TLS-terminated, health-checked, horizontally-scalable front door with almost no undifferentiated heavy lifting. This is the workhorse AWS architecture for a Spring Boot REST API behind a React SPA. The single most important new idea versus Journey 1: there are now two separate TCP connections and TLS lives on only the first one.

🔑 Key point — two TCP connections, one TLS leg

The browser does not have a TCP connection to your Spring Boot app. It has a connection to the ALB. The ALB, acting as a reverse proxy (Part 10), opens a completely separate connection to a chosen ECS task. So the journey has two transport legs:

  • Leg A: browser ↔ ALB — over the public Internet, encrypted (HTTPS/TLS), terminated at the ALB using a certificate from ACM (AWS Certificate Manager).
  • Leg B: ALB ↔ ECS task — inside the VPC, usually plaintext HTTP on :8080 (the VPC is private; many teams stop here, though you can re-encrypt — see the three-level block below).

This split is why your app sees the ALB's IP as the "client," not the browser's — and why X-Forwarded-For exists.

2.b — Step-by-step walkthrough

  1. DNS resolution via Route 53. The browser resolves app.example.com. The authoritative zone in Route 53 holds an ALIAS record (an AWS-specific record like a CNAME but resolvable at the zone apex) pointing at the ALB. The resolver returns one of the ALB's public IPs, e.g. 203.0.113.10 (Part 6).
  2. TCP handshake to the ALB. The browser opens TCP to 203.0.113.10:443. Packets enter the VPC through the Internet Gateway (IGW), land in the public subnet, and are admitted by the ALB's security group alb-sg (allows 443 from anywhere). Handshake completes (Part 4/11).
  3. TLS handshake — terminates at the ALB. Over that TCP pipe the browser performs the Part 8 TLS handshake: ClientHello with SNI (Server Name Indication) app.example.com → ALB selects the matching ACM certificate → key exchange → encrypted tunnel. TLS ends here. The ALB now holds the plaintext request.
  4. HTTP request + L7 routing. The browser sends GET /api/orders/42. The ALB, an L7 device, reads the path, matches a listener rule (e.g. /api/* → the orders target group), and picks a healthy target using the target group's health checks (Part 9 — only targets passing GET /actuator/health are eligible).
  5. New connection to the ECS task. The ALB opens a fresh TCP connection (often from a keep-alive pool) to the chosen task at 10.0.10.42:8080, plaintext HTTP. The app's security group app-sg allows 8080 only from alb-sg (Part 11 SG-to-SG reference) — the task is unreachable from the Internet directly.
  6. Forwarded headers. The ALB adds X-Forwarded-For: 198.51.100.25 (the real client IP), X-Forwarded-Proto: https (the original scheme), and X-Forwarded-Port: 443. Without these, Spring Boot would believe the client is the ALB and that the connection was plain HTTP.
  7. Spring Boot processes. Tomcat accepts, DispatcherServlet routes to OrderController exactly as in Journey 1 — the app is identical; only what is in front of it changed.
  8. JDBC to RDS. The controller queries PostgreSQL at 10.0.20.5:5432. The DB security group db-sg allows 5432 only from app-sg (the Part 11 SG chain: Internet → alb-sg → app-sg → db-sg).
  9. Optional egress to an external API. If the controller calls Stripe, that outbound request leaves the private subnet via the NAT Gateway (Part 11) — private tasks have no public IP, so the NAT GW in the public subnet performs source NAT and gives them Internet egress.
  10. Response unwinds. Spring Boot writes the JSON response on Leg B → ALB receives it → ALB writes it back to the browser over the still-encrypted Leg A (re-applying TLS) → browser renders.

🧪 The one-line fix every Spring Boot team needs behind a proxy
# application.properties — trust the proxy's forwarded headers
server.forward-headers-strategy=native      # or =framework

# Now:
#   request.getRemoteAddr()  ──►  198.51.100.25   (real client, from X-Forwarded-For)
#   request.isSecure()       ──►  true            (from X-Forwarded-Proto: https)
#   redirects + cookies      ──►  built as https://app.example.com/...

This single property is the most common "works locally, breaks behind the load balancer" fix in the Spring world. The classic symptom — "my login redirect drops the user onto http:// and they get a security warning" — is X-Forwarded-Proto being ignored (Part 9).

🟢 Beginner — where does TLS live?

The padlock in the browser proves the connection between the browser and the ALB is encrypted. From the ALB to your app, traffic is usually plain text — but that hop is inside Amazon's private network, not the public Internet, so it is considered safe for most apps.

🟡 Intermediate — TLS termination vs re-encryption

The ALB terminates TLS: it decrypts the request so it can read the path and route at L7. By default Leg B (ALB → task) is HTTP. You can switch the target group to HTTPS so the ALB re-encrypts to the task — this is "TLS re-encryption" (sometimes loosely called end-to-end). You then run TLS twice and your app must present its own certificate on 8080.

🔴 Advanced — when re-encryption is actually required

Compliance regimes (PCI-DSS for cardholder data, HIPAA, FedRAMP) often mandate encryption in transit everywhere, including inside the VPC, because the threat model includes a compromised host on the same subnet sniffing the wire. Then you re-encrypt Leg B (ALB target group protocol = HTTPS, app holds a cert) or push TLS all the way to the pod with a service mesh (Journey 3, Part 13 mTLS). The cost is double handshakes and double CPU for crypto; the benefit is no plaintext anywhere. Most non-regulated apps rationally accept plaintext inside the VPC and terminate once at the ALB.

2.e — What could break here + how you'd debug it

🛠 Follow the failure (Journey 2)
  • Page won't resolve → Route 53 record missing/typo, or resolver cache stale (Part 6). Debug: dig app.example.com — confirm it returns the ALB IP.
  • Connection times out (no SYN-ACK) → almost always a security group or NACL (Part 11): alb-sg not allowing 443, or the task's app-sg not allowing 8080 from alb-sg. A timeout (not a refusal) is the signature of a firewall silently dropping packets. Debug: VPC Flow Logs, check SG/NACL rules.
  • HTTP 502 Bad Gateway from the ALB → the ALB reached a target but got a malformed/closed response: the app crashed, returned a bad response, or closed the keep-alive connection early (Part 9). Debug: app logs + ALB HTTPCode_Target_5XX metrics.
  • HTTP 503 Service Unavailable → no healthy targets in the target group — every task is failing its health check (Part 9). Debug: target group health tab; check /actuator/health, deployment state, task crash loops.
  • HTTP 504 Gateway Timeout → a target was selected but did not respond within the ALB idle timeout — slow query, slow downstream, deadlock (Part 9). Debug: app latency metrics, slow-query logs, thread dumps.
  • Logins redirect to http:// / wrong host → X-Forwarded-Proto/Host ignored. Set server.forward-headers-strategy (Part 9, fix above).
  • External API calls hang from the app → no route to the Internet: missing NAT Gateway or route table entry (Part 11). Debug: route tables, NAT GW status.

Journey 3 — Browser → Kubernetes Ingress → Service → Pod

🧭 When you use this — and why you'd choose it

When: containerized microservices running on Kubernetes (EKS on AWS). You have many services, you deploy constantly, you need self-healing, rolling updates, and service discovery built in. Why choose it: Kubernetes turns the manual wiring of Journey 2 into declarative objects — a Service gives you a stable virtual address in front of a churning set of pods, an Ingress gives you L7 routing, and the control plane reschedules dead pods automatically. The defining new idea here: pod IPs are ephemeral and the client never sees them — the Service abstraction (Part 12) hides all the churn behind one stable name.

🔑 Key point — the Service is the stable mask over ephemeral pods

Pod orders-7f9c at 10.0.10.31 might be killed and rescheduled as orders-2k1d at 10.0.10.77 thirty seconds from now (Part 12 — pod IPs are ephemeral). The Service's endpoint list is continuously updated to contain only ready pods. This is exactly the load-balancer indirection of Part 9, implemented as kernel packet rules instead of a hardware box.

3.b — Step-by-step walkthrough

  1. DNS to the cloud LB. app.example.com resolves (via Route 53, Part 6) to the public IP of the cloud Load Balancer that an Ingress/Service-of-type-LoadBalancer provisioned — an NLB (L4) or ALB (L7) sitting in the public subnets (Part 11).
  2. TCP handshake to the LB at 203.0.113.10:443 (Part 4), admitted by the LB's security group.
  3. TLS handshake. Depending on setup, TLS terminates either at the cloud LB or is passed through (L4 NLB) to terminate at the Ingress Controller pod. In the common Nginx-Ingress pattern, the NLB passes TCP through and the Ingress Controller terminates TLS (Part 8/12).
  4. Ingress Controller L7 routing. The Ingress Controller pod (Nginx or Envoy) now holds the plaintext request. It reads Host: app.example.com and path /api/orders/42, matches an Ingress rule, and selects the backend Service orders (Parts 10/12).
  5. To the ClusterIP Service. The controller sends the request to the Service virtual IP, e.g. 10.96.12.7:80. This IP is not assigned to any machine — it exists only as iptables/IPVS rules (Part 12).
  6. kube-proxy DNAT to a pod. The node's kube-proxy rules perform DNAT (destination NAT): the packet destined for the Service IP is rewritten to a specific ready pod IP, e.g. 10.0.10.31:8080, chosen across the endpoint set (L4 load balancing, Part 9/12). Readiness probes (Part 9) decide which pods are eligible.
  7. Pod processes. Spring Boot in pod orders-7f9c handles the request — identical app code to Journeys 1 and 2.
  8. East-west call. The orders pod needs customer data. It calls http://customer/api/customers/9. CoreDNS (the cluster DNS, Part 12) resolves the short name customer to the customer Service's ClusterIP. The request then repeats steps 5–6 inside the cluster: Service → kube-proxy DNAT → a healthy customer pod.
  9. Optional sidecar mTLS. If a service mesh (Istio/Linkerd, Part 13) is installed, the orders pod's traffic is transparently intercepted by its Envoy sidecar, which opens a mutual-TLS connection to the customer pod's sidecar — encrypting and authenticating east-west traffic without the app knowing.
  10. Database. The customer pod runs JDBC to RDS at 10.0.20.5:5432 (the SG chain still applies — node/pod security group allowed by db-sg).
  11. Response unwinds back through each hop in reverse, TLS re-applied on the public leg, to the browser.
🌍 Analogy — the Service is a department phone extension

Calling pod 10.0.10.31 directly is like memorizing one specific employee's personal mobile number — useless the moment they leave the company. Calling the orders Service is like dialing the "Orders Department" extension: the switchboard (kube-proxy) routes you to whichever clerk is currently on shift and available (ready). Staff turnover (pod churn) is invisible to callers. CoreDNS is the internal company directory that turns the department name into that extension number.

🧭 When you use this — and why you'd choose it

Why choose it: Nginx is the canonical reverse proxy (Part 10). On one host it can terminate TLS, serve your React static build directly, proxy API calls to Spring Boot, hold keep-alive upstream connections, and upgrade WebSockets — all from one config file you fully control. The key insight: Nginx is doing by hand exactly what the ALB did as a managed service in Journey 2. Same role (L7 reverse proxy + TLS termination + load balancing), different operator — you instead of AWS.

4.b — Step-by-step walkthrough

  1. DNS. app.example.com resolves to the host's public IP 203.0.113.10 (an A record this time, not an ALIAS — there is no AWS LB to alias to). Part 6.
  2. TCP handshake to 203.0.113.10:443 (Part 4). The host's firewall (security group, ufw, or iptables) must allow 443.
  3. TLS terminates at Nginx. Nginx holds the certificate (e.g. from Let's Encrypt) and performs the Part 8 handshake. It now has the plaintext request. (This is the same termination role the ALB played — but you provisioned the cert and configured the cipher suite yourself.)
  4. Nginx decides: static or proxy. Nginx matches the request path against its location blocks (Part 10):
    • GET / or /assets/app.js → served directly from disk (/var/www/react/). Spring Boot is never touched. This is why Nginx in front of a SPA is so efficient — static files never enter the JVM.
    • GET /api/orders/42 → proxy_pass http://127.0.0.1:8080 to Spring Boot.
  5. The proxy_set_header chain. When proxying, Nginx rewrites/adds headers exactly like the ALB's X-Forwarded-* — but here you write the rules (Part 9/10): 
      proxy_set_header Host              $host;
  proxy_set_header X-Real-IP         $remote_addr;
  proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
  proxy_set_header X-Forwarded-Proto $scheme;
  6. Keep-alive upstream. Nginx maintains a pool of persistent TCP connections to 127.0.0.1:8080 (Part 4/7 keep-alive), so it does not pay a fresh handshake to Spring Boot on every request — the same reuse principle as connection pooling.
  7. Spring Boot processes the request (Tomcat → DispatcherServlet → controller → JDBC → PostgreSQL) — identical to every journey.
  8. WebSocket upgrade (live feature). For a live notifications feature, the browser opens wss://app.example.com/ws/notifications. The request arrives as an HTTP/1.1 Upgrade: websocket request (Part 7). Nginx must be told to pass the upgrade through: 
      location /ws/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_set_header Upgrade    $http_upgrade;
    proxy_set_header Connection "upgrade";
  }
    Now the connection is upgraded end-to-end and Spring Boot can push messages over the long-lived socket.
  9. Response flows back through Nginx, re-encrypted over the browser's TLS leg.
🔑 Key point — Journey 4 and Journey 2 are the same shape

Lay Fig 14.6 next to Fig 14.3 and the structure is identical: a public L7 entry point that terminates TLS, reads the path, injects forwarded headers, and proxies to a private app on 8080 over a second connection. The ALB is a managed, horizontally-scaled, multi-tenant Nginx (conceptually). Everything you learned about one transfers to the other. The differences are operational: who patches it, who scales it, who holds the cert, who writes the routing rules — AWS for the ALB, you for Nginx.

Journey 5 — Browser → CDN → Load Balancer → Application

🧭 When you use this — and why you'd choose it

When: a global application serving a mix of static and dynamic content to latency-sensitive users on every continent — an e-commerce site, a media platform, any product where a user in Sydney and a user in São Paulo both expect a snappy experience while your origin lives in us-east-1. Why choose it: a CDN (Content Delivery Network) like Amazon CloudFront puts hundreds of edge POPs (points of presence) physically close to users worldwide. It terminates TLS near the user (killing handshake latency — Part 1's latency weapon), serves cacheable assets from the edge without ever touching your origin, and forwards only the uncacheable requests over an optimized backbone to the origin (which is the ALB or Nginx from the earlier journeys). The defining new idea: there are now two HTTP legs (browser↔edge, edge↔origin) and a cache that can make the second leg disappear entirely.

5.a — The topology (with the two cache paths)

A CDN is, in Part 10's terms, a giant geographically-distributed reverse proxy. The single most important thing to understand is the branch at the edge: a cache hit never leaves the edge, while a cache miss (and all dynamic requests) is forwarded to the origin. We draw both paths:

🔑 Key point — the CDN only owns the cacheable half

The CDN does not serve "everything." It serves what is cacheable: static assets (JS/CSS/images/fonts), and any response your origin explicitly marks cacheable via Cache-Control (Part 7). Your app.js with Cache-Control: public, max-age=31536000, immutable is served from the Sydney edge in ~10 ms and never touches us-east-1. But GET /api/orders/42 — personalized, dynamic — is marked Cache-Control: no-store, so it is always forwarded to the origin, paying the ~200 ms round trip (but over the CDN's optimized backbone, which is still faster and more reliable than the open Internet). Knowing which half is which is the whole game.

5.b — Step-by-step walkthrough (both paths)

  1. DNS resolves to the nearest edge. app.example.com is a CNAME/ALIAS to a CloudFront distribution. CloudFront uses anycast (Part 3 — one IP advertised from many locations) and geo-aware DNS (Part 6) so the Sydney user's resolver returns an edge IP whose nearest POP is in Sydney. The user reaches an edge ~10 ms away instead of an origin ~200 ms away.
  2. TCP handshake to the edge (Part 4) — fast, because the edge is geographically close. Round-trip-dependent handshakes (TCP + TLS) are exactly what proximity speeds up.
  3. TLS terminates at the edge. CloudFront presents your certificate (from ACM) and completes the Part 8 handshake near the user. Terminating TLS close to the client is a major latency win — the multi-round-trip handshake happens over 10 ms legs, not 200 ms legs.
  4. The edge computes a cache key and looks it up. The cache key is normally the host + path (+ selected query strings/headers). Now the branch:
  5. Path A — cache HIT. For GET /assets/app.js, if a fresh copy is in the edge cache, CloudFront returns it immediately with a header like X-Cache: Hit from cloudfront. The origin is never contacted. Total time ≈ the 10 ms edge round trip. This is the magic of a CDN.
  6. Path B — cache MISS or dynamic. For GET /api/orders/42 (or a static asset not yet cached at this edge), CloudFront forwards the request to the origin over its optimized private backbone. Optionally it first checks an Origin Shield — a single designated regional cache that consolidates requests from all edges so your origin sees far fewer requests (and a higher cache-hit ratio).
  7. The origin is just an earlier journey. The origin is your ALB (Journey 2) or Nginx (Journey 4) in us-east-1. From the origin's perspective, CloudFront is simply a client at the edge's IP — it processes the request through Spring Boot → RDS exactly as before. (CloudFront forwards the real client IP in CloudFront-Viewer-Address / X-Forwarded-For, Part 9.)
  8. Response caches on the way back. The origin's response travels back to the edge. If its Cache-Control permits, the edge stores it, so the next Sydney user requesting the same asset gets a HIT (Path A). ETag/Last-Modified (Part 7) let the edge later revalidate cheaply with a conditional request (If-None-Match → 304 Not Modified) instead of re-downloading.
  9. Browser renders from whichever path served it — indistinguishable to the user except in speed.

🌍 Analogy — the CDN edge is a neighborhood library branch

The origin in us-east-1 is the national archive — authoritative, but far away. Each CDN edge is your local library branch. If the book (asset) you want is on the branch shelf (cache hit), you walk out with it in two minutes. If it is not (cache miss), the branch requests it from the national archive over a fast inter-library courier (the CDN backbone), lends it to you, and keeps a copy on the shelf so the next patron gets it instantly. Rare, one-of-a-kind, constantly-changing documents (dynamic/personalized requests) always go to the archive. The Origin Shield is a single regional warehouse that all branches ask first, so the national archive is rarely bothered.

5.c — Where TLS terminates and re-encrypts across the CDN journey

🟢 Beginner — two padlocks, end to end

There are two encrypted legs: browser-to-edge and edge-to-origin. The browser's padlock is the first one. The CDN decrypts at the edge so it can decide hit-vs-miss, then re-encrypts to talk to your origin. Your data is encrypted on the public Internet the whole way; it is briefly in plaintext only inside the edge and inside your origin, which you control.

🟡 Intermediate — terminate, inspect, re-originate

CloudFront terminates the viewer TLS at the edge (Viewer Protocol Policy). It must — it cannot compute a cache key or read Cache-Control on encrypted bytes. On a miss it opens a separate TLS connection to the origin (Origin Protocol Policy = HTTPS), so the edge↔origin leg is re-encrypted. That is two independent TLS sessions, just like Journey 2 had browser↔ALB and (optionally) ALB↔task, but stretched across continents.

🔴 Advanced — the security side-benefits fall out for free

Because every viewer connection terminates at the CDN edge, the CDN becomes a natural enforcement point: it absorbs volumetric DDoS (the edge fleet has more capacity than any origin), runs a WAF (Web Application Firewall) to filter malicious requests before they reach you, and offloads all TLS handshake CPU from your origin. The origin can then be locked down to accept connections only from the CDN (via an origin access identity or a shared secret header + security group), shrinking its attack surface to one well-defended front door. The CDN is simultaneously a latency tool, a caching tool, and a security perimeter — three wins from one architectural move (Part 10's reverse-proxy benefits, globalized).

5.e — What could break here + how you'd debug it

🛠 Follow the failure (Journey 5)
  • Stale content served after a deploy → the edge is serving a cached old asset that hasn't expired (Part 7 Cache-Control/TTL). This is why teams fingerprint filenames (app.4f3a1.js) — a new build = a new URL = a guaranteed fresh fetch. Debug: check X-Cache and Age headers; invalidate the distribution.
  • Everything is a cache MISS (low hit ratio) → cache key includes too much (e.g. forwarding all query strings or cookies), or origin sends Cache-Control: no-store on assets. Debug: CloudFront cache statistics; tighten the cache policy.
  • 502/504 from CloudFront → the origin is failing or slow (Part 9 — same 502/504 semantics, now reported by the CDN). Debug: hit the origin directly (bypass the CDN) to isolate whether it's the edge or the origin.
  • TLS error at the edge → certificate/SNI mismatch on the distribution, or the viewer used an unsupported protocol (Part 8). Debug: openssl s_client -connect the edge hostname; check the distribution's certificate and minimum TLS version.
  • Redirect loop / wrong scheme → origin ignoring X-Forwarded-Proto from CloudFront and bouncing HTTPS→HTTP (Part 9). Same forward-headers fix.
  • 403 from CloudFront → WAF rule blocked the request, or origin-access restriction misconfigured. Debug: WAF logs.

Things that are ALWAYS true, regardless of architecture

🔑 The invariants — true in every journey above
  1. It always starts with DNS. Name → IP is phase one, every single time (Part 6). Even localhost resolves (via the hosts file). No connection happens until you have an IP.
  2. There is always a TCP + TLS handshake cost per new connection (Parts 4/8). Every fresh connection pays round trips before any data moves — which is precisely why keep-alive, connection pooling (HikariCP), HTTP/2 multiplexing, and TLS session resumption exist everywhere. Reuse is the universal optimization.
  3. Every L7 hop can read and rewrite headers — which makes each L7 hop a place to route, cache, authenticate, compress, or (if misconfigured) break. More L7 hops = more power and more failure modes.
  4. The real client IP survives only via X-Forwarded-For across L7 hops (Part 9). The moment a proxy opens a new connection, the app's view of "the client" becomes the proxy unless XFF carries the truth — and the app must be told to trust it.
  5. More hops = more places to debug, but also more places to cache, secure, and route. Each middleman is a liability and an asset simultaneously. The art of architecture is adding exactly the hops whose benefit (caching at the edge, TLS offload, L7 routing) outweighs their latency and operational cost.
  6. The application code barely changes. The exact same Spring Boot controller ran in all five journeys. What changed was everything in front of it. Your app is the constant; the network is the variable.

How X-Forwarded-For accumulates across hops

🟢 Beginner — the header that remembers the client

When a proxy forwards your request, it tells the next server "hey, the real person who sent this is at this IP" using the X-Forwarded-For header. Without it, your app would think the proxy is the user.

🟡 Intermediate — it's a comma-separated trail

Each proxy appends the IP it saw to X-Forwarded-For, building a left-to-right trail: the original client is leftmost, each subsequent proxy is added on the right. With two proxies (CDN edge then origin LB) the app sees two IPs. Your code must pick the correct entry — usually the leftmost trusted one — to identify the true client.

🔴 Advanced — why you must count your trusted hops

Because clients can forge X-Forwarded-For, you cannot blindly trust the leftmost value — an attacker could prepend a fake IP. The correct rule: trust only the entries appended by infrastructure you control, which means configuring the number of trusted proxy hops (Spring's ForwardedHeaderFilter with a trusted-proxies list, or a framework strategy). In Journey 5 with a CDN and an origin LB, that's two trusted hops; getting the count wrong either exposes you to IP spoofing or makes you attribute traffic to your own load balancer.

🧪 The all-in-one bisection trick

When a request fails through a multi-hop journey, bisect the path: test each hop in isolation, working from the inside out. Interview questions

🎤 Try answering out loud before you click
Walk me through what happens from typing a URL to seeing the page. (The all-time classic.)

Span every phase: (1) DNS — the browser resolves the hostname via its recursive resolver, walking root → TLD → authoritative (Route 53), getting an IP (Part 6). (2) TCP — it opens a socket to that IP:443 and completes the three-way handshake, SYN/SYN-ACK/ACK (Part 4). (3) TLS — over that pipe it runs the TLS handshake: ClientHello with SNI, the server presents its certificate, keys are agreed, an encrypted tunnel forms (Part 8). (4) HTTP — the browser sends GET / with headers (Part 7). (5) The front door — that endpoint is usually a load balancer or reverse proxy (ALB/Nginx, Part 9/10) which terminates TLS, reads the path, picks a healthy backend, and opens a second connection to the app, adding X-Forwarded-For. (6) The app — Tomcat → DispatcherServlet → controller (Part 7) runs the logic and issues a JDBC query to PostgreSQL on 5432 (Part 4/5). (7) Return — the response unwinds back through the proxy (re-encrypted) to the browser, which parses HTML/JSON and renders, firing more requests for assets (often served from a CDN edge, Part 14). Strong answers name where TLS terminates and that there are multiple TCP connections, not one.

In Journey 2 (browser → ALB → ECS), how many TLS handshakes occur, and where?

By default one: the browser ↔ ALB handshake, terminated at the ALB using an ACM certificate. The ALB → ECS task leg (Leg B) is plaintext HTTP inside the VPC, so no second handshake. If you enable re-encryption (target group protocol = HTTPS, app presents its own cert), there are two — one per leg. The key teaching point: the browser never has a TLS (or even TCP) connection to your Spring Boot app; it connects to the ALB, which is a separate reverse-proxy connection.

Where does the real client IP live after an ALB (or any reverse proxy)?

In the X-Forwarded-For request header, which the ALB injects with the original client's IP (198.51.100.25). At the TCP level, request.getRemoteAddr() returns the ALB's private IP, because the app's connection is to the ALB, not the browser. To recover the true client you must read XFF — and configure the app to trust it (Spring's server.forward-headers-strategy). With multiple proxies (CDN + ALB) XFF is a comma-separated trail, client-first; trust only the hops you operate.

Explain the cache hit vs miss path in a CDN.

On a hit, the requested object is fresh in the nearest edge POP's cache; CloudFront returns it directly (~10 ms) and the origin is never contacted (X-Cache: Hit). On a miss (or any uncacheable/dynamic request marked no-store), the edge forwards the request over the CDN's optimized backbone to the origin (the ALB/Nginx, ~200 ms for a Sydney↔us-east-1 round trip), optionally via an Origin Shield, then caches the response on the way back per its Cache-Control/ETag so the next user gets a hit. The CDN only caches what is cacheable; personalized data always reaches the origin.

How does adding a CDN change latency, and why?

It cuts latency for two reasons. First, the TLS/TCP handshakes terminate at an edge ~10 ms away instead of an origin ~200 ms away — and handshakes are multi-round-trip, so proximity multiplies the saving (Part 1: latency is distance-bound). Second, cacheable assets are served entirely from the edge, never paying the origin round trip at all. Dynamic requests still go to the origin, but over an optimized, persistent, pre-warmed backbone that is faster and more reliable than the open Internet. Net effect: static-heavy pages feel near-instant worldwide; even dynamic calls get a modest boost.

Given a 504, where do you look — and how is it different from 502 and 503?

A 504 Gateway Timeout means the proxy/LB selected a backend but the backend did not respond within the timeout — so look at the backend's speed: slow database queries, a deadlock, an overwhelmed thread pool, a slow downstream dependency. Tools: app latency dashboards, slow-query logs, a JVM thread dump. Contrast: 502 Bad Gateway = the backend answered but with a malformed or prematurely-closed response (often a crash or a keep-alive mismatch) — look at app crash logs. 503 Service Unavailable = there were no healthy backends at all — look at health checks and readiness (target group / kubectl get endpoints). All three are from Part 9, and the distinction is exactly what separates a confident answer from a guess.

Why are there two TCP connections behind a load balancer, not one?

Because the load balancer (or any reverse proxy) operates at L4/L7 by terminating the client connection and originating a new one to the backend. The client↔LB connection and the LB↔backend connection are independent: they can use different protocols (HTTPS vs HTTP), different keep-alive pools, even different HTTP versions. This is what lets the LB read the path to route (L7), reuse warm backend connections, and present one stable public endpoint while backends churn. It is also why the app can't see the client's TCP source IP and needs XFF.

A user in Sydney says the site is slow but your origin is in us-east-1. What do you suspect and check?

Geography: a ~200 ms round trip per request, multiplied by every uncached asset and every handshake. First check whether a CDN is in front and what the cache-hit ratio is (X-Cache/Age headers) — a low hit ratio means the edge isn't helping. If there's no CDN, that's the fix: put CloudFront in front so TLS terminates near the user and static assets serve from a Sydney edge. Also check for chatty behaviour — many sequential API round trips each pay the full transcontinental latency (Part 1's N+1 problem). The lever is moving content closer (edge caching) and reducing round trips, not bandwidth.

In Kubernetes, the pod IP changed but clients never noticed. Why?

Because clients target the Service, not the pod. The Service has a stable virtual IP (ClusterIP) that kube-proxy programs into every node's iptables/IPVS rules, DNAT-ing traffic to whichever ready pod IPs currently back it (Part 12). When a pod dies and is rescheduled with a new IP, the endpoint list updates automatically and the Service keeps routing — the ephemeral pod IP is an internal implementation detail the client never sees. CoreDNS resolves the Service name to that stable VIP, so even the name-to-address mapping is insulated from pod churn.

Where exactly does TLS terminate in each of the five journeys, and where is traffic ever plaintext?

J1: no TLS at all (plain HTTP on loopback). J2: at the ALB; plaintext on the ALB→task leg inside the VPC (unless re-encrypted). J3: at the cloud LB or Ingress controller pod; plaintext between Service/pod unless a mesh adds mTLS east-west. J4: at Nginx; plaintext on Nginx→Spring Boot (loopback). J5: at the CDN edge near the user, then re-encrypted edge→origin, then terminates again at the origin LB. The pattern: TLS terminates at the outermost L7 device that needs to read the request, and any "plaintext" leg is deliberately kept on a network you control (a VPC, a single host's loopback).

Common misconceptions

❌ Myths engineers actually believe

❌ "There's one TCP connection from my browser straight to my app."
✅ Behind any proxy or load balancer, the browser connects to the proxy, and the proxy opens a separate connection to the app. Every L7 hop is its own TCP (and possibly TLS) connection. In the CDN journey there are at least two; with a CDN plus an origin LB plus a mesh, more. This is why the app can't see the browser's source IP and why X-Forwarded-For exists.

❌ "TLS is end-to-end to my application by default."
✅ TLS almost always terminates at the edge — the ALB, the Ingress controller, Nginx, or the CDN edge — not at your app. The leg from there to your app is frequently plaintext (inside a VPC or on loopback). True end-to-end encryption to the pod requires deliberate work: re-encryption at the LB, or a service mesh doing mTLS. The padlock proves browser-to-edge security, not browser-to-app.

❌ "The CDN serves everything."
✅ A CDN serves only what is cacheable: static assets and responses your origin marks cacheable. Every dynamic, personalized, or no-store request is forwarded to the origin and pays the full origin latency. A CDN with a 30% hit ratio is leaving most requests going to us-east-1 anyway — the goal is to maximize what's cacheable, not to assume the edge handles all traffic.

❌ "More hops always means slower."
✅ Not when a hop caches. A CDN adds a hop yet makes static content dramatically faster, because the edge cache serves it in ~10 ms instead of a ~200 ms origin trip. The right hops (edge caches, nearby replicas) reduce latency; only the wrong hops add it. Architecture is choosing which hops earn their keep.

❌ "The app sees the browser's IP directly behind a load balancer."
✅ It sees the load balancer's IP at the TCP layer. The real client IP survives only in X-Forwarded-For (or X-Real-IP), and only if the app is configured to trust and parse it. Forget this and your rate-limiting, geo-blocking, and audit logs all attribute every request to your own load balancer.

❌ "localhost and production take totally different network paths."
✅ The phases are identical — resolve, transport, (secure,) HTTP, process, return — and the application code is byte-for-byte the same. Production just inserts middlemen (LB, proxy, CDN) in front and adds TLS. The request your controller handles looks the same; what changed is everything before it reaches the controller. That's why "works locally, breaks in prod" is nearly always a middleman issue (a header, a cert, an SG), not an app-logic issue.

❌ "A 502 and a 504 are basically the same error."
✅ They point at different problems. 502 = the backend answered badly or closed early (it's broken). 504 = the backend didn't answer in time (it's slow). 503 = there was no healthy backend to ask. Treating them as interchangeable sends you debugging the wrong layer; the status code is the diagnosis (Part 9).
