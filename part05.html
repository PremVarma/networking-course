Ports & Sockets — Many Apps, One Address

Part 3 got your packet to the right machine. Part 4 made the delivery reliable. But the machine is running Spring Boot, PostgreSQL, Redis, a Kafka consumer, and an SSH (Secure Shell) session — simultaneously. When bytes arrive at the network card, which program gets them? This part answers that with two of the most-used, least-understood words in backend engineering: ports and sockets. By the end, server.port=8080, :5432 in a JDBC (Java Database Connectivity) URL, and "address already in use" will all be transparent to you.

1. Why ports exist — problem #6 finally gets its answer

Recall the ten problems from Part 1. Problem #6 was the "which app?" problem: a machine runs many programs at once — when data arrives at the machine, which program should receive it? Parts 3 and 4 gave us everything except that answer. An IP (Internet Protocol) address identifies a machine. Routing gets the packet to that machine. TCP (Transmission Control Protocol) guarantees the bytes arrive complete and in order. And then… the operating system is holding a handful of bytes addressed to 192.168.1.7 — a machine that is currently running a Spring Boot server, a PostgreSQL database, a Redis cache, a browser with forty tabs, and Spotify. Deliver the bytes to whom?

🧭 Why ports exist

An IP address is machine-grained, but communication is program-grained. Something must subdivide one machine address into many program-level addresses. That something is the port number: a 16-bit number carried in every TCP and UDP (User Datagram Protocol) segment that tells the receiving operating system which program's mailbox the data belongs in. IP gets the data to the right building; the port gets it to the right apartment.

It is worth pausing on what the world would look like without ports, because it makes the design obvious in retrospect. There are only two alternatives, and both are terrible:

  • One network program per machine. If the only address is the machine address, then only one program can "own" the network. Want to run a web server and a database? Buy a second computer. Your laptop could run the React dev server or the Spring Boot API — never both.
  • Every program sees all traffic. Alternatively, the OS (operating system) hands every arriving byte to every running program and lets them fight over it. Now every application must parse all traffic, discard what isn't theirs (how would they even know?), and trust every other app not to read its data. It is a privacy, performance, and correctness disaster.

Ports solve this with sixteen bits. The OS keeps a table — port number → program — and when a TCP segment arrives saying "destination port 5432," the kernel walks the table and delivers the payload to exactly one process: PostgreSQL. This act of sorting one inbound stream into many program-level streams is called demultiplexing, and the reverse (many programs sharing one network interface on the way out) is multiplexing.

🌍 Analogy — building address vs apartment number

Extend the postal analogy that has carried us since Part 1. The IP address is the street address of an apartment building: it gets the courier van (routing, Part 3) to the right front door anywhere on Earth. But "delivered to the building" is not "delivered." The envelope also carries an apartment number — the port — and the building's mailroom (the OS kernel) drops the letter into exactly one mailbox. Apartment 8080 is where the Spring Boot family lives; apartment 5432 is the PostgreSQL family; apartment 22 only opens for couriers with SSH (Secure Shell) credentials. Crucially, the courier company (IP, Layer 3) never reads apartment numbers — sorting mail inside the building is the building's own job (transport layer, Layer 4).

1.1 Why ports live at Layer 4, not Layer 3

This is a precision point that separates "memorized the OSI (Open Systems Interconnection) model" from "understood it" — and interviewers know that. Recall the division of labor from Parts 2 and 4:

  • Layer 3 (Network — IP) moves packets between machines across networks. Its job ends the moment the packet arrives at the destination host. The IP header contains source and destination IP addresses — and no port numbers at all. Routers, which are Layer 3 devices, forward billions of packets without ever knowing which application they belong to.
  • Layer 4 (Transport — TCP/UDP) delivers data between processes. It picks up where IP stops: at the front door of the host. The very first fields of both the TCP and UDP headers are source port and destination port, because process-level addressing is precisely the transport layer's mandate.

So "IP address + port" is not one address split in two for convenience — it is two addresses from two different layers, doing two different jobs: Layer 3 finds the host; Layer 4 demultiplexes within the host. This is also why a router can route your Spring-Boot-to-PostgreSQL traffic without understanding JDBC, and why NAT (Network Address Translation) devices — which do rewrite ports — are technically reaching up into Layer 4, a layer violation we flagged in Part 3.

📜 What came before

Ports are older than TCP itself. The ARPANET's (Advanced Research Projects Agency Network) original protocol, NCP (Network Control Program, 1970), already used numbered "sockets" to separate conversations on one host. When TCP/IP replaced NCP in 1983 (Part 1's "flag day"), the idea carried over as the 16-bit port. The early port assignments were literally a text file maintained by one man — Jon Postel, who for decades edited the "Assigned Numbers" RFC (Request for Comments) by hand. If you wanted a port for your new protocol, you emailed Jon. That informal list grew into today's registry run by IANA (Internet Assigned Numbers Authority), the same body that coordinates IP address allocation. The historical fingerprints are still visible: port 25 (SMTP — Simple Mail Transfer Protocol) was assigned in 1982, port 80 (HTTP — HyperText Transfer Protocol) in 1991 when a CERN physicist named Tim Berners-Lee asked for one. PostgreSQL's 5432 and Redis's 6379 are simply later entries in the very same ledger.

🟢 Beginner — say it simply

An IP address finds the right computer; a port number finds the right program on that computer. It is an apartment number written next to the building address. Without ports, one computer could only run one network program at a time.

🟡 Intermediate — the mechanics

Ports are 16-bit fields in the TCP/UDP header (Layer 4), not the IP header (Layer 3). The kernel keeps a mapping of (protocol, local IP, local port) → socket → process, and demultiplexes inbound segments by destination port. Routers never look at ports (except NAT middleboxes, which rewrite them — a deliberate layer violation).

🔴 Advanced — what experts know

"Which app gets the bytes" is resolved by a kernel lookup against bound sockets, with most-specific-wins semantics: a socket bound to a specific IP beats one bound to the wildcard address, and an established connection's full 4-tuple match beats any listener. That lookup order is the formal version of everything in sections 3–6 — and modern kernels add programmable steps to it (e.g. SO_REUSEPORT hashing across multiple listeners, eBPF socket-lookup hooks) that load balancers and service meshes (Parts 9, 13) exploit.

2. The mechanics — a 16-bit number and its three kingdoms

A port is not an object, a wire, or a process — it is literally just a number: an unsigned 16-bit integer, so 0 through 65,535. It exists in exactly one place: a field inside every TCP segment and UDP datagram. You met these headers in Part 4; zoom in on the first four bytes, which are the same for both protocols:

   the TCP segment your Spring Boot app sends to PostgreSQL:

   byte 0          byte 2          byte 4 …

   │  SOURCE PORT  │   DEST PORT   │  seq number, flags, window…  │
   │    51234      │     5432      │  (the rest of Part 4's       │
   │   (16 bits)   │   (16 bits)   │   TCP header)                │
   ├───────────────┴───────────────┴──────────────────────────────┤
   │  payload: the Postgres wire-protocol bytes (the SQL query)   │
   └──────────────────────────────────────────────────────────────┘

   the IP header wrapped around this (Part 2's encapsulation) has
   src/dst IP addresses — and NO ports. ports are Layer 4 property.

Sixteen bits, 65,536 possible values per protocol per machine — and note per protocol: TCP port 53 and UDP port 53 are different mailboxes that just share a number (DNS — Domain Name System — famously uses both, as we saw in Part 4). IANA divides the number line into three ranges, and each range has a personality you will recognize from daily work:

RangeNameWho uses itWhat you see in practice
0 – 1023Well-known / system portsStandardized server software: HTTP 80, HTTPS 443, SSH 22, SMTP 25, DNS 53Privileged: on Linux/macOS, binding requires root (or CAP_NET_BIND_SERVICE). This is THE reason your dev servers default to 8080/8000/3000 — they are the "no sudo required" echoes of 80.
1024 – 49151Registered portsVendor/application defaults registered with IANA: PostgreSQL 5432, MySQL 3306, Redis 6379, Kafka 9092, MongoDB 27017Anyone may bind them without privileges; registration just prevents two products claiming the same default. Your whole backend stack lives here.
49152 – 65535Dynamic / ephemeral portsOperating systems, automatically, for the client side of connectionsYou never configure these; the OS hands them out and reclaims them. Section 5 is all about them.
🧪 Real example — your OS's actual ephemeral range

The IANA ephemeral range is a recommendation; operating systems choose their own. Linux famously uses a wider one, and you can read it right now:

$ sysctl net.ipv4.ip_local_port_range
net.ipv4.ip_local_port_range = 32768	60999

$ cat /proc/sys/net/ipv4/ip_local_port_range
32768	60999

So a Linux box can source roughly 28,232 simultaneous outbound connections to one destination IP+port before exhausting client ports — a real ceiling that bites connection-hungry services (and one reason connection pools and keep-alive exist, Part 7). Windows since Vista uses 49152–65535, matching IANA.

📜 Why 1024 is the magic boundary

The privileged/unprivileged split at 1024 dates to 1980s multi-user Unix machines. On a shared university computer, dozens of users ran programs side by side. If any student could bind port 25, they could impersonate the mail server and read everyone's email. The fix: ports below 1024 may only be bound by root, so a connection to a low port "must" be talking to software the administrator blessed. The guarantee means little on your single-user laptop, but the rule survives — which is why mvn spring-boot:run with server.port=80 throws an access error on Linux while 8080 works, and why production setups put a load balancer or reverse proxy (Parts 9–10) on 80/443 and run your app on a high port behind it.

🔑 Key point

A port is just a 16-bit number in the Layer 4 header plus a kernel table entry saying which process claimed it. Nothing physical, nothing global — the same port number exists independently on every machine (and separately for TCP and UDP). "Port 8080" alone names nothing; 192.168.1.7:8080/TCP names exactly one mailbox in the universe.

3. Sockets and the 5-tuple — the great demolition

Now the centerpiece of this part — two definitions that engineers blur constantly:

🔑 Key point — socket vs connection

A socket is one endpoint of communication: the combination (IP address, port, protocol), materialized inside a program as a file-descriptor-like handle the OS gives you. A connection is a pair of endpoints in conversation, uniquely identified by the 5-tuple: {protocol, source IP, source port, destination IP, destination port}. The socket is one phone; the connection is the call — and the call is identified by both phone numbers, not one.

That last clause is the demolition charge. Place it carefully and ask the question every backend engineer eventually asks:

"My server listens on exactly one port — 443. How can it possibly hold 10,000 simultaneous client connections? Don't they collide?"

They never collide, because the kernel does not identify a connection by the server port. It identifies it by the entire 5-tuple. The server-side IP and port may be identical across all 10,000 connections — as long as each client brings a different source IP or source port, every tuple is unique, and the kernel can demultiplex perfectly. Watch three clients hit the same API server:

The kernel's view of those three conversations — three rows, all sharing the right-hand side, each row unique as a whole:

#ProtocolSource IPSource portDestination IPDestination portUnique?

When a segment arrives at the server, the kernel reads all four address fields (the protocol is implicit in the header type), looks up the exact tuple, and hands the bytes to the right connection's buffer. The server port being "shared" costs nothing — a call-center's single public number, with every caller still distinguishable.

🌍 Analogy — a letter thread needs BOTH full addresses

In the postal analogy: a socket is one apartment door (building + apartment number). A connection is an ongoing correspondence between two doors — and the mailroom files it under the pair of addresses. The customer-service desk in apartment 443 of the api.example.com building can run ten thousand simultaneous correspondences, because each incoming envelope carries a distinct return address (sender's building + sender's apartment). Two letters from the same building are still distinguishable — they come from apartments 51234 and 51235. Nobody ever needed the customer-service desk to move to a new apartment per customer; they just file by the full return address.

3.1 The corollary: the 65,535 "limit" is not where you think it is

Once the 5-tuple clicks, a famous myth collapses. People reason: "ports go up to 65,535, therefore a server maxes out at 65,535 connections." Wrong, and now you can see why: the server port is fixed across all connections, so it consumes nothing per client. The variability lives on the client side of the tuple. The real arithmetic:

  • Per client-source-IP, per destination: one client IP talking to one server IP:port can open at most ~65k connections (one per source port; ~28k with default Linux ephemeral range) — because only then does the tuple run out of room. This limit is about the client, not the server.
  • For the server: with clients spread across the Internet, the tuple space is effectively unbounded (every distinct client IP brings its own 65k source ports). Servers routinely hold millions of concurrent connections.
  • The real server limits are resources: every connection is a socket, every socket is a file descriptor (check ulimit -n, often a meager 1024 by default), plus kernel memory for buffers, plus whatever your application allocates per connection (a thread? 1 MB of stack? — this is why thread-per-connection Tomcat and event-loop Netty/Node scale so differently, next section).
# the actual ceilings on a Linux server, none of which is 65535:
$ ulimit -n                          # file descriptors per process
1024
$ sysctl fs.file-max                 # file descriptors, system-wide
fs.file-max = 9223372036854775807
$ sysctl net.core.somaxconn          # accept-queue depth cap (Part 4!)
net.core.somaxconn = 4096
🟢 Beginner — say it simply

A socket is one end of a conversation (an address + apartment number). A connection is identified by both ends together. That is why one server port can talk to thousands of clients at once — each client comes from a different address, so every conversation still looks different to the server.

🟡 Intermediate — the mechanics

Connection identity = 5-tuple {proto, src IP, src port, dst IP, dst port}. Inbound segments are matched against established tuples first, then against listeners. The 65,535 ceiling applies per {src IP → dst IP:port} pair (source-port exhaustion, a client-side problem); server capacity is bounded by file descriptors, memory, and per-connection application cost instead.

🔴 Advanced — what experts know

Source-port exhaustion is a real production incident pattern — but it strikes middleboxes and clients: a NAT gateway, an egress proxy, or a service making frantic short-lived connections to one upstream (each connection then burning a tuple slot for 60 s of TIME_WAIT, Part 4). Mitigations: connection pooling/keep-alive, widening ip_local_port_range, multiple source IPs, or SO_REUSEADDR/timestamp-based TIME_WAIT reuse. Interviewers love "what actually limits concurrent connections?" precisely because the naive 65k answer is one tuple-field wide of the truth.

4. Two kinds of socket: the listener and the worker

Here is the subtlety hiding inside every server you have ever started: a server does not use one socket — it uses one listening socket plus one connection socket per client. The lifecycle is a fixed three-step ritual that every server on Earth performs, whether it is Tomcat, PostgreSQL, Redis, or a Kafka broker:

  1. bind — the process claims a local (IP, port): "I am taking 0.0.0.0:8080." The kernel checks nobody else holds it (this is where BindException is born, section 6).
  2. listen — the socket is switched into passive mode: it will never send data; its only job is to receive connection attempts (TCP SYN — synchronize — segments, Part 4) and queue completed handshakes in the accept queue (the backlog you met in Part 4).
  3. accept — the application pulls one completed connection off the queue, and the kernel hands it a brand-new socket dedicated to that one client. The listening socket is untouched and keeps listening. Repeat forever.

   └────────────┬────────────┘          └────────────────────────────┘

This is why ss (socket statistics, the modern Linux tool) shows a server twice — once in LISTEN state and once per client in ESTAB — all on the same port. They are different sockets: new SYNs go to the listener; data for existing conversations goes straight to the right worker socket.

🌍 Analogy — the restaurant host stand

The listening socket is the host stand at a restaurant's front door. The host never serves food. When guests arrive (SYN), the host checks them in (handshake), and if no table is free yet they wait in the entryway (the accept queue / backlog — and if the entryway fills, newcomers are turned away at the door, which is exactly the connection-refused-under-load behavior from Part 4). accept() is the moment a waiter seats the party at their own table (a new connection socket) and serves only them. One host stand, many tables — one listener on 8080, many established sockets on 8080.

4.1 How your frameworks actually do this

  • Tomcat (your Spring Boot default) — a dedicated acceptor thread sits in an accept() loop on the listener; each new connection socket is handed to a worker pool (default server.tomcat.threads.max=200). Two hundred workers ⇒ roughly two hundred requests in flight; when a service "hangs under load," suspect an exhausted worker pool or a full accept queue, never a "full port."
  • Netty / Node.js / FastAPI(uvicorn) — the event-loop family. One or a few threads watch thousands of connection sockets at once using readiness notification (epoll on Linux): "wake me when any of these sockets has data." Many sockets, few threads — how one Node process on port 3000 holds 50,000 idle WebSocket connections.
  • PostgreSQL — old-school and proud: the postmaster listens on 5432 and forks a whole process per connection. Each Postgres connection costs megabytes of server memory — the networking-level reason connection pools (HikariCP in Spring Boot, default 10) exist.
🟢 Beginner — say it simply

A server has one special "front door" socket that only accepts new visitors, and it creates a private socket for each visitor it lets in. The front door never closes and never talks — it just keeps letting people in while the private conversations happen at their own tables.

🟡 Intermediate — the mechanics

bind() claims (IP, port); listen() makes it passive with a backlog (accept queue); accept() dequeues a completed handshake and returns a new connected socket bound to the same local port but a distinct remote tuple. Frameworks differ in what happens next: thread-per-connection (Tomcat workers, Postgres fork) vs event loop multiplexing thousands of sockets per thread (Netty, Node, uvicorn).

🔴 Advanced — what experts know

The accept path itself becomes a bottleneck at extreme connection-churn rates: a single acceptor thread serializes all accepts. SO_REUSEPORT lets N processes each bind their own listener on the same port and lets the kernel hash incoming handshakes across them — used by NGINX, Envoy, and HAProxy for multi-core accept scaling and for zero-downtime reloads (start new workers, drain old ones, same port the whole time). Distinguish this sharply from SO_REUSEADDR, which merely permits rebinding a port still occupied by TIME_WAIT ghosts (Part 4) — the thing that makes "restart the app immediately" work.

5. Client ports vs server ports — fixed meets ephemeral

Every connection has two ports, and they are chosen by completely different logic:

  • The server port is fixed and famous. A server must be discoverable: clients have to know where to knock before any communication exists. So servers bind well-known, configured, documented ports — 443, 5432, 6379, 9092 — published in config files, connection strings, and IANA's registry. A server on a random port is a doorbell with no label.
  • The client port is ephemeral and anonymous. The client needs some port — the reply has to land somewhere — but nobody needs to know it in advance; it travels inside every segment the client sends (the source-port field), so the server just reads it. The OS auto-assigns one from the ephemeral range at connect time and reclaims it after the connection dies.

🌍 Analogy — the return address, and the concierge who rewrites it

The server's port is a storefront address printed on every ad — fixed, public, memorable. Your ephemeral port is the return address scribbled on your envelope — it only needs to be valid for the duration of the correspondence, and the post office (your OS) assigns you a temporary PO box for it. Now the Part 3 callback: your home router's NAT is a concierge who, for mail leaving the building, may cross out your return address and substitute the building's public one — including a different apartment number it chose, noting the substitution in its ledger. So the server may see 49.36.181.40:30412 when your laptop sent from 192.168.1.7:51234. Replies hit the concierge, the ledger translates back, and your laptop never knows.

🔑 Key point

Fixed server ports answer "where do I knock?" (discoverability); ephemeral client ports answer "where do replies land?" (return addressing) — and the OS automates the second completely. When you write spring.data.redis.port=6379 you are configuring the destination; the source port of every connection in your Redis pool was picked by the kernel.

6. Binding addresses — the gotcha factory

When a server binds, it claims a port on one or more IP addresses — and that second half is the most underrated source of "it doesn't work" in backend development. Your machine has several IP addresses (Part 3): at minimum the loopback 127.0.0.1 and a LAN (Local Area Network) address like 192.168.1.7; servers add more. Binding decides which doors the listener actually watches:

Where you set this in your stack — note every framework has the knob, with different defaults:

# Spring Boot — application.properties (default address is 0.0.0.0)

# PostgreSQL — postgresql.conf (default: localhost only!)

# Redis — redis.conf ships bound to loopback, on purpose
bind 127.0.0.1 ::1
🔑 Key point — the "works on my machine, dies in Docker" flag

Plant this flag for Part 12: when an app inside a container binds 127.0.0.1, "this machine" means the container — its private loopback, unreachable even from your own laptop one layer outside. The app works when you run it directly (you and it share a loopback) and goes dark in Docker (you no longer do). Uvicorn's loopback default makes FastAPI the classic victim: docker run -p 8000:8000 myapi + connection reset = check the --host. The full mechanics of Docker's network namespaces and port publishing arrive in Part 12; until then, the rule of thumb is absolute: in a container, bind 0.0.0.0.

One more rule the kernel enforces at bind time: one port, one owner (per protocol, per address). If anything already holds 8080, your bind fails instantly — Java's BindException, C's EADDRINUSE ("error: address in use"). You have seen it; now debug it like a professional on both operating systems:

80 — HTTP. The port Tim Berners-Lee registered for the web. Today it is mostly a polite greeter: production sites keep 80 open only to answer 301 Moved Permanently → https://…. When a load balancer health-checks your pod with a plain HTTP probe, this is the world it lives in. Part 7 dissects the protocol itself.

443 — HTTPS. Same HTTP conversation, wrapped in TLS encryption first. Hold this thought: nothing about the number 443 encrypts anything — encryption comes from the TLS handshake (Part 8); 443 is merely the agreed meeting point where clients expect TLS to be spoken. You could serve TLS on 8443 (Tomcat's classic alternative) or plaintext on 443; convention, not physics.

22 — SSH. Your remote terminal, but also more of your daily life than you think: git push origin main over an SSH remote is a TCP connection to port 22 of GitHub (git@github.com), authenticated by your SSH key. scp, sftp, Ansible, and most CI (Continuous Integration) deploy steps ride the same port.

25 — SMTP. The protocol mail servers use to hand mail to each other. Spammers abused home machines as mail cannons so thoroughly that most consumer ISPs (Internet Service Providers) block outbound port 25 entirely — which is why your Spring Boot app sends mail via an email API over 443, or via SMTP submission on port 587 (STARTTLS upgrade) or 465 (implicit TLS from the first byte) with authentication. Three ports, one protocol family: 25 = server↔server transfer, 587/465 = authenticated client submission.

53 — DNS. The port your machine queries hundreds of times an hour to turn names into IP addresses. Part 4's UDP-vs-TCP discussion plays out here in miniature: small queries ride UDP (one packet out, one back, no handshake tax); large responses and zone transfers fall back to TCP on the very same port number. How those lookups actually resolve is the entire subject of Part 6 — next door.

3306 — MySQL and 5432 — PostgreSQL. The two relational defaults. Nothing magical happened at registration time — these are just the numbers the projects asked IANA for (5432 was chosen at Berkeley partly because it was free and partly because it riffs on "PGSQL" phone-keypad lore). Every JDBC URL you have ever written embeds one of them, and section 8 dissects one character by character.

6379 — Redis. Famously derived from the keypad spelling of "MERZ" — an Italian-TV in-joke by Redis's author. The protocol behind it (RESP) is so simple it doubles as this course's first complete Layer 7 protocol demo, in section 8.

9092 — Kafka. The broker's client port — and uniquely among these nine, connecting to it is only step one of a two-step dance involving metadata and redirection that confuses every engineer's first Docker compose file. Section 8 gives it the full treatment.

🔑 Key point

Defaults below 1024 belong to the standardized Internet (80, 443, 22, 25, 53) and need privileges to bind; your backend stack's defaults (5432, 6379, 9092, 8080…) live in the registered range precisely so an ordinary process can claim them. Every docker run -p 5433:5432 you have ever typed is this sentence in command form.

8. Your stack, port by port — four walkthroughs

Theory done. Now run the four pillars of your actual stack through everything this part built: Spring Boot serving, PostgreSQL answering queries, Redis caching, Kafka streaming. For each: the config you write, and precisely what happens at startup.

8.1 Spring Boot — what server.port=8080 actually does

# application.properties
server.port=8080
# (implicitly: server.address=0.0.0.0 — all interfaces)

At startup, Spring Boot's embedded Tomcat performs exactly the ritual from section 4: it asks the kernel to bind 0.0.0.0:8080, switches the socket to listen with an accept queue (default backlog 100, knob: server.tomcat.accept-count), starts its acceptor thread, and logs the line you have read a thousand times without seeing it:

2026-06-12T10:14:03.118  INFO 31337 --- [main] o.s.b.w.embedded.tomcat.TomcatWebServer :
    Tomcat initialized with port(s): 8080 (http)
2026-06-12T10:14:05.842  INFO 31337 --- [main] o.s.b.w.embedded.tomcat.TomcatWebServer :
    Tomcat started on port(s): 8080 (http) with context path ''

From that moment, ss -tlnp shows a LISTEN row owned by your JVM (Java Virtual Machine), and every request from your React app mints a new connection socket served by a worker thread. Changing the port is one property (server.port=8081), a flag (--server.port=8081), or an environment variable (SERVER_PORT=8081) — and server.port=0 asks the OS for any free port, which is exactly what @SpringBootTest(webEnvironment = RANDOM_PORT) uses so parallel CI test suites never collide.

Now start a second instance while the first is running, and section 6's one-owner rule fires as the most readable error message Spring ever produced:

***************************
APPLICATION FAILED TO START
***************************

Description:

Web server failed to start. Port 8080 was already in use.

Action:

Identify and stop the process that's listening on port 8080 or configure this
application to listen on another port.

So two instances need two ports (8080, 8081) — and immediately a new problem is born: clients knew one address. Who tells them about the second? Spreading clients across many instances behind one stable address is precisely what a load balancer does, and that is Part 9's opening scene.

8.2 PostgreSQL — dissecting the JDBC URL you paste without reading

8.3 Redis — the simplest Layer 7 protocol you will ever read

# application.properties
spring.data.redis.host=cache.internal.example.com
spring.data.redis.port=6379

Same shape as Postgres: name + port → DNS → TCP handshake → speak the protocol. But Redis's protocol (RESP) is so human-readable that you can perform the whole stack by hand and watch every layer of Parts 1–5 cooperate in two lines:

$ redis-cli -h cache.internal.example.com -p 6379 PING
PONG

$ redis-cli -h cache.internal.example.com -p 6379 SET user:42:session "abc123" EX 1800
OK

That PING/PONG is the entire round trip: name resolved, TCP connection to port 6379 established, four bytes of application protocol sent, four bytes returned. When your Spring Boot service feels slow and you suspect the cache, this one-liner is the fastest possible "is Redis up, reachable, and answering?" probe — it tests DNS, routing, the port, the bind address, the firewall, and the server process in a single command.

8.4 Kafka — bootstrap is only the introduction

Kafka looks like the others for exactly one config line — then takes a turn:

# application.properties
spring.kafka.bootstrap-servers=broker1.internal.example.com:9092

Here is the twist: bootstrap servers are not "the" connection — they are the introduction. A Kafka cluster has many brokers, and your topic's partitions are spread across them with one broker leading each partition. A producer must talk directly to each partition's leader. So the client's first connection to broker1:9092 exists mainly to ask one question: "who is in this cluster, and where do I reach them?" The broker answers with cluster metadata — a list of every broker's advertised address — and the client then opens new, direct connections to whichever brokers it actually needs:

Fig 5.7 — Kafka's two-step: bootstrap, then direct connections from metadata
   YOUR SPRING BOOT PRODUCER                    KAFKA CLUSTER
        │
        │  ① TCP connect: broker1:9092          ┌─────────────────┐
        ├──────────────────────────────────────►│ broker1  :9092  │
        │  ② "metadata, please"                 └────────┬────────┘
        │  ③ reply — the cluster roster:                 │
        │     broker1.internal.example.com:9092          │ (what each broker
        │     broker2.internal.example.com:9092          │  ADVERTISES is
        │     broker3.internal.example.com:9092          │  configured, not
        │ ◄───────────────────────────────────           │  discovered!)
        │
        │  ④ NEW direct connections to the partition leaders it needs:
        ├──────────────────────────────────────► broker2:9092
        └──────────────────────────────────────► broker3:9092

   the addresses in step ③ come from each broker's advertised.listeners
   config — the broker tells clients where it THINKS it is reachable

The addresses in step ③ are not detected — each broker simply repeats its configured advertised.listeners value. The broker is telling clients where it believes it can be reached, and if that belief is wrong, clients fail in a maddeningly specific way: bootstrap works, metadata arrives, and then the follow-up connections dial a wrong number.

🧪 Real example — the legendary Docker gotcha

You run a broker in a container with advertised.listeners=PLAINTEXT://localhost:9092 (or leave a default that resolves that way). From your laptop: bootstrap to localhost:9092 succeeds (the port is published), metadata returns "reach me at localhost:9092" — and by luck that string is also correct from the laptop's perspective, so everything works. Now your Spring Boot app runs in its own container: it bootstraps fine via the compose-network name kafka:9092… receives metadata saying "localhost:9092"… and obediently connects to its own container's loopback, where no broker lives. Connection refused, forever, despite bootstrap visibly succeeding. The fix is conceptually one line — advertise an address clients can resolve and reach (advertised.listeners=PLAINTEXT://kafka:9092) — and the full multi-listener pattern (INTERNAL/EXTERNAL listeners on separate ports) gets its complete resolution in Part 12, where Docker networking finally makes the whole failure obvious.

🌍 Analogy — the switchboard that reads you the staff directory

Bootstrapping Kafka is calling a company's front desk: one published number (the bootstrap address), and the receptionist's only real job is reading you the directory — "Sales is extension 9092 at the Pune building, Engineering is 9092 at the Mumbai building." From then on you dial people directly. Now the gotcha in analogy form: the directory entries are self-reported. If the Mumbai engineer wrote "reach me at: my desk" in the directory, that works for someone standing at his desk and strands everyone else. advertised.listeners is the broker's directory entry — it must be written from the caller's point of view, not the broker's.

9. URLs and implied ports — why you never type :443

You have never typed https://github.com:443, yet that connection went to port 443. Every URL (Uniform Resource Locator) scheme carries a default port, and clients silently fill it in when you omit one. That is the entire trick — the port is always there; conventions just let it go without saying:

SchemeDefault portSo this URL……actually means
http://80http://example.com/apiexample.com:80
https://443https://api.github.com/reposapi.github.com:443
postgres:// (and jdbc:postgresql://)5432postgres://db.internal/ordersdb.internal:5432
redis://6379redis://cache.internalcache.internal:6379
ssh:// (and git@host: remotes)22git@github.com:you/repo.gitgithub.com:22

Dev URLs spell the port out — http://localhost:8080/actuator/health, http://localhost:3000, http://localhost:5173 — for exactly the reason section 2 gave: your dev servers sit on unprivileged stand-ins for 80, so the default would point at the wrong door. Deploy behind a load balancer terminating 443 (Parts 8–9) and the explicit port disappears again — you moved to the address the scheme assumes. One more everyday sighting: a React dev setup proxying /api to http://localhost:8080 is just two implied-vs-explicit URLs glued together — browser → :3000 (explicit, unprivileged), proxy → :8080 (explicit), production → :443 (implied).

🔑 Key point

"No port in the URL" never means "no port in the connection." Every TCP connection in existence has both ports filled in (the header fields are not optional, Fig 5.2). Schemes are a lookup table from protocol name to default destination port — clients consult it; the network never sees the scheme at all.

10. Firewalls and what "opening a port" really means

Ops says "we opened port 8080 for you." Nothing was opened — no hatch, no valve. A firewall is a packet filter: it inspects each packet's addresses and ports against a rule list and either forwards or drops it. "Opening port 8080" means adding a rule: allow inbound TCP segments whose destination port is 8080 (in particular the SYN that starts a handshake — Part 4) to reach the host. "Closed" means such packets are dropped (silence — the client times out) or rejected (an active refusal — the client gets "connection refused" instantly). The distinction matters when debugging: instant refusal usually means reachable host, nobody listening (or a reject rule); a long hang usually means a drop rule or no route.

Note the layering of defenses — both fences exist independently:

  • OS / host firewall — rules enforced by the machine itself: ufw/nftables on Linux, Windows Defender Firewall (the dialog that pops up the first time java.exe listens on a new port — that prompt is literally asking permission to add an allow rule).
  • Network firewall — rules enforced before traffic reaches the machine: your office perimeter, your home router (which, via NAT, drops unsolicited inbound by default — Part 3), and in the cloud, AWS Security Groups (Amazon Web Services), which are per-instance allow lists. Part 11 builds on this with the canonical production pattern: allow TCP 8080 only from the load balancer's security group, allow 5432 only from the app tier — port rules as architecture.
🌍 Analogy — the gate guard with a visitor list

Back to the apartment building: the firewall is the compound's gate guard. "Opening apartment 8080 to visitors" does not unlock the apartment — it adds a line to the guard's clipboard: visitors for apartment 8080 may enter the compound. The apartment door still needs someone home (a listening process) and the building mailroom (the OS) still routes by apartment number. Three independent reasons a visitor fails: turned away at the gate (firewall), wrong building (IP/routing), nobody answers the door (no listener). Debugging connectivity is figuring out which of the three happened — and the toolbox below is how.

12. Interview questions

🎤 Try answering out loud before you click
A server listens on a single port. How can it serve thousands of simultaneous connections?

Because connections are identified by the full 5-tuple {protocol, source IP, source port, destination IP, destination port}, not by the server port alone. Each client arrives from a distinct source IP:port, so every tuple is unique even though the destination side is identical across all of them; the kernel demultiplexes inbound segments by exact tuple match. Strong answers add the mechanism: the listening socket accepts handshakes, and each accept() returns a new connected socket sharing the same local port — so it is one listener plus N connection sockets, bounded by file descriptors and memory, not by port arithmetic.

Why can't two processes bind the same port? Are there exceptions?

Binding registers (protocol, local address, port) exclusively in the kernel, because inbound demultiplexing needs a single unambiguous owner — two owners of TCP 0.0.0.0:8080 would make "who gets this SYN?" undefined. Hence EADDRINUSE/BindException. Nuances that mark a senior answer: TCP 8080 and UDP 8080 coexist (different protocols); SO_REUSEADDR permits rebinding over TIME_WAIT remnants; and SO_REUSEPORT deliberately allows multiple sockets on the identical address:port, with the kernel load-balancing incoming connections across them — used by NGINX/Envoy for multi-core accept scaling and zero-downtime reloads.

What is an ephemeral port, who assigns it, and when?

The temporary source port the operating system auto-assigns to the client side of a connection at connect() time, from a configured range (IANA suggests 49152–65535; Linux defaults to 32768–60999 via net.ipv4.ip_local_port_range). It exists so replies have a return address; it needs no pre-agreement because it travels in every segment's source-port field. It is released when the connection closes (after TIME_WAIT). Consequence worth volunteering: ~28–65k concurrent connections per client IP to one destination — source-port exhaustion.

What is the difference between binding to 0.0.0.0 and 127.0.0.1?

The bind address selects which interfaces the listener accepts traffic from. 127.0.0.1 binds only the loopback — reachable solely by processes on the same host (or same container; in Docker "the host" means the container's own namespace). 0.0.0.0 is the wildcard: all current and future IPv4 interfaces, so anyone who can route to any of the machine's addresses can connect, subject to firewalls. Production framing: loopback binds are blast-radius reduction for local-only services; wildcard binds are for anything that must serve others — and inside containers you essentially always bind 0.0.0.0, because the container's loopback is invisible from outside.

Walk me through exactly what happens when Spring Boot starts on port 8080.

Embedded Tomcat asks the kernel to bind TCP 0.0.0.0:8080 (configurable via server.port / server.address); if another process owns it, startup aborts with "Port 8080 was already in use." On success it calls listen with a backlog (server.tomcat.accept-count, default 100), creating the accept queue, and logs "Tomcat started on port(s): 8080." An acceptor thread loops on accept(); each completed three-way handshake yields a new connection socket, which is handed to a worker thread from the pool (default max 200) that parses HTTP and invokes your controllers. So at steady state: one LISTEN socket plus one ESTABLISHED socket per in-flight client, all showing port 8080 in ss.

Why does Kafka need advertised listeners? Why isn't bootstrap.servers enough?

Because the bootstrap connection is only used to fetch cluster metadata; real traffic flows over direct connections from the client to each relevant broker (each partition has a leader broker the client must reach). The metadata contains addresses the brokers advertise — the configured advertised.listeners — not addresses clients discovered. If a broker advertises an address unresolvable or unreachable from the client's network position (the classic: localhost:9092 from inside Docker), bootstrap succeeds yet all subsequent connections fail. It also explains why a plain TCP load balancer in front of Kafka brokers breaks the protocol: clients need to reach specific brokers, not "any broker."

Socket vs port vs connection — define all three precisely.

A port is a 16-bit number in the TCP/UDP header identifying a program-level mailbox on a host. A socket is one communication endpoint — (IP, port, protocol) — materialized as a file descriptor a process reads and writes. A connection is a pair of endpoints in conversation, identified by the 5-tuple; on a server it corresponds to a connected socket distinct from the listening socket. The hierarchy: ports are names, sockets are objects holding those names, connections are relationships between two sockets.

Is the number of connections a server can handle limited to 65,535?

No. 65,535 is the port-number space, and the server's port is fixed across all its connections — it consumes no per-client resource. The tuple space allows ~65k connections per client source IP to one destination, so the aggregate across many clients is effectively unbounded. Real server limits: file descriptors (ulimit -n), kernel and application memory per connection, accept-queue depth, and the concurrency model (thread-per-connection vs event loop). Production systems hold millions of concurrent connections per machine.

What does "opening port 8080 on the firewall" technically do?

It adds a filter rule permitting inbound packets with destination TCP port 8080 — crucially the SYN segments that initiate handshakes — to pass; without it they are dropped (timeout) or rejected (instant refusal). It does not start a listener or change the host: a packet must still pass the host firewall and find a bound socket. In AWS terms it is a security-group ingress rule — production rules also scope the source (allow 8080 only from the load balancer's security group).

13. Common misconceptions

❌ Myths engineers actually believe

❌ "Each new client connection consumes another port on the server."
✅ All connections to a server share its one listening port; uniqueness comes from the client side of the 5-tuple. A new connection costs the server a socket (a file descriptor + memory), never a port number. The ephemeral-port meter runs on the client.

❌ "Ports are physical things on the machine."
✅ The RJ45 jack on a switch is a physical port; a TCP port is not. It is a 16-bit field in a header plus a kernel table entry mapping the number to a process. Nothing exists at "port 8080" until a process binds it, and the same number exists independently on every machine, separately for TCP and UDP.

❌ "Port 443 traffic is encrypted because it's port 443."
✅ Numbers encrypt nothing. Encryption comes from TLS, negotiated by the endpoints (Part 8); 443 is merely the conventional meeting place where clients expect TLS. You can serve TLS on 8443 or plaintext on 443. Likewise an "open port 22" is only as secure as the SSH daemon behind it.

❌ "A server can have at most 65,535 connections."
✅ That number is the port space, and the server's port is shared by all connections. The ~65k ceiling applies per client-source-IP to one destination (source-port exhaustion). Server capacity is governed by file descriptors, memory, and the concurrency model — millions of concurrent connections per box is routine.

❌ "We bound it to 127.0.0.1, so it's secured."
✅ Loopback binding is reachability control, not authentication. Every process and user on that host (and anything sharing the network namespace) connects freely, no password asked. It shrinks exposure — good! — but a Redis with no AUTH on 127.0.0.1 is still wide open to everything local. Security needs authentication, authorization, and encryption on top.

❌ "EXPOSE 8080 in the Dockerfile opens the port."
✅ EXPOSE is documentation — metadata declaring intent. It neither binds, publishes, nor opens anything. Reaching a container from outside requires publishing (-p 8080:8080) and the app binding 0.0.0.0 inside. Part 12 untangles the full chain (namespace → publish → host firewall).

❌ "IP routes packets to the right application."
✅ IP's contract ends at the host (Layer 3); it carries no port fields at all. Application delivery is the transport layer demultiplexing by port inside the host (Layer 4). That split is why routers never know which app traffic belongs to — and why NAT, which rewrites ports, is a celebrated layer violation.

🔗 How this connects

Looking back: Part 4 gave you TCP's reliable byte pipe between two machines; this part finished the delivery — ports demultiplex that pipe to the right process, sockets are the endpoints your code holds, and the 5-tuple is why one port serves thousands of clients. You can now read every field of 192.168.1.7:51234 → 203.0.113.10:443 and say who chose it and when. Looking forward: one mystery remains in every connection string you have seen today: db.internal.example.com, cache.internal, broker1:9092 — names, not addresses. Before any handshake in this part could begin, something translated those names into IPs, billions of times a day, in milliseconds, without a central server melting down. That something is the Internet's phone book — and how names become IPs is Part 6 — DNS.
