Java Multithreading & Concurrency

Complete Edition — Zero to Hero. Every topic, real production examples, interview-ready.

This is the only Java concurrency guide you'll need. We start from "what is a thread" and end at virtual threads, structured concurrency, and senior-level interview questions. Examples come from real systems — payment APIs, web scrapers, connection pools, circuit breakers — not toy demos.

Part 0 — Mental Models & Glossary

Read this first

What is this section and why does it exist?

Concurrency uses a lot of weird vocabulary — "monitor", "happens-before", "CAS", "backpressure". Most tutorials assume you know these words. This section assumes you don't. We'll build mental pictures and define every term in plain English. Then the rest of the guide will feel familiar instead of intimidating.

You don't need to memorize everything here. Skim it once. Come back when you hit a confusing word later.

0.1 Why concurrency is hard (and why that's normal)

Programming a single thread is like cooking alone in your kitchen. You do step 1, then step 2, then step 3. If step 2 messes up, you know exactly why — you were the only one there.

Programming with threads is like cooking with 3 friends in the same kitchen, all blindfolded. You can't see what they're doing. They can't see you. Sometimes you both reach for the salt at the same instant. Sometimes friend B reads the recipe while friend A is mid-edit. Sometimes the dish is ruined and nobody knows whose move broke it.

That's concurrency. And here's the brutal part: most concurrency bugs don't appear when you test. They appear in production, at 3am, on a Tuesday, once every 50,000 requests, and you can never reproduce them on your laptop.

The real promise of this guide

By the end, you won't have memorized every API. You'll have built intuitions: "this code looks dangerous because two threads are touching the same variable", "this needs a queue between the producer and consumer", "this lock is held for too long". Those intuitions are what separate junior from senior engineers.

0.2 Five mental models that unlock everything

Model 1: A thread is a worker; the heap is a shared whiteboard

Imagine a room full of workers (threads). In the middle of the room is a giant whiteboard (the heap). Each worker has their own private notepad (their stack) — others can't see it. But the whiteboard is shared. Anyone can erase or rewrite anything on it.

Question to keep asking yourself as you code: "Which of my variables are on private notepads, and which are on the shared whiteboard?" The whiteboard variables need rules. The notepad ones don't.

Model 2: The OS can pause your thread between any two instructions

Even a tiny line like count = count + 1 is actually three machine steps: read, add, write. The operating system is allowed to freeze your thread between any two of those steps and run somebody else.

So when you write count++, you should mentally read it as: "read count from the whiteboard. (another worker might do something here) Add one. (another worker might do something here) Write back to the whiteboard."

If you don't trust this assumption, you'll write code that "works on my laptop" and breaks in production.

Model 3: A lock is a key on a single bathroom door

You have a one-person bathroom (a critical section). There's one key. To enter, you grab the key. While you're inside, nobody else can enter — they wait outside. When you leave, you put the key back, and one of the waiters grabs it.

That's exactly what synchronized and Lock do. The key is the lock. The bathroom is the code inside the synchronized block.

Why this matters: if you stay in the bathroom for an hour, everyone waits an hour. So always make critical sections small and fast. Never call slow things (like a database) while holding a lock.

Model 4: Threads have private cached views of the whiteboard

Real CPUs are tricky. When worker A writes x = 5 on the whiteboard, worker B doesn't always see it instantly. B might have a photo of the whiteboard from 2 seconds ago in their pocket and keep reading from the photo.

This is called a visibility problem. We solve it by occasionally forcing workers to refresh their view — using volatile, locks, or atomics. (Don't worry about exactly how yet — we'll cover it.)

Why does it work this way? Because if every write went straight to RAM and every read went to RAM, your laptop would be 100× slower. CPUs trade some "freshness" for huge speed.

Model 5: Don't share state — pass messages

The single best way to avoid concurrency bugs is to not have shared state in the first place. Two patterns help:

  • Immutable data: once created, can't be changed. Multiple threads can read it freely — no conflict possible. (Java records, List.of(), etc.)
  • Queues: instead of two threads editing the same list, one thread puts messages into a queue, another thread takes them out. The queue handles all the coordination. You write straight-line code on either side.

Whenever you can choose between "share a variable carefully" and "send a message through a queue" — pick the queue. Future-you will thank present-you.

Part 1 — Foundations

Why this part

What you'll learn

The vocabulary and mental picture every Java developer needs: what a thread really is, how the OS juggles threads on a small number of CPU cores, and the lifecycle a thread goes through from "just created" to "finished".

Why it matters

If you skip this, every later concept ("the OS may pause your thread between any two instructions") sounds like magic. Spend 15 minutes here and the next 25 parts feel natural.

1.1 Process vs Thread

A process is a running program. The OS gives it its own private memory: heap (objects), stack (local variables per thread), code, and data. When you run java MyApp, the OS creates a process and loads the JVM into it.

A thread is a unit of execution inside a process. A process can have many threads, and they share the same heap — but each has its own stack and program counter.

┌─────────── PROCESS (JVM) ───────────┐ │ │ │ ┌───── HEAP (shared) ─────┐ │ │ │ User objects, caches │ │ │ │ static fields │ │ │ └─────────────────────────┘ │ │ │ │ Thread-1 Thread-2 Thread-3 │ │ ┌─────┐ ┌─────┐ ┌─────┐ │ │ │stack│ │stack│ │stack│ │ ← each thread has its own │ │ pc │ │ pc │ │ pc │ │ │ └─────┘ └─────┘ └─────┘ │ │ │ └─────────────────────────────────────┘
Analogy

A restaurant is a process. The kitchen, fridge, and ingredients = shared heap. Each chef is a thread with their own cutting board (stack) and recipe-step they're on (program counter). Two restaurants (processes) can't grab each other's ingredients without explicit delivery (IPC).

Deep insight

"Threads share memory" is both Java's killer feature and the root of every concurrency bug. The whole rest of this guide is essentially: "how do we share memory without losing our minds?"

1.2 Why Multithreading?

Three reasons, each from a real system:

1. Responsiveness

Your phone's banking app shows "Loading..." while fetching the balance. The UI thread keeps the spinner spinning while a worker thread does the network call. Without threads, the screen would freeze.

2. Throughput

A typical Spring Boot REST API runs on Tomcat which has a thread pool of ~200 worker threads. When 10,000 users hit your endpoint simultaneously, ~200 are processed in parallel; the rest queue. Single-threaded? You'd serve one request at a time.

3. CPU utilisation

Your laptop has 8 cores. A single-threaded program uses 12.5% of the CPU max. A video encoder that spawns 8 threads uses ~100%. That's an 8× speedup — for free.

Real case: Netflix

Netflix's video encoding farm uses thousands of machines, each running parallel chunks of a movie. A 2-hour movie is split into 1000 chunks; each chunk encoded by a thread on a worker. Encoding goes from days to minutes. Without multithreading, Netflix wouldn't scale.

1.3 CPU Scheduling — what's really happening

You usually have more threads than CPU cores. The OS scheduler does preemptive time-slicing — it gives each thread a few ms (typically 10–100ms), pauses it (a "context switch"), and runs another.

Timeline (Core 1): [T1 10ms][T2 10ms][T1 10ms][T3 10ms][T1 10ms][T2 10ms]... ↑ context switch: kernel saves T1 registers, loads T2 registers, jumps to T2's PC Timeline (Core 2): [T4 10ms][T5 10ms][T4 10ms][T5 10ms][T4 10ms][T6 10ms]...

A context switch costs ~1–10µs. Sounds tiny, but at 10,000 threads doing nothing useful, you can spend most of your CPU just switching. This is why "more threads = faster" is wrong past a point.

Mental model

Assume the OS can pause your thread between any two bytecode instructions. Even a single line like x = x + 1 can be interrupted halfway. Code that doesn't survive that assumption is buggy.

Common confusion

RUNNABLE in Java means "ready or running" — the JVM doesn't expose whether a thread is currently on a CPU. Don't trust state for fine-grained debugging — use thread dumps (Part 24).

1.5 Daemon Threads

Threads come in two flavours:

  • User threads (default) — JVM waits for them to finish before exiting.
  • Daemon threads — JVM exits when only daemons remain. Used for background work (GC, JIT, monitoring).
Thread t = new Thread(() -> {
    while (true) {
        flushMetrics();
        Thread.sleep(1000);
    }
});
t.setDaemon(true);   // must be set BEFORE start()
t.start();
Watch out

Daemons are killed abruptly when the JVM exits — no finally blocks guaranteed, no graceful cleanup. Don't use them for work that must complete (writing files, flushing buffers).

Part 2 — Creating Threads

Why this part

What you'll learn

The four ways Java lets you start a new thread, and which one is the right answer in real production code (spoiler: not the one most tutorials show).

Why it matters

Most beginner code uses new Thread().start() — and most production code never does. Understanding why will save you from the most common scaling and stability bugs in Java backends.

Java gives you four ways to create threads. We'll cover all of them, when to use each, and why three of them are wrong for production.

2.1 Way #1 — Extend Thread (rarely correct)

class PrinterThread extends Thread {
    private final String msg;
    public PrinterThread(String msg) { this.msg = msg; }

    @Override
    public void run() {
        System.out.println("[" + getName() + "] " + msg);
    }
}

new PrinterThread("hello").start();
Why this is bad
  • Java has single inheritance — extending Thread burns your one extension slot.
  • Couples "what to do" with "how to run it". You can't easily move that work to a thread pool.
  • Inherits 50+ methods you don't need (setPriority, checkAccess, etc.) — confusing API.

2.2 Way #2 — Implement Runnable (the right way for low-level)

class EmailTask implements Runnable {
    private final String to;
    public EmailTask(String to) { this.to = to; }

    @Override
    public void run() {
        emailService.send(to, "Welcome!");
    }
}

Thread t = new Thread(new EmailTask("alice@x.com"), "email-worker-1");
t.start();

// Or with a lambda (Java 8+):
new Thread(() -> emailService.send("bob@x.com", "Hi"), "email-worker-2").start();
Why Runnable wins over Thread
You can extend something else (e.g., AbstractTask)
Same Runnable can be submitted to a thread pool, scheduled, retried — reusable
Lambdas make it one line
The whole modern concurrency API (ExecutorService, CompletableFuture) expects Runnable/Callable

2.3 Way #3 — Callable + Future (when you need a result)

Runnable.run() returns void and can't throw checked exceptions. Bad for "fetch user, return user".

import java.util.concurrent.*;

ExecutorService pool = Executors.newFixedThreadPool(4);

Callable<User> task = () -> {
    Thread.sleep(200);            // can throw checked!
    return userRepo.findById(42);  // returns a value!
};

Future<User> future = pool.submit(task);
User user = future.get(2, TimeUnit.SECONDS);   // always pass a timeout!
pool.shutdown();
Method on FuturePurpose
get()Block until result. Throws if task threw.
get(timeout, unit)Block up to timeout. Always prefer this.
isDone()Has the task finished (success/error/cancelled)?
cancel(boolean mayInterrupt)Try to stop. true = interrupt the thread if running.
isCancelled()Was cancel() called and successful?
Future limitations

Future is from 2004 and shows its age. You can't: chain transformations, combine multiple futures, attach callbacks, or be notified when done. For modern code, use CompletableFuture (Part 14).

2.4 Way #4 — Submit to an ExecutorService (production default)

This is what 99% of production code looks like. We'll cover deeply in Part 12, but the basic shape:

ExecutorService pool = Executors.newFixedThreadPool(10);

for (Order order : pendingOrders) {
    pool.submit(() -> processOrder(order));   // fire-and-forget
}

pool.shutdown();
pool.awaitTermination(30, TimeUnit.SECONDS);
Decision tree — which API?
  • Simple background task with no result → Runnable + ExecutorService.submit()
  • Need a value back → Callable + Future (or better, CompletableFuture)
  • Need to chain / combine async ops → CompletableFuture (Part 14)
  • Periodic / delayed → ScheduledExecutorService (Part 13)
  • Massive number of blocking I/O tasks (Java 21+) → Virtual threads (Part 17)
  • Extending Thread directly → almost never

2.5 Naming threads — non-negotiable in production

Untitled threads show up as Thread-1, Thread-2 in stack traces. Useless. Always name your threads.

// Bad: anonymous threads
pool.submit(task);

// Good: ThreadFactory with names
ThreadFactory factory = new ThreadFactory() {
    private final AtomicInteger counter = new AtomicInteger(1);
    @Override
    public Thread newThread(Runnable r) {
        Thread t = new Thread(r, "order-processor-" + counter.getAndIncrement());
        t.setDaemon(false);
        t.setUncaughtExceptionHandler((th, ex) -> log.error("Thread {} died", th.getName(), ex));
        return t;
    }
};
ExecutorService pool = Executors.newFixedThreadPool(10, factory);
Real case: I once spent 4 hours on this

A production API was 100% CPU. Thread dump showed 200 threads named pool-1-thread-N, pool-2-thread-N, ... I had no idea which pool was the problem. Two minutes after adding meaningful names (db-pool, http-pool, email-pool), I saw it was the email pool burning CPU due to a Sendgrid client retry storm. Always name your threads.

Part 3 — Thread Methods Deep Dive

Why this part

What you'll learn

The methods you'll call on a Thread: start, sleep, join, interrupt. What they really do, what traps they hide, and the right way to stop a running thread without corrupting data.

Why it matters

Almost every Java thread bug at the beginner level comes from misusing one of these methods — calling run() instead of start(), swallowing InterruptedException, or trying to use deprecated Thread.stop(). Master these and you've cleared the most common bug minefield.

3.1 start() vs run() — the #1 beginner trap

Runnable task = () -> System.out.println(Thread.currentThread().getName());

Thread t = new Thread(task, "worker");
t.run();    // ❌ runs in CALLING thread (e.g., main). NOT a new thread!
t.start();  // ✅ creates a new OS thread, then calls run() inside it

run() is just a regular method. start() is the magic — it asks the JVM to spawn a real OS thread and call run() inside it. Calling start() twice on the same thread throws IllegalThreadStateException — threads are one-shot objects.

3.2 sleep(ms)

Pauses the current thread for at least ms milliseconds.

try {
    Thread.sleep(500);
    Thread.sleep(Duration.ofSeconds(2));   // Java 19+ overload
} catch (InterruptedException e) {
    Thread.currentThread().interrupt(); // restore the flag — see 3.5
}
Sleep gotchas
  • Doesn't release locks. If you hold a synchronized lock, sleeping while holding it blocks everyone else. Use wait() if you want to release the lock.
  • Not precise. Actual sleep can be longer (sometimes much longer under load). Don't use for animations or timing-critical code.
  • "Fixing" tests with sleep(100) is a code smell — your test is racy. Use proper synchronization (latches, awaitility).

3.3 join()

worker.join() makes the caller wait until worker finishes.

Thread a = new Thread(() -> doWork("A"));
Thread b = new Thread(() -> doWork("B"));
a.start(); b.start();
a.join();        // wait for A
b.join();        // then wait for B
System.out.println("both done");

// Timed variant — don't wait forever
a.join(5000);
if (a.isAlive()) {
    System.err.println("A still running after 5s, giving up");
    a.interrupt();
}
Real use: parallel-then-merge

Common pattern in batch jobs: spawn N workers to process partitions of input, join them all, then merge results. Each worker writes to its own slot in a results array (no shared state, no locks).

3.4 yield() — almost always wrong

A hint to the scheduler that the current thread is willing to give up its time slice. JVM-dependent — may do nothing on some platforms.

Forget it exists. If you think you need yield(), you actually need a proper synchronizer (latch, semaphore, lock).

3.5 interrupt() — cooperative cancellation done right

Java's Thread.stop() is deprecated and dangerous (it can corrupt locked data structures). The right way to cancel a thread is cooperatively:

  1. Caller sets the thread's interrupt flag with thread.interrupt().
  2. The running thread checks the flag and exits gracefully.
public class FileScanner implements Runnable {
    @Override
    public void run() {
        while (!Thread.currentThread().isInterrupted()) {
            File file = nextFile();
            if (file == null) break;
            scan(file);
        }
        cleanup();   // flush partial results, close handles
        log.info("Scanner exited cleanly");
    }
}

Thread t = new Thread(new FileScanner(), "scanner");
t.start();
// ... time passes ...
t.interrupt();    // request cancellation
t.join();         // wait for clean exit

Blocking methods and InterruptedException

Methods like sleep, wait, join, BlockingQueue.take, Future.get are interruptible. When interrupted:

  • They throw InterruptedException
  • They clear the interrupt flag. ⚠️
// WRONG — swallows interrupt, caller can't cancel us
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    // nothing — interrupt is now LOST
}

// CORRECT — restore the flag so callers/loops see it
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return;   // or rethrow if your method declares it
}

// BEST — let it propagate
public void work() throws InterruptedException {
    Thread.sleep(1000);
}
The Golden Rule of InterruptedException

You have two options: (a) propagate (declare throws InterruptedException), or (b) restore the flag (Thread.currentThread().interrupt()). Never silently swallow it.

Why? Imagine your code is in a library. The user calls shutdownNow(). If your library swallows the interrupt, their service won't shut down — and they'll blame your library.

Part 4 — wait / notify

Why this part

What you'll learn

The original way Java threads signal each other ("hey, the queue isn't empty anymore — wake up"). Three methods on every Java object: wait(), notify(), notifyAll().

Why it matters

Modern Java has nicer alternatives (BlockingQueue, CountDownLatch) — and you should usually prefer them. But every concurrent collection in the JDK is built on top of wait/notify. Understanding it makes the rest of concurrency click. Plus, every interview asks about it.

Plain-English summary

"Wait" = "go to sleep until somebody pokes me". "Notify" = "poke one sleeper". "NotifyAll" = "poke everybody". And — twist — sometimes Java pokes you for no reason (spurious wakeups), so always re-check why you woke up.

Before java.util.concurrent, Java had wait(), notify(), and notifyAll() on Object. They're still important — every concurrent collection is built on them, and they show up constantly in interviews.

4.1 The mental model

Every Java object has:

  • A monitor (lock) — used by synchronized
  • A wait set — a queue of threads waiting to be notified
MethodWhat it doesMust hold lock?
obj.wait()Releases the lock and parks the thread on obj's wait setYes — throws IllegalMonitorStateException otherwise
obj.wait(ms)Same but with timeoutYes
obj.notify()Wakes one arbitrary thread from obj's wait setYes
obj.notifyAll()Wakes all threads on obj's wait set (they re-compete for the lock)Yes
Key insight

wait() atomically releases the lock AND parks the thread. When notified, it wakes up and re-acquires the lock before returning. This is how it differs from sleep() — sleep keeps the lock; wait releases it.

4.2 The canonical pattern (always-while-loop)

synchronized (lock) {
    while (!conditionMet()) {     // always WHILE, never IF — see 4.3
        lock.wait();
    }
    doWork();
}

// In another thread:
synchronized (lock) {
    makeConditionTrue();
    lock.notifyAll();              // usually notifyAll, not notify — see 4.4
}

4.3 Why while, not if? — Spurious Wakeups

Java's spec allows wait() to return without anyone calling notify. This is called a spurious wakeup, and it's not a bug — it's just how OS scheduling works on some platforms.

If you use if, you proceed assuming the condition is true — but it might not be. Always re-check in a loop.

4.4 notify() vs notifyAll()

notify()notifyAll()
Wakes one arbitrary threadWakes all waiting threads
Faster (less thundering herd)Safer (no missed wakeups)
Use when all waiters are equivalent and waiting on the same conditionUse when waiters have different conditions (e.g., producer-consumer with full vs empty)
When in doubt, use notifyAll()

notify() can cause "lost wakeups" if the woken thread doesn't actually need to proceed (and goes back to wait). The cost of waking everyone unnecessarily is usually tiny.

4.5 Worked example — Bounded Buffer

public class BoundedBuffer<T> {
    private final Object[] buf;
    private int head, tail, count;

    public BoundedBuffer(int capacity) { buf = new Object[capacity]; }

    public synchronized void put(T item) throws InterruptedException {
        while (count == buf.length) wait();   // wait until not full
        buf[tail] = item;
        tail = (tail + 1) % buf.length;
        count++;
        notifyAll();                       // signal "not empty" to consumers
    }

    @SuppressWarnings("unchecked")
    public synchronized T take() throws InterruptedException {
        while (count == 0) wait();           // wait until not empty
        T item = (T) buf[head];
        buf[head] = null;
        head = (head + 1) % buf.length;
        count--;
        notifyAll();                       // signal "not full" to producers
        return item;
    }
}
Real case: this IS java.util.concurrent.ArrayBlockingQueue

The JDK's ArrayBlockingQueue is essentially this code, but with two Conditions (notFull, notEmpty) instead of one wait set, so producers don't accidentally wake other producers. Use ArrayBlockingQueue in real code — never reinvent.

4.6 Solving "ABCABC..." with three threads

The interview classic from Exercise 3.2:

public class ABCPrinter {
    private final Object lock = new Object();
    private int turn = 0;   // 0=A, 1=B, 2=C

    public void print(String letter, int myTurn) throws InterruptedException {
        for (int i = 0; i < 10; i++) {
            synchronized (lock) {
                while (turn != myTurn) lock.wait();
                System.out.print(letter);
                turn = (turn + 1) % 3;

            }
        }
    }

    public static void main(String[] args) throws Exception {
        ABCPrinter p = new ABCPrinter();
        new Thread(() -> tryRun(() -> p.print("A", 0))).start();
        new Thread(() -> tryRun(() -> p.print("B", 1))).start();
        new Thread(() -> tryRun(() -> p.print("C", 2))).start();
    }
}

4.7 Common bugs

Bug 1: IllegalMonitorStateException

Calling wait/notify without holding the lock on that object. Always wrap in synchronized(obj).

Bug 2: Lost wakeup

Notifier fires notify() before waiter calls wait(). The notification is lost. Always set the condition and notify under the same lock — and always re-check the condition.

Bug 3: Using if instead of while

Spurious wakeup → wrong behaviour. Always loop.

Modern advice

Use ReentrantLock + Condition (Part 8) instead of intrinsic monitors when you need multiple wait sets, fair queueing, or interruptible/timed waits. For producer-consumer, just use BlockingQueue.

Part 5 — Race Conditions

Why this part

What you'll learn

The most famous concurrency bug, with full step-by-step walkthroughs. Three flavours of race conditions you'll meet in real code, and how to spot them in code reviews before they reach production.

Why it matters

Race conditions are the bug that makes you doubt yourself: code that "should" be correct, that passes all tests, that fails once in 50,000 requests in production. Once you can recognise the pattern, you'll see it everywhere — including code you've already shipped. (Sorry.)

5.1 What's a race condition?

A race condition exists when the correctness of a program depends on the timing or interleaving of multiple threads. The bug is the possibility — even if it manifests rarely.

5.2 The classic counter race

public class UnsafeCounter {
    private int count = 0;
    public void increment() { count++; }   // LOOKS atomic. ISN'T.
    public int get() { return count; }
}

public class CounterRace {
    public static void main(String[] args) throws Exception {
        UnsafeCounter c = new UnsafeCounter();
        Runnable task = () -> {
            for (int i = 0; i < 100_000; i++) c.increment();
        };
        Thread t1 = new Thread(task), t2 = new Thread(task);
        t1.start(); t2.start();
        t1.join();  t2.join();
        System.out.println(c.get());   // expected 200,000
    }
}
Run 1: 137,452 Run 2: 198,201 Run 3: 145,008 Run 4: 200,000 ← sometimes correct by luck!

5.3 Why does this happen? — bytecode reality

count++ compiles to three bytecode instructions:

GETFIELD count ← read count from heap into register ICONST_1 ← push 1 IADD ← add PUTFIELD count ← write back to heap

The OS can pause the thread between any of these. So:

Time T1 T2 count value ──── ─────────────── ─────────────── ────────────── 0 READ → 5 5 1 READ → 5 5 2 ADD = 6 5 3 ADD = 6 5 4 WRITE 6 6 5 WRITE 6 6 ← lost +1!

One increment vanished. Repeat this hundreds of times → final value below 200,000.

5.4 Three classes of race conditions

Read-modify-write race

Like the counter. Fix: lock, atomic, or compareAndSet loop.

Check-then-act race

// BUG: between check and act, another thread can change state
if (!cache.containsKey(k)) {
    cache.put(k, expensiveCompute(k));   // might be a duplicate!
}

// FIX: atomic compound operation
cache.computeIfAbsent(k, this::expensiveCompute);

Visibility race

Thread A writes; Thread B reads, but sees a stale value (cached in B's CPU register or L1 cache). We'll go deep on this in Part 10 (Java Memory Model).

// BUG: B may never see the update
private boolean stopped = false;
public void stop() { stopped = true; }
public void loop() { while (!stopped) { ... } }   // may run forever!

// FIX: volatile (Part 9)
private volatile boolean stopped = false;

5.5 Real-world race condition: bank transfer

public class Account {
    private long balance;
    public void debit(long amount) {
        if (balance >= amount) {        // CHECK
            balance -= amount;            // ACT
        } else {
            throw new InsufficientFundsException();
        }
    }
}
Real case: $1M bug

A fintech startup found that during high-traffic periods, a single account could be debited twice for the same transaction. Why? Two requests arrived simultaneously. Both saw balance = 1000. Both checked "≥ 1000? yes". Both subtracted. Final balance: -1000. The fix was a row-level DB lock + idempotency keys. Read the original race: a textbook check-then-act.

Part 6 — Synchronization

Why this part

What you'll learn

How to use synchronized to protect shared data from race conditions. The simplest, most common tool in Java concurrency.

Why it matters

This is the fix for the bugs you saw in Part 5. synchronized is in literally every non-trivial Java codebase. Knowing how to use it correctly — and where it goes wrong — is foundational.

Plain-English summary

Remember "the bathroom key" from Part 0? synchronized is Java's way of saying "before this code runs, grab the key. When it's done, give the key back." Only one thread at a time can hold the key, so only one runs the protected code at a time.

6.1 LEVEL 1 The simple version: lock + unlock

Remember our broken counter from Part 5? Two threads both did count++, and we lost some increments. Here's the fix in one keyword:

public class Counter {
    private int count = 0;

    public synchronized void increment() {  // ← that one keyword fixes it
        count++;
    }

    public synchronized int get() {
        return count;
    }
}

What does synchronized on a method do? Two things, both crucial:

  1. Mutual exclusion — only one thread can be inside any synchronized method on this object at a time. If thread A is in increment(), thread B trying to enter increment() OR get() has to wait.
  2. Memory visibility — when a thread releases the lock (exits the method), all the changes it made are guaranteed visible to whichever thread enters next. (Remember Model 4 in Part 0 — the cached views? synchronized forces a refresh.)
Bathroom key analogy revisited

Each Java object has its own bathroom key. synchronized void increment() means "to call this method, grab this object's key first". If somebody else has the key, you wait outside.

The "someone else has the key" case is when threads pile up — exactly what we want. They politely line up instead of trampling each other's data.

Try it: the fixed counter

Take the Counter above and run the same race test from Part 5: two threads, each calling increment() 100,000 times. Now you reliably get 200,000. The race is gone.

Show answer

get() can read while another thread is mid-write. Without synchronization, it might see a stale or torn value. The visibility rule (point 2 above) only kicks in when both reader AND writer use synchronized. Add synchronized to get() too.

6.2 LEVEL 1 Three places to put synchronized

(a) On an instance method — locks this

public synchronized void increment() { count++; }
// Equivalent to:
public void increment() {
    synchronized (this) { count++; }
}

Means: "to enter this method, grab the lock that lives inside this object." Two different Counter objects don't block each other — each has its own lock. Two calls on the same Counter do.

(b) On a static method — locks the class object

public static synchronized void init() { ... }
// Equivalent to:
public static void init() {
    synchronized (Counter.class) { ... }
}

Means: "grab the lock on the class itself". There's only one Counter.class object, so this is a single global lock for all instances.

(c) As a block — locks any object you choose

public class Counter {
    private int count;
    private final Object lock = new Object();   // dedicated lock object

    public void increment() {
        synchronized (lock) {
            count++;
        }
    }
}

This is the preferred form in production code. Why?

Why a private lock object beats synchronized(this)

If you write synchronized(this), your object's lock is publicly accessible. Anyone holding a reference to your Counter can lock on it themselves, possibly accidentally:

Counter c = new Counter();
synchronized (c) {           // hostile or buggy code locks YOUR object
    Thread.sleep(60_000);   // nobody can call c.increment() for 1 minute!
}

With a private final lock object, no outside code can interfere. Always do this in libraries and shared code.

6.3 LEVEL 2 Reentrancy — the same thread can grab its own lock

Suppose info() needs to call log(), and both are synchronized:

public class Logger {
    public synchronized void info(String msg) {
        log("INFO: " + msg);   // calls another synchronized method
    }
    public synchronized void log(String line) {
        System.out.println(line);
    }
}

When info() runs, the thread already holds the lock. Then it calls log() which also wants the lock. Without help, the thread would deadlock with itself.

Java's locks are reentrant: they keep a counter of how many times the same thread has grabbed them. The thread holds it until it has released it the same number of times. So the example above just works.

Why "reentrant" is a fancy word for "obvious behaviour"

You'd expect calling your own methods to work. Reentrancy is what makes that expectation true. (Some lock systems in other languages aren't reentrant — and beginners hate them for it.)

6.4 LEVEL 2 Lock granularity — don't lock too much

Synchronization isn't free. While one thread is inside, others wait. So a too-broad lock turns your concurrent code back into single-threaded code.

Bad: one lock for everything

public class UserCache {
    private final Map<Long,User> users = new HashMap<>();
    private final Map<Long,Order> orders = new HashMap<>();

    public synchronized void addUser(User u)   { users.put(u.id, u); }
    public synchronized void addOrder(Order o) { orders.put(o.id, o); }
}

Adding a user blocks adding an order — for no reason! These are unrelated maps.

Better: one lock per resource

private final Object userLock = new Object();
private final Object orderLock = new Object();

public void addUser(User u)   { synchronized(userLock)  { users.put(u.id, u); } }
public void addOrder(Order o) { synchronized(orderLock) { orders.put(o.id, o); } }

Best (often): use a concurrent collection and skip locks

private final Map<Long,User> users = new ConcurrentHashMap<>();
public void addUser(User u) { users.put(u.id, u); }   // already thread-safe

(More on concurrent collections in Part 20.)

Rule of thumb

Lock the smallest piece of code that accesses the smallest piece of state for the shortest time. Then ask: "do I really need a lock at all, or can I use a concurrent collection / atomic / immutable snapshot?"

6.5 LEVEL 2 The cardinal sin: I/O inside a lock

public synchronized void processOrder(Order o) {
    db.save(o);              // 50ms — and we hold the lock the whole time
    payment.charge(o);       // 200ms — same
    notifications.send(o);   // 100ms — same
}

While one order processes, every other thread that calls processOrder waits 350ms. Multiply by hundreds of concurrent users → server falls over.

Real case: 30-second outage

A team had synchronized on a method that called Redis. Redis briefly slowed to 500ms responses. Suddenly all 200 Tomcat threads were lined up at the lock. p99 latency went from 50ms to 30 seconds; the service was effectively down. Lesson: never block on I/O inside a lock.

Fix pattern: read what you need under the lock, do the I/O outside, take the lock again briefly to commit:

Order snapshot;
synchronized (lock) { snapshot = currentOrder.copy(); }
PaymentResult r = payment.charge(snapshot);   // no lock held
synchronized (lock) { applyResult(r); }

6.6 LEVEL 3 What synchronized actually compiles to

For the curious. The compiler emits two bytecodes: monitorenter (acquire) and monitorexit (release). The exit is wrapped in implicit try/finally so an exception still releases the lock.

At runtime, the JVM has clever optimisations:

  • Thin lock: an uncontended acquire is just a CAS on the object header (~2 nanoseconds).
  • Fat lock: only when there's actual contention does the JVM allocate a real OS-level monitor.
  • Lock elision: if the JIT proves no other thread can reach the locked object, it removes the lock entirely.
  • Biased locking (deprecated in JDK 15+): used to bias the lock to one thread for nearly-free re-acquisition.
Practical takeaway

synchronized with no contention is nearly free. The cost is contention — many threads piling up at the same lock. So: keep critical sections small, don't share more state than you need.

Part 7 — Deadlock, Livelock, Starvation

Why this part

What you'll learn

The three ways your perfectly-locked code can still go wrong: deadlock (everyone stuck), livelock (everyone moving but nobody progressing), and starvation (one thread never gets a turn). And how to prevent each.

Why it matters

Deadlock is the #2 most-feared concurrency bug after race conditions. Once you see your service freeze with all threads pointing at each other in a thread dump, you'll never forget it. The good news: a small set of techniques (lock ordering, tryLock, no nested locks) prevents 99% of cases.

7.1 Deadlock — the four conditions (Coffman)

Deadlock requires all four:

  1. Mutual exclusion — resources are held exclusively.
  2. Hold and wait — a thread holds one resource while waiting for another.
  3. No preemption — resources are released only voluntarily.
  4. Circular wait — T1 waits for T2, T2 waits for T3, ..., Tn waits for T1.

Break any one condition and deadlock is impossible.

7.2 The classic two-lock deadlock

public class Bank {
    public void transfer(Account from, Account to, long amount) {
        synchronized (from) {
            synchronized (to) {       // nested locking
                from.debit(amount);
                to.credit(amount);
            }
        }
    }
}

// Thread 1: bank.transfer(A, B, 100)   → locks A, then waits for B
// Thread 2: bank.transfer(B, A, 100)   → locks B, then waits for A
// → DEADLOCK. Both threads frozen forever.
T1 holds A waits for B ↑ │ │ ▼ waits for A T2 holds B (circular wait)

7.3 Fix #1 — Lock ordering

Acquire locks in a globally consistent order — e.g., by hash code or natural ID.

public void transfer(Account from, Account to, long amount) {
    Account first  = from.id < to.id ? from : to;
    Account second = from.id < to.id ? to   : from;

    synchronized (first) {
        synchronized (second) {
            from.debit(amount);
            to.credit(amount);
        }
    }
}

Now both threads always acquire the lower-ID account first → no circular wait → no deadlock.

Hash-code tie-break

If your objects don't have a natural ID, use System.identityHashCode. Beware collisions — fall back to a tie-breaker lock (a third "global" lock acquired only on collision).

7.4 Fix #2 — tryLock with timeout

Don't wait forever; back off and retry.

public boolean transfer(Account from, Account to, long amount) throws InterruptedException {
    while (true) {
        if (from.lock.tryLock(100, TimeUnit.MILLISECONDS)) {
            try {
                if (to.lock.tryLock(100, TimeUnit.MILLISECONDS)) {
                    try {
                        from.debit(amount);
                        to.credit(amount);
                        return true;
                    } finally { to.lock.unlock(); }
                }
            } finally { from.lock.unlock(); }
        }
        Thread.sleep(ThreadLocalRandom.current().nextInt(50));   // jitter to avoid livelock
    }
}

7.5 Fix #3 — Don't hold multiple locks

Often you can refactor: copy data out under one lock, do work without locks, then commit under the other lock. Best fix is no nested locking at all.

7.6 Detecting deadlocks at runtime

import java.lang.management.*;

ThreadMXBean bean = ManagementFactory.getThreadMXBean();
long[] ids = bean.findDeadlockedThreads();
if (ids != null) {
    ThreadInfo[] infos = bean.getThreadInfo(ids, true, true);
    for (ThreadInfo info : infos) log.error("DEADLOCK: {}", info);
}

A monitoring thread can run this every minute and alert. jstack also detects and prints "Found one Java-level deadlock" automatically.

7.7 Livelock

Threads keep responding to each other but make no progress. Like two polite people in a corridor: each steps aside in sync, forever.

// Polite-husband-and-wife livelock
while (!fork.isAvailable()) {
    fork.releaseSpoon();
    Thread.sleep(100);   // no jitter — both threads sleep equal time
    fork.takeSpoon();
}

Fix: randomized backoff. Add jitter so threads desynchronise.

7.8 Starvation

A thread never gets the resource because others keep grabbing it.

High-priority threads dominateDon't rely on priorities
Unfair lock — lucky thread re-acquires immediatelynew ReentrantLock(true) for fair lock (slower but fair)
Reader-heavy ReadWriteLock starves writersUse StampedLock or fair RW lock
One slow task blocks the executor queueSeparate pools for fast vs slow work
Real case: writer starvation

A team used ReentrantReadWriteLock for a config cache (read-heavy). Under load, writes (config refreshes) were starved for minutes — the read lock was never empty. They switched to StampedLock with optimistic reads. Reads got faster and writes got through.

Part 8 — Locks (ReentrantLock, ReadWriteLock, StampedLock)

Why this part

What you'll learn

Three "premium" lock classes from java.util.concurrent.locks — ReentrantLock (synchronized++), ReadWriteLock (many readers, one writer), and StampedLock (ultra-fast read-mostly).

Why it matters

synchronized is great but limited — it can't time out, can't be interrupted, can't have multiple wait queues. These classes fix that. You'll reach for ReentrantLock when you need tryLock with a timeout (deadlock-resistant code), and ReadWriteLock when reads outnumber writes 100-to-1 (caches).

Beginner's tip

If you're just starting out: stick with synchronized. Read this part, but only switch to these when you have a specific reason. The extra power comes with extra responsibility — you must call unlock() in a finally block, every time, no exceptions.

java.util.concurrent.locks gives you flexible alternatives to synchronized.

8.1 ReentrantLock — synchronized++ 

import java.util.concurrent.locks.ReentrantLock;

public class SafeCounter {
    private final ReentrantLock lock = new ReentrantLock();
    private int count;

    public void increment() {
        lock.lock();
        try {
            count++;
        } finally {
            lock.unlock();   // ALWAYS unlock in finally — even if work throws
        }
    }
}

8.2 Condition — wait/notify, professional edition

public class BoundedBuffer<T> {
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull  = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();
    private final Object[] buf;
    private int head, tail, count;

    public BoundedBuffer(int n) { buf = new Object[n]; }

    public void put(T x) throws InterruptedException {
        lock.lock();
        try {
            while (count == buf.length) notFull.await();
            buf[tail] = x;
            tail = (tail + 1) % buf.length;
            count++;
            notEmpty.signal();   // only wake a consumer, not other producers
        } finally { lock.unlock(); }
    }

    @SuppressWarnings("unchecked")
    public T take() throws InterruptedException {
        lock.lock();
        try {
            while (count == 0) notEmpty.await();
            T x = (T) buf[head];
            buf[head] = null;
            head = (head + 1) % buf.length;
            count--;
            notFull.signal();
            return x;
        } finally { lock.unlock(); }
    }
}

Compare to the wait/notify version in Part 4 — no thundering herd. Only the relevant side wakes up.

8.3 ReadWriteLock — many readers, one writer

public class ConfigCache {
    private final ReadWriteLock rw = new ReentrantReadWriteLock();
    private final Lock r = rw.readLock();
    private final Lock w = rw.writeLock();
    private Map<String,String> data = new HashMap<>();

    public String get(String key) {
        r.lock();
        try { return data.get(key); }
        finally { r.unlock(); }
    }
    public void refresh(Map<String,String> fresh) {
        w.lock();
        try { data = new HashMap<>(fresh); }
        finally { w.unlock(); }
    }
}

Watch out

If reads dominate writes by a lot AND each read is short, the bookkeeping overhead of ReadWriteLock can be slower than plain synchronized. Always benchmark.

8.4 StampedLock — fastest reader pattern (Java 8+)

Adds optimistic reads — no blocking, just a stamp validation.

import java.util.concurrent.locks.StampedLock;

public class Point {
    private double x, y;
    private final StampedLock sl = new StampedLock();

    public void move(double dx, double dy) {
        long stamp = sl.writeLock();
        try { x += dx; y += dy; }
        finally { sl.unlockWrite(stamp); }
    }

    public double distanceFromOrigin() {
        long stamp = sl.tryOptimisticRead();    // no actual lock!
        double cx = x, cy = y;
        if (!sl.validate(stamp)) {              // did a writer happen?
            stamp = sl.readLock();              // fall back to real read lock
            try { cx = x; cy = y; }
            finally { sl.unlockRead(stamp); }
        }
        return Math.sqrt(cx*cx + cy*cy);
    }
}
Why StampedLock is fast

Optimistic reads do no synchronization at all — just two atomic loads. If validation passes (no writer happened during the read), you're done. Only on a write conflict do you fall back to a real lock. Perfect for read-mostly hot paths like position lookups in a game engine, geometric data, or sensor readings.

StampedLock caveats
  • Not reentrant. Don't try to re-acquire it.
  • No Condition support.
  • Read fields into local variables before validating — values may be inconsistent mid-read.
  • Don't trust mutable objects read optimistically — only "snapshot" primitive reads are safe.

Part 9 — Atomics & volatile

Why this part

What you'll learn

How to update shared variables without locks. Two tools: the volatile keyword (for visibility) and the java.util.concurrent.atomic classes (for safe single-variable updates).

Why it matters

Locks are fine but they have overhead — and locking forces threads to wait. Atomics let many threads update the same variable concurrently with hardware-level guarantees and no waiting. Counters, IDs, flags, lock-free data structures — all built on atomics.

Plain-English summary

Two unrelated problems live in this Part:

  • "My write isn't visible to other threads." → fix with volatile.
  • "My counter loses increments under concurrent updates." → fix with AtomicInteger (or similar).

volatile ≠ atomic. volatile ≠ "thread-safe". They sound similar but solve different problems. We'll keep them clearly separate.

9.1 LEVEL 1 The simplest case: a "stop" flag

Suppose you want a worker thread that loops forever until told to stop:

public class Worker {
    private boolean stopped = false;

    public void run() {
        while (!stopped) {
            doSomeWork();
        }
        System.out.println("stopped");
    }

    public void stop() {
        stopped = true;
    }
}

Looks fine, right? Run it. Have main thread call stop() after a second. The worker will...

...sometimes loop forever.

Why? Remember Mental Model 4 from Part 0 — "threads have private cached views of the whiteboard". The worker thread might cache stopped in a CPU register, never bothering to look at the heap again. Main writes true, but the worker never sees it.

The fix: volatile

private volatile boolean stopped = false;

volatile tells the JVM: "this variable is shared between threads — every read goes to the heap, every write is published immediately."

Analogy

Without volatile, each worker has a photo of the whiteboard from earlier. With volatile, they're forbidden from using the photo — they must walk to the whiteboard and look every time.

9.2 LEVEL 1 What volatile does NOT do

Now back to our broken counter. Surely volatile fixes it?

public class Counter {
    private volatile int count = 0;
    public void increment() { count++; }   // STILL WRONG!
}

Run the race test. Still not 200,000. Why?

Because count++ is three operations (read, add, write). volatile makes the read fresh and the write visible — but two threads can still both read 5, both compute 6, both write 6. The race lives in the gap between read and write, and volatile doesn't help there.

The volatile trap

Beginners hear "volatile makes a variable thread-safe". That's wrong. volatile guarantees:

  • ✅ Visibility — writes seen by other threads.
  • ✅ Ordering — writes don't get reordered around the volatile access.
  • ❌ Atomicity for compound operations like x++ or x += y.

When IS volatile enough?

Scenariovolatile OK?
One writer, many readers (stop flag, config pointer)✅ Yes
Many threads independently x = newValue✅ Yes (last writer wins; if you don't care which, fine)
Many threads doing x++❌ No — use AtomicInteger
Many threads doing x = x + somethingElse❌ No
Read-then-write based on the read❌ No — use a lock or atomic

9.3 LEVEL 1 The other tool: AtomicInteger

This is the safe fix for the counter:

import java.util.concurrent.atomic.AtomicInteger;

public class Counter {
    private final AtomicInteger count = new AtomicInteger(0);

    public void increment() {
        count.incrementAndGet();
    }
    public int get() {
        return count.get();
    }
}

incrementAndGet() performs the entire read-add-write as one indivisible operation. No matter how many threads run it concurrently, no increment is lost.

And it does this without locks. No thread waits. How is that possible? That's our LEVEL 2 story.

9.4 LEVEL 2 CAS — the magic ingredient

CPUs have a special instruction called Compare-And-Swap (CAS). In Java terms it works like this:

// Pseudocode for what CAS does in hardware (atomically):
boolean compareAndSwap(memory, expectedValue, newValue) {
    if (memory == expectedValue) {
        memory = newValue;
        return true;     // "yes, I successfully swapped"
    } else {
        return false;    // "memory wasn't what I expected; not swapped"
    }
}

The whole comparison-and-swap is one CPU instruction — uninterruptible. With this primitive, atomic increment becomes:

// What incrementAndGet() does, simplified:
int incrementAndGet() {
    while (true) {
        int current = value;
        int next    = current + 1;
        if (compareAndSwap(value, current, next)) {
            return next;            // won the race, done
        }
        // CAS failed → another thread changed value first → retry the whole loop
    }
}
Analogy

You go to write your name in a guestbook. You see "5 names so far" and prepare to write "6". Just as your pen touches paper, you check: "is it really still 5?" If yes — write 6, done. If no — somebody beat you to it; you scratch out your plan, look again ("oh now it's 7"), prepare to write 8, check again, etc. You keep retrying until you win.

That's CAS. Many writers all retry; eventually each succeeds. Nobody waits in a queue — they just retry.

Why CAS is fast

No OS context switch. No thread suspension. Under low contention, an atomic operation costs about the same as a regular write (~nanoseconds). Under heavy contention, threads spin — which can become slower than a real lock. Use atomics where contention is moderate.

9.6 LEVEL 2 The "atomic snapshot" pattern

One of the most powerful tricks in concurrent Java: store an immutable snapshot in an AtomicReference. Reads are completely lock-free; updates atomically replace the snapshot.

public class RoutingTable {
    // Map is immutable; we replace the whole reference atomically.
    private final AtomicReference<Map<String,String>> routes =
        new AtomicReference<>(Map.of());

    public String resolve(String host) {
        return routes.get().get(host);    // lock-free, super fast
    }

    public void add(String host, String ip) {
        routes.updateAndGet(curr -> {
            Map<String,String> next = new HashMap<>(curr);
            next.put(host, ip);
            return Map.copyOf(next);          // new immutable map
        });
    }
}
Real case: feature flags at scale

LinkedIn's feature-flag library stores all flags as one big immutable map in an AtomicReference. Reads (millions per second) are lock-free. Updates (rare) atomically swap the whole map. Latency for a flag check: ~20ns. This pattern is everywhere in high-performance Java.

9.7 LEVEL 2 When AtomicLong gets slow: LongAdder

Under heavy contention (e.g., a metrics counter incremented by 100 threads), AtomicLong spends most of its time in CAS retry loops — threads keep stepping on each other.

LongAdder solves this by giving each thread its own private cell to update. The total is computed by summing all cells when you ask:

LongAdder hits = new LongAdder();
hits.increment();              // fast: writes only this thread's cell
long total = hits.sum();      // slower: aggregate all cells
Use AtomicLong whenUse LongAdder when

Total ordering matters (unique IDs)You only need an aggregate (counters, metrics)
Low-to-medium contentionHigh contention (50+ writer threads)

9.8 LEVEL 3 The ABA problem

CAS only checks "is the value still X?" It can't tell if X→Y→X happened in between. Usually this doesn't matter; in lock-free data structures (like a stack of nodes), it can.

// Imagine popping the head of a lock-free stack:
Node head = top.get();        // head = nodeA, head.next = nodeB
// ... another thread pops nodeA, pops nodeB, pushes nodeA back ...
//     top is again nodeA, but nodeB is gone! head.next now points to garbage.
top.compareAndSet(head, head.next);   // CAS thinks "still nodeA, all good"
//                                       but installs a stale next pointer → corruption

Fix: use AtomicStampedReference, which attaches a version counter; CAS checks both reference and stamp.

Should you worry about ABA?

For typical app code (counters, flags, snapshot swaps): no. ABA is mostly an issue for hand-rolled lock-free queues and stacks. If you're not building those, skip this section.

9.9 LEVEL 3 VarHandle (Java 9+)

Lower-level access for library authors. Lets you do CAS on a regular field without wrapping it in an Atomic class. Used internally by JDK collections. You probably don't need it — but worth knowing the name when you see it in stack traces.

9.10 What you've learned

  • volatile = visibility + ordering. NOT atomicity.
  • Use volatile for: stop flags, config pointers, single-write multi-read.
  • Don't use volatile for compound updates like x++.
  • Use AtomicInteger/Long/Reference for safe lock-free updates.
  • The magic underneath is CAS — a hardware atomic primitive.
  • Under heavy contention, prefer LongAdder for counters.
  • The "atomic immutable snapshot" pattern is a powerful alternative to locking.

Part 10 — Java Memory Model (JMM)

Why this part

What you'll learn

The rules that govern when one thread's writes become visible to another. This is the Java Memory Model — JMM for short. We'll start with what actually happens on real CPUs (it's weirder than you think), then learn just enough JMM vocabulary to write correct code.

Why it matters

This is the theoretical foundation that explains why volatile, synchronized, and atomics work the way they do. You can write correct code without knowing the JMM by following recipes. But you can't debug subtle concurrency bugs, or design new patterns, without it.

Honest warning for beginners

This is the hardest part of this guide. Don't try to memorize it. Read Levels 1 and 2 once. Skip Level 3 on first pass. Come back when you find yourself asking "but why does Java need volatile at all?"

10.1 LEVEL 1 The illusion you grew up with

You think your code runs like this:

CPU executes instructions in source order. Memory writes go straight to RAM. Other threads see them immediately.

None of that is true on modern hardware. Let's see why.

10.2 LEVEL 1 Three sources of "weirdness"

Source 1 — CPU caches (the "private photo" problem)

Each CPU core has its own private L1/L2 cache. A write goes to the cache, not directly to RAM. Other cores may not see it for many nanoseconds — or until forced to refresh.

Core 1 Core 2 ┌────┐ ┌────┐ │ L1 │ │ L1 │ ← per-core caches (private!) ├────┤ ├────┤ │ L2 │ │ L2 │ └─┬──┘ └─┬──┘ └──────┬──────────────┘ ▼ Shared L3 │ ▼ RAM

This is exactly Mental Model 4 from Part 0 — each thread has its private "photo of the whiteboard" (its CPU's cache).

Source 2 — CPU instruction reordering

To run faster, modern CPUs execute multiple instructions in parallel and may complete them out of source order. As long as your single thread can't tell the difference, this is allowed.

// Source code:                  // CPU might run as:
a = 1;                              b = 2;
b = 2;                              a = 1;
// Single-threaded result is identical. But other threads see the writes "out of order."

Source 3 — Compiler / JIT reordering

Before your code even gets to the CPU, the Java JIT compiler may reorder operations during optimization. Same rule: as-if-single-threaded preserved, anything else is fair game.

The big takeaway

Your code does not execute in source order. Your CPU does not immediately publish writes to other threads. By default, the only guarantee is that your one thread sees its own work in order.

Anything beyond that — making thread B see thread A's writes — requires you to ask for it, by using volatile, synchronized, atomics, or some other JMM-aware tool.

10.3 LEVEL 2 A famous example: the "both zero" puzzle

// Shared variables, both start at 0
int a = 0, b = 0;

// Thread 1                    Thread 2
a = 1;                          b = 1;
int r1 = b;                    int r2 = a;

Common-sense reasoning: at least one of r1 or r2 must be 1. "Either Thread 1 wrote a first, then Thread 2's read of a sees 1; or Thread 2 wrote b first, then Thread 1's read of b sees 1."

Wrong. Without synchronization, both reads can return 0. The CPU is free to reorder each thread's two statements (since they're independent within that thread):

// Possible execution:
T1: r1 = b;       // reads 0
T2: r2 = a;       // reads 0
T1: a = 1;
T2: b = 1;
// Both r1=0 and r2=0 — surprising but valid!

This is not a bug, this is the spec. If you don't want this, you need to forbid the reordering — that's what volatile and locks do.

10.4 LEVEL 2 Happens-before: the only rule that matters

The JMM defines a relationship called happens-before, written A hb B. If A happens-before B, then:

  • A's effects are visible to B.
  • A is not reordered after B.

Without a happens-before edge between two operations in different threads, the JVM makes no guarantees. They can be reordered, made invisible, anything.

Analogy

Think of "happens-before" as a road. If there's a road from A to B, you can drive from A to B — A's writes reach B's reads. Without a road, B is on a separate island; A's writes might never get there.

The whole game of writing correct concurrent Java is: "make sure there's a road between every pair of operations that need one". And the road-builders are: synchronized, volatile, atomics, thread start/join, etc.

10.5 LEVEL 2 The road-builders (happens-before edges you can use)

RulePlain English
Program orderIn a single thread, statement N happens-before statement N+1.

volatileA write to a volatile field happens-before any subsequent read of that field by another thread.

Thread joinEverything a thread did happens-before another thread's successful join() on it.
InterruptionA thread's interrupt() call happens-before the interrupted thread observes the interruption.
TransitivityIf A hb B and B hb C, then A hb C. Roads chain together.
The practical recipe

For any write you want another thread to see, ensure your code creates one of these edges:

  • You write inside a synchronized block; the other thread reads inside a synchronized block on the same lock.
  • You write to a volatile field; the other thread reads that field.
  • You use an atomic class.
  • You publish via a thread-safe collection (e.g., ConcurrentHashMap.put hb get).
  • You start the thread (the writes happened in the parent before start()).

Plain reads/writes of plain fields have no happens-before relationship across threads. Treat them as if other threads might see anything.

10.6 LEVEL 2 Safe publication — making new objects visible

"Publishing" an object means making it visible to other threads after construction. The bug to avoid: another thread sees the reference, but the fields aren't yet set.

// UNSAFE — another thread might see config != null but with default field values
public class Holder {
    public static Config config;
    public static void init() {
        config = new Config(...);   // JVM may publish reference BEFORE fields are written
    }
}

Sounds insane? It's because the constructor's writes can be reordered with the config = ... assignment. From an outside thread, you might see config != null with all primitive fields still 0 / null.

Safe publication idioms (in order of preference)

1. Static final fieldstatic final Config C = new Config(); — class-init guarantees
2. Volatile / AtomicReferencevolatile Config config;
3. Lock-protectedAlways set + read inside synchronized on the same lock
4. Thread-safe collectionStored into a ConcurrentHashMap
5. Final-field guaranteeThe object's fields are final — see 10.7

10.7 LEVEL 2 The final-field superpower

Java gives final fields a special guarantee: once the constructor returns, any thread reading the object sees the final fields fully set — without any synchronization.

public final class Point {
    private final double x, y;
    public Point(double x, double y) { this.x = x; this.y = y; }
    public double getX() { return x; }   // no synchronization needed
    public double getY() { return y; }
}
// You can share Point across threads, lock-free, with zero risk.

This is why immutable objects are automatically thread-safe. Make your data classes final + final-fields-only (or use record) and large classes of bugs simply can't happen.

Important caveat: don't leak this from the constructor

The final-field guarantee only kicks in after the constructor returns. If you give out this mid-construction (e.g., by adding it to a static list, or starting a thread that uses this), other threads can see the half-built object. Always finish constructing before publishing.

10.9 LEVEL 3 Why volatile-DCL was broken before Java 5

For the historically curious

Before Java 5, the famous "Double-Checked Locking" idiom was actually broken — the JMM at the time didn't guarantee that a thread seeing instance != null would see all the fields the constructor wrote. The 2005 JMM revision fixed this by mandating that volatile creates the necessary happens-before edge.

That's why every modern DCL example you see uses private static volatile MyClass instance — without volatile, you're back in pre-2005 broken-land. (We'll see DCL in pattern 22.9.)

10.10 LEVEL 3 What you don't need to know (but might wonder about)

  • Memory barriers / fences — CPU instructions like mfence, lfence, sfence that force ordering. Java emits them for you when you use volatile, locks, or atomics. You don't write them by hand.
  • Cache coherency protocols (MESI) — how CPUs synchronize their caches. Interesting trivia; not needed for Java code.
  • Sequential consistency — the strict "everything happens in some global order" model. The JMM is weaker than this for performance.
  • Out-of-thin-air values — a theoretical JMM corner where unsynchronized reads could return values "from the future". Doesn't happen in real JVMs but the spec works hard to forbid it.

10.11 What you've learned

  • CPUs cache, reorder, and JITs reorder. Source order is not execution order across threads.
  • Cross-thread visibility is only guaranteed when there's a happens-before edge.
  • Edge-builders: synchronized, volatile, atomics, thread start/join, thread-safe collections.
  • Final fields published after construction are visible to all threads automatically.
  • Safest design: avoid mutable shared state. Use immutable objects + queues + concurrent collections.

Part 11 — ThreadLocal

Why this part

What you'll learn

How to give each thread its own private copy of a value — no sharing, no locks, no race conditions. And the one footgun (memory leaks) that bites every team eventually.

Why it matters

Web apps use ThreadLocal constantly: per-request user IDs, trace IDs, locales, security context. SLF4J's logging context (MDC) is a ThreadLocal. Spring Security's authentication context is a ThreadLocal. You'll see it everywhere.

Plain-English summary

Imagine a locker room: each worker has their own labeled locker. They never look in each other's lockers. ThreadLocal is that locker — same variable name, but each thread sees its own copy.

11.1 What is it?

A ThreadLocal<T> gives each thread its own private copy of a value. No sharing, no synchronization, no race conditions.

public class RequestContext {
    private static final ThreadLocal<String> USER_ID = new ThreadLocal<>();

    public static void setUser(String id) { USER_ID.set(id); }
    public static String getUser() { return USER_ID.get(); }
    public static void clear() { USER_ID.remove(); }   // CRITICAL — see 11.5
}

Two threads calling setUser("alice") and setUser("bob") store into different "slots" — they don't interfere.

11.2 Real uses

Per-request context (most common)

In a Spring MVC app, a servlet filter sets USER_ID, TRACE_ID, LOCALE on the request thread. Any code deep in the call stack can read them without passing them as parameters.

@Component
public class TraceFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req,
                                    HttpServletResponse res, FilterChain chain)
            throws Exception {
        String traceId = req.getHeader("X-Trace-Id");
        if (traceId == null) traceId = UUID.randomUUID().toString();
        MDC.put("traceId", traceId);   // SLF4J's MDC IS a ThreadLocal map
        try {
            chain.doFilter(req, res);
        } finally {
            MDC.clear();   // MUST clean up
        }
    }
}

Non-thread-safe utilities

SimpleDateFormat is not thread-safe and creating new instances is expensive. Cache one per thread:

private static final ThreadLocal<SimpleDateFormat> FMT =
    ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

public String format(Date d) { return FMT.get().format(d); }

(In Java 8+ just use DateTimeFormatter — it's already thread-safe and you don't need ThreadLocal.)

11.3 InheritableThreadLocal

Child threads inherit a snapshot of the parent's value at start() time.

private static final InheritableThreadLocal<String> TENANT = new InheritableThreadLocal<>();

TENANT.set("acme");
new Thread(() -> System.out.println(TENANT.get())).start();   // "acme"
Watch out

It's a one-time copy at thread start. Subsequent changes in the parent are NOT seen by the child. Also, thread pools reuse threads — inherited values from the original creator stick around. Use TransmittableThreadLocal (Alibaba) or a custom ExecutorService wrapper for pooled scenarios.

11.4 The big footgun: memory leaks

This is the most-dangerous part of ThreadLocal, and it bites everyone in production at least once.

Why ThreadLocals leak

A ThreadLocal is implemented as a map on each Thread object: Thread.threadLocals. Keys are weak references to the ThreadLocal object; values are strong references.

If you set a value and never remove(), the value lives as long as the thread does. In a thread pool, threads live forever → values accumulate → OOM.

Worse: if your value's class loader gets unloaded (e.g., webapp redeploy in Tomcat), the strong reference from the threadLocals map prevents GC of the entire ClassLoader → "metaspace leak" warnings.

11.5 The discipline

try {
    USER_ID.set(currentUser());
    chain.doFilter(req, res);
} finally {
    USER_ID.remove();   // always
}

Or use a try-with-resources wrapper:

public static AutoCloseable setUser(String id) {
    USER_ID.set(id);
    return USER_ID::remove;
}

try (AutoCloseable __ = RequestContext.setUser("alice")) {
    doWork();
}   // auto-cleared on exit

11.6 Performance

ThreadLocal.get() is ~5-15ns — a hash lookup on the thread's own map. Cheap, but not free. In hot paths, cache the value into a local variable.

11.7 Java 21+: ScopedValue

Java 21 introduced ScopedValue as a structured, leak-proof alternative. Values are valid only within a lexical scope — perfect with virtual threads.

final static ScopedValue<String> USER = ScopedValue.newInstance();

ScopedValue.where(USER, "alice").run(() -> {
    handleRequest();   // USER.get() returns "alice" anywhere in here
});
// Outside the scope, USER.isBound() is false. No remove() needed.
Decision
  • Java 21+ + virtual threads → use ScopedValue.
  • Otherwise → ThreadLocal with strict remove() in finally.
  • Spring/SLF4J users get RequestContextHolder / MDC for free — just remember they're thread-local.

Part 12 — Executor Framework

Why this part

What you'll learn

The thread pool — a small, fixed number of reusable worker threads that process tasks from a queue. The right way to run async work in production Java.

Why it matters

This is the most important pattern in the entire guide. Every Spring Boot app uses thread pools. Every Tomcat server uses thread pools. Every CompletableFuture you write next chapter runs on a thread pool. If you only learn one thing past Part 5, learn this.

Plain-English summary

Don't create a new thread every time you have something async to do. Instead, hire a small fixed team of workers. When you have work, drop it into their inbox (a queue). They pick it up, do it, and come back for more.

That's it. That's the whole concept. The rest of the chapter is about configuring this team — how big, what to do when their inbox is full, how to clean up gracefully.

12.1 LEVEL 1 Why not just use new Thread()?

You can spin up a new thread for every task. Don't. Here's why:

ProblemWhy it bites
Each thread costs ~1 MB of stack memory10,000 threads = 10 GB. Your laptop dies.
Thread creation is slow (~ms each)Per-request creation tanks throughput.
Unbounded threads → context switching dominatesCPU spends all its time switching, none actually working.
You'd reinvent queueing, sizing, error handlingAnd you'd do it badly.

The Executor framework solves all of this. It separates two concerns:

  • What to run — your code, packaged as a Runnable or Callable.
  • How to run it — the executor (a thread pool with extras).

12.2 LEVEL 1 The simplest example

import java.util.concurrent.*;

// 1. Create a pool of 4 worker threads
ExecutorService pool = Executors.newFixedThreadPool(4);

// 2. Submit tasks — fire-and-forget, returns immediately
for (int i = 0; i < 10; i++) {
    final int id = i;
    pool.submit(() -> {
        System.out.println("Task " + id + " on " + Thread.currentThread().getName());
    });
}

// 3. When done, shut down (waits for queued tasks)
pool.shutdown();
pool.awaitTermination(10, TimeUnit.SECONDS);

Task 0 on pool-1-thread-1 Task 1 on pool-1-thread-2 Task 2 on pool-1-thread-3 Task 3 on pool-1-thread-4 Task 4 on pool-1-thread-1 ← reused! Task 5 on pool-1-thread-2 ...

12.7 LEVEL 2 The execution algorithm (counter-intuitive!)

When you call pool.submit(task):

  1. If < corePoolSize threads exist → create a new thread for this task.
  2. Else, if there's room in the queue → put it in the queue.
  3. Else, if < maximumPoolSize threads → create a new (temp) thread.
  4. Else → reject via the rejection handler.
The "max threads doesn't matter" trap

Notice step 2: queue first, expand pool second. That means if your queue is unbounded (like the default LinkedBlockingQueue), step 2 always succeeds — and your pool never grows past corePoolSize, no matter how big you set max!

People set core=10, max=100 and wonder why they only ever see 10 threads. Now you know: the queue ate the work first.

Fix: use a bounded queue (ArrayBlockingQueue, or LinkedBlockingQueue with explicit capacity). Then full queue → step 3 → pool grows.

Backend queue called from sync API: use CallerRunsPolicy. The HTTP thread itself runs the task — beautifully throttling the API by making it slow when overloaded.

12.10 LEVEL 2 Graceful shutdown

public void shutdownGracefully(ExecutorService pool, Duration timeout) {
    pool.shutdown();    // stop accepting new tasks; let queued tasks finish
    try {

            log.warn("Pool didn't terminate in time, forcing shutdown");
            List<Runnable> dropped = pool.shutdownNow();   // interrupt + drain
            log.warn("Dropped {} tasks", dropped.size());
        }
    } catch (InterruptedException e) {
        pool.shutdownNow();
        Thread.currentThread().interrupt();
    }
}

  • ✅ Always name your threads with a meaningful prefix.
  • ✅ Always use a bounded queue + a deliberate rejection policy.
  • ✅ Always set an UncaughtExceptionHandler on the ThreadFactory.
  • ✅ Always pass a timeout to future.get().
  • ✅ Always call shutdown() + awaitTermination() on app stop.
  • ✅ Use separate pools for distinct workloads (DB vs HTTP vs CPU).
  • ❌ Don't use Executors.newCachedThreadPool() in production.
  • ❌ Don't block while holding a lock — you'll exhaust the pool.

Part 13 — ScheduledExecutorService

Why this part

What you'll learn

How to schedule tasks to run after a delay ("send reminder in 5 minutes") or repeatedly ("flush metrics every 10 seconds"). The thread-pool cousin that handles time.

Why it matters

Every server has scheduled tasks: cache refreshers, metric flushes, heartbeats, cleanup jobs, periodic health checks. ScheduledExecutorService is the standard way. Plus it has one famous trap (silent kills on exception) that's caused countless silent monitoring outages — we'll cover that.

For delayed and periodic tasks. Replaces the legacy java.util.Timer (which has dangerous behaviour — one bad task kills the whole timer thread).

13.1 The four scheduling methods

ScheduledExecutorService sched = Executors.newScheduledThreadPool(2);

// 1) Run once after a delay
sched.schedule(() -> log.info("5s passed"), 5, TimeUnit.SECONDS);

// 2) Periodic at fixed RATE — next start = previous start + period (regardless of duration)
sched.scheduleAtFixedRate(this::heartbeat, 0, 10, TimeUnit.SECONDS);

// 3) Periodic with fixed DELAY — next start = previous END + delay
sched.scheduleWithFixedDelay(this::poll, 0, 10, TimeUnit.SECONDS);

// 4) Schedule a Callable to get a result later
ScheduledFuture<String> f = sched.schedule(() -> compute(), 1, TimeUnit.SECONDS);

13.2 fixedRate vs fixedDelay — pick carefully

fixedRate (period=10s, task takes 3s): start@0 ─┐ start@10 ─┐ start@20 ─┐ end@3 │ end@13 │ end@23 │ ← runs every 10s, on the dot fixedRate when task takes 12s (longer than period!): start@0 ───────── end@12 start@12 (immediately!) ───────── end@24 ← back-to-back — careful! fixedDelay (delay=10s, task takes 3s): start@0 ─ end@3 ─wait─ start@13 ─ end@16 ─wait─ start@26 ← exactly 10s gap between runs
Use fixedRate whenUse fixedDelay when
You want a steady cadence (heartbeat, metrics flush)You don't want overlapping runs (DB cleanup, polling external service)
Tasks are fast and boundedTask duration varies and may exceed the interval

13.3 The silent-killer bug

If your scheduled task throws, scheduling stops

If scheduleAtFixedRate's task throws an uncaught exception, the periodic schedule is cancelled silently. No more invocations. No log, unless you check the ScheduledFuture.

Cause: a billion silent monitoring outages.

// CORRECT: catch everything inside the task
sched.scheduleAtFixedRate(() -> {
    try {
        flushMetrics();
    } catch (Throwable t) {     // even Errors
        log.error("flushMetrics failed", t);
    }
}, 0, 10, TimeUnit.SECONDS);

13.4 Cron-like scheduling

ScheduledExecutorService doesn't do cron expressions. For "every Monday 3am", use:

  • Spring: @Scheduled(cron = "0 0 3 * * MON")
  • Quartz for advanced features (clustering, persistence)
  • For simple delays, compute the next-run Duration and call schedule recursively from inside the task.

13.5 Real example: a self-rescheduling job

public class DailyReportJob {
    private final ScheduledExecutorService sched;

    public void start() { scheduleNext(); }

    private void scheduleNext() {
        ZonedDateTime now = ZonedDateTime.now(ZoneId.of("UTC"));
        ZonedDateTime next = now.toLocalDate().atStartOfDay(now.getZone()).plusDays(1);
        long delayMs = Duration.between(now, next).toMillis();
        sched.schedule(this::run, delayMs, TimeUnit.MILLISECONDS);
    }

    private void run() {
        try { generateReport(); }
        catch (Throwable t) { log.error("report failed", t); }
        finally { scheduleNext(); }   // always re-schedule
    }
}

Part 14 — CompletableFuture (Deep Dive) CRITICAL

Why this part

What you'll learn

How to chain async operations together cleanly: "fetch the user, then fetch their orders, then combine into a profile, with a 2-second timeout, returning a fallback on error." All without blocking, all readable.

Why it matters

If Part 12 (Executors) is the most important infrastructure in this guide, CompletableFuture is the most important API. Every modern backend Java codebase uses it. Senior interviews will ask. Without it, you write callback-pyramid spaghetti.

Plain-English summary

A Future is "a promise that a value will be there later". You ask for it, it tells you "not yet", you wait. Plain Future only lets you wait — you can't say "and then do X with it". CompletableFuture adds the "and then" — chaining, combining, error handling, timeouts. Like JavaScript Promises, if you've used those.

14.1 LEVEL 1 The problem in pictures

Suppose you need to: fetch a user, then fetch their orders using their user ID, then save a report. With plain Future:

// Plain Future — clunky and blocking
Future<User> userF = pool.submit(() -> userClient.find(id));
User user = userF.get();                 // blocks!
Future<List<Order>> ordersF = pool.submit(() -> orderClient.list(user.id));
List<Order> orders = ordersF.get();      // blocks again!
saveReport(user, orders);

Look at the .get() calls. Each one freezes the calling thread until the result is ready. We're not running these in parallel — we're serialising them via the pool. Bad.

With CompletableFuture:

CompletableFuture.supplyAsync(() -> userClient.find(id), pool)
    .thenCompose(user -> CompletableFuture.supplyAsync(() -> orderClient.list(user.id), pool)
        .thenApply(orders -> saveReport(user, orders)));

No blocking. The callback chain itself runs as each step completes. Whatever thread happens to be free picks up the next step.

14.2 LEVEL 1 Creating a CompletableFuture

// 1. Already-completed (useful for tests, fallbacks)
CompletableFuture<String> done   = CompletableFuture.completedFuture("hi");
CompletableFuture<String> failed = CompletableFuture.failedFuture(new RuntimeException("oops"));

// 2. Run a Runnable (no return value) on a thread pool
CompletableFuture<Void> r = CompletableFuture.runAsync(() -> log.info("hello"), pool);

// 3. Run a Supplier (returns a value) on a thread pool
CompletableFuture<String> s = CompletableFuture.supplyAsync(() -> fetchUrl(url), pool);

// 4. Manually completed — for adapting callback-style APIs
CompletableFuture<String> cf = new CompletableFuture<>();
asyncClient.fetch(url, (result, err) -> {
    if (err != null) cf.completeExceptionally(err);
    else             cf.complete(result);
});
⚠️ Always pass an executor for I/O

If you call supplyAsync(supplier) without an executor, it runs on the common ForkJoinPool — a small, shared, JVM-wide pool sized for CPU work. Doing blocking I/O on it can stall every parallel stream and CompletableFuture in the JVM.

Always be explicit: supplyAsync(supplier, myExecutor) for I/O.

14.4 LEVEL 1 Chaining when the next step is also async — thenCompose

Most async chains: step 2 is itself an async call.

// Wrong — gives you a future-of-a-future, weird and useless
CompletableFuture<CompletableFuture<Profile>> bad =
    fetchUserId().thenApply(id -> fetchProfile(id));   // fetchProfile returns CF

// Right — flat future
CompletableFuture<Profile> good =
    fetchUserId().thenCompose(id -> fetchProfile(id));
Analogy

thenApply is map in functional programming.
thenCompose is flatMap — for when your callback returns a "wrapped" value that needs unwrapping.

Rule of thumb: if your callback ends with return someCompletableFuture, use thenCompose. Otherwise, thenApply.

14.5 LEVEL 1 Combining two parallel results — thenCombine

    (user, orders) -> new Profile(user, orders));

14.7 LEVEL 1 Timeouts (Java 9+)

fetchUrl(url)
    .orTimeout(2, TimeUnit.SECONDS)               // completes exceptionally after 2s
    .completeOnTimeout("FALLBACK", 2, TimeUnit.SECONDS); // completes with fallback after 2s

Always set timeouts on external calls. Without one, a hung dependency can pile up requests until you run out of threads.

14.8 LEVEL 2 The "Async" suffix — where does the callback run?

This trips up everyone who learns CompletableFuture. Each chaining method has THREE variants:

VariantWhere the callback runs
thenApply(fn)The thread that completed the previous stage (or the caller, if already done)
thenApplyAsync(fn)ForkJoinPool.commonPool() — careful, see warning below
thenApplyAsync(fn, executor)Your provided executor — preferred for production
Why this matters more than it looks

Without "Async", a callback runs on whatever thread completed the parent. If that's a Netty I/O thread, your callback runs there too — and a slow callback stalls all I/O. If it's the calling thread (because the parent was already done), it runs synchronously.

For non-trivial logic in a chain: always use the Async variant with an explicit executor. Predictable threading.

14.9 LEVEL 2 allOf and anyOf — fan-out / fan-in

// Wait for ALL — completes when last finishes
CompletableFuture.allOf(f1, f2, f3)
    .thenRun(() -> {
        // All done; safely call .join() on each
        List<String> results = List.of(f1.join(), f2.join(), f3.join());
    });

// Wait for ANY — completes as soon as one finishes (success OR failure!)
CompletableFuture.anyOf(f1, f2, f3)
    .thenAccept(first -> log.info("first: {}", first));
Helper: a nicer "allOf" that returns the list

The built-in allOf returns CompletableFuture<Void> — annoying. Most teams write a helper:

public static <T> CompletableFuture<List<T>> sequence(List<CompletableFuture<T>> futures) {
    return CompletableFuture
        .allOf(futures.toArray(new CompletableFuture[0]))
        .thenApply(v -> futures.stream().map(CompletableFuture::join).toList());
}

14.10 LEVEL 2 Real example: parallel API aggregator

The pattern for building a "page" from multiple microservices in parallel — with timeouts and graceful degradation:

public class DashboardService {
    private final ExecutorService pool = Executors.newFixedThreadPool(20);

    public Dashboard load(long userId) {
        CompletableFuture<User>        user    = call(() -> userClient.find(userId),     User.empty());
        CompletableFuture<List<Order>> orders  = call(() -> orderClient.list(userId),    List.of());
        CompletableFuture<Wallet>      wallet  = call(() -> walletClient.balance(userId), Wallet.empty());
        CompletableFuture<Feed>        feed    = call(() -> feedClient.recommend(userId), Feed.empty());

        return CompletableFuture.allOf(user, orders, wallet, feed)
            .thenApply(v -> new Dashboard(user.join(), orders.join(), wallet.join(), feed.join()))
            .orTimeout(2, TimeUnit.SECONDS)
            .exceptionally(ex -> Dashboard.empty())
            .join();
    }

    private <T> CompletableFuture<T> call(Supplier<T> s, T fallback) {
        return CompletableFuture.supplyAsync(s, pool)
            .completeOnTimeout(fallback, 800, TimeUnit.MILLISECONDS)
            .exceptionally(ex -> { log.warn("call failed", ex); return fallback; });
    }
}
Real case: Netflix Hystrix → Resilience4j

This pattern (parallel calls + per-call timeouts + fallbacks + global timeout) is exactly what Netflix's Hystrix popularised. Today, Resilience4j layers on circuit breakers, bulkheads, retries — but the core CompletableFuture composition is the same. Every modern Java backend has some flavour of this.

14.11 LEVEL 3 Retry with exponential backoff

public <T> CompletableFuture<T> retry(Supplier<CompletableFuture<T>> op, int attempts, long delayMs) {
    return op.get().handle((result, ex) -> {
        if (ex == null)        return CompletableFuture.completedFuture(result);
        if (attempts <= 1)     return CompletableFuture.<T>failedFuture(ex);
        return delayed(delayMs).thenCompose(v -> retry(op, attempts - 1, delayMs * 2));
    }).thenCompose(Function.identity());
}

private CompletableFuture<Void> delayed(long ms) {
    CompletableFuture<Void> cf = new CompletableFuture<>();
    scheduler.schedule(() -> cf.complete(null), ms, TimeUnit.MILLISECONDS);
    return cf;
}

Part 15 — Fork/Join Framework

Why this part

What you'll learn

A specialised thread pool for recursive divide-and-conquer tasks (sort an array, walk a tree, sum a million numbers). Uses "work-stealing" for near-linear scaling on pure CPU work.

Why it matters

Day-to-day, you'll rarely use Fork/Join directly. But it powers parallelStream() and is the default executor for CompletableFuture's "Async" methods — so knowing it explains those better. And for CPU-bound batch jobs, it can give near-linear speedup with surprisingly little code.

Beginner advice

Skim on first pass. Not needed for correct concurrent code.

Fork/Join (Java 7+) is a thread pool optimised for recursive divide-and-conquer CPU-bound work. It powers parallel streams.

15.1 Work-stealing — the secret sauce

In a normal pool, all workers pull from a single queue → contention. In Fork/Join, each worker has its own deque:

Worker-1: [t1, t2, t3] ← own deque Worker-2: [t4] Worker-3: [] ← idle! When Worker-3 is idle, it "steals" from Worker-1's deque tail. Result: very low contention, near-linear scaling on CPU work.

15.2 The pattern: RecursiveTask / RecursiveAction

public class SumTask extends RecursiveTask<Long> {
    private final int[] arr;
    private final int lo, hi;
    private static final int THRESHOLD = 10_000;

    public SumTask(int[] arr, int lo, int hi) {
        this.arr = arr; this.lo = lo; this.hi = hi;
    }

    @Override
    protected Long compute() {
        if (hi - lo <= THRESHOLD) {
            long sum = 0;
            for (int i = lo; i < hi; i++) sum += arr[i];
            return sum;
        }
        int mid = (lo + hi) >>> 1;
        SumTask left  = new SumTask(arr, lo, mid);
        SumTask right = new SumTask(arr, mid, hi);
        left.fork();                            // schedule left for some worker
        long rightResult = right.compute();      // run right on this thread
        long leftResult  = left.join();          // wait for left
        return leftResult + rightResult;
    }
}

ForkJoinPool pool = ForkJoinPool.commonPool();
long total = pool.invoke(new SumTask(arr, 0, arr.length));

15.3 Best practices

  • Choose THRESHOLD wisely — too small means tons of fork overhead; too large means wasted parallelism. Rule of thumb: aim for tens of thousands of operations per leaf.
  • Pure CPU only — never block in fork/join tasks (no I/O, no synchronized contended locks). Blocking starves the pool.
  • Don't use commonPool for app work — it's shared across the JVM (parallel streams use it too). Create your own ForkJoinPool for serious CPU work.
  • Fork right, compute left — minor perf win and keeps stack manageable.
When to use Fork/Join
  • Pure CPU-bound recursive problems: tree walks, matrix ops, sort/merge, image processing.
  • Where you can recursively halve until a sequential threshold.

Don't use it for I/O — that's what regular thread pools (or virtual threads) are for.

Part 16 — Parallel Streams

Why this part

What you'll learn

How to add a single .parallel() call to a Java stream and have it process millions of elements concurrently. And — crucially — when this is a great idea vs a terrible one.

Why it matters

Parallel streams look magical for tutorials. In production they're a sharp knife. Used right, you get free 8× speedups on bulk transformations. Used wrong, you stall every async operation in your JVM. The trick is knowing the difference.

Java 8 streams have a parallel() mode that runs operations concurrently on the Fork/Join common pool.

long total = numbers.parallelStream()
    .filter(n -> n % 2 == 0)
    .mapToLong(Integer::longValue)
    .sum();

16.1 When parallel streams shine

  • Large dataset (millions of elements).
  • Per-element work is non-trivial CPU (e.g., parsing, hashing, math).
  • Operations are stateless and side-effect-free.
  • Source supports cheap splitting (ArrayList, arrays).

16.2 When they're a trap

The commonPool problem

parallelStream uses ForkJoinPool.commonPool() by default. One slow operation can starve all parallel streams in the JVM. If you must use parallel streams for serious work, run them inside your own ForkJoinPool:

ForkJoinPool pool = new ForkJoinPool(8);
pool.submit(() -> data.parallelStream().map(...).collect(...)).get();

16.3 Real example: parsing 1M log lines

List<LogLine> parsed = lines.parallelStream()
    .map(LogParser::parse)
    .filter(line -> line.severity() >= Severity.WARN)
    .collect(Collectors.toList());

On an 8-core machine, ~6× speedup is realistic.

Rule of thumb

Parallel streams are great for pure-CPU bulk transformations on big in-memory collections. For everything else (especially I/O), use CompletableFuture with an explicit executor, or virtual threads.

Part 17 — Virtual Threads (Project Loom, Java 21+)

Why this part

What you'll learn

A new kind of thread (Java 21+) that's so cheap you can have millions of them. It changes how we structure server code: instead of "200 worker threads sharing a pool", you give every request its own dedicated thread.

Why it matters

This is the biggest concurrency change in Java's history. It makes the simple "thread per request" model practical at any scale — without rewriting your code in reactive style. If you work on backend Java, this is your future.

Plain-English summary

Old (platform) threads are real OS workers — fancy, expensive, ~1 MB each, ~ms to create. You can afford ~1000 in a JVM.

Virtual threads are fake "lightweight workers" managed by the JVM, riding on top of a small fixed pool of real ones. They cost a few KB each and you can have millions. When one blocks (waiting for DB, etc.), the JVM moves it off its real worker and runs another. The real workers stay busy.

17.1 LEVEL 1 The problem they solve

You're building a backend API. Each request takes ~150ms — almost all of it spent waiting:

Request handling timeline (typical): Compute (parse, validate) : 5ms ▓ DB query : 50ms ▓▓▓▓▓▓▓▓▓▓ (waiting) Compute (transform) : 5ms ▓ Call external API : 100ms ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ (waiting) Response : 5ms ▓ Total: 165ms. CPU work: 15ms. The thread is BLOCKED for 150ms.

If you have 200 worker threads, you can serve only 200 concurrent requests — even though 150/165ms of each is just "waiting around".

Old workarounds — both painful:

  • Bigger thread pools — but each thread costs ~1 MB. 10,000 threads = 10 GB just for stacks.
  • Reactive code (WebFlux/Mono) — non-blocking, but you rewrite everything as callbacks. Stack traces become useless. Debugging is misery.

Virtual threads give you the best of both: simple, blocking-style code that scales to millions of concurrent requests.

17.2 LEVEL 1 How they work — the carrier model

Many virtual threads (cheap, ~few KB each) ────────────────────────────────────────── VT-1 VT-2 VT-3 VT-4 VT-5 ... VT-1,000,000 When a VT runs, it sits on top of a real thread: VT-3 (running) VT-7 (running) │ │ ▼ ▼ Carrier-1 Carrier-2 ... ← real OS threads (~N_cpu of them) ───────────────────────────────── Sequence when VT-3 calls a blocking I/O: 1. JVM detects: VT-3 about to block 2. JVM saves VT-3's stack to the heap (a "continuation") 3. JVM unmounts VT-3 from Carrier-1 4. JVM picks another ready VT (say VT-9), mounts it on Carrier-1 5. Carrier-1 keeps working — never idle! 6. When VT-3's I/O completes, JVM remounts it on a free carrier
Analogy: actors and stages

The carrier threads are stages (real, fixed in number — say 8). Virtual threads are actors (millions of them, each with their own role).

An actor stands on a stage and acts. When the actor's role calls for them to "go offstage and wait" (blocking I/O), they leave the stage. Another actor steps onto the empty stage immediately. When the first actor's "wait" is over, they come back to whichever stage is free.

Stages are never empty when there's work to do. And you can have a million actors — they're free. That's virtual threads.

17.3 LEVEL 1 Using virtual threads

Thread.startVirtualThread(() -> log.info("hi from a virtual thread"));

// 2. With a builder (named, useful for debugging)
Thread t = Thread.ofVirtual()
    .name("order-vt-", 0)         // auto-numbered: order-vt-0, order-vt-1, ...
    .start(() -> processOrder(o));

// 3. As an ExecutorService — best for migrating existing thread-pool code

    for (Request req : requests) {
        exec.submit(() -> handle(req));   // each task → its own VT
    }
}   // auto-shuts down at end of try-with-resources

17.4 LEVEL 1 The migration story (it's almost too easy)

Most existing thread-pool code becomes virtual-thread code by changing one line:

// Before
ExecutorService pool = Executors.newFixedThreadPool(200);

// After (Java 21+)
ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor();

Spring Boot 3.2+ and Tomcat 10.1+ have built-in virtual-thread modes. In application.properties:

spring.threads.virtual.enabled=true

Now Tomcat handles every request on its own VT. Your existing controller code keeps working — but the server scales 100× better for I/O-heavy workloads.

17.5 LEVEL 2 The "pinning" problem

There's one catch in Java 21–23: virtual threads cannot unmount from their carrier in two situations:

  1. Inside a synchronized block (fixed in Java 24).
  2. Inside native code (JNI).

If a VT blocks while pinned, it pins the carrier thread too — defeating the whole point. With enough pinning, you exhaust the small carrier pool and your service slows down dramatically.

Detect and fix pinning

Run with -Djdk.tracePinnedThreads=full to log when pinning happens.

The fix is usually one of:

  • Replace synchronized with ReentrantLock — locks don't pin.
  • Move I/O calls outside synchronized blocks (good practice anyway).
  • Upgrade to Java 24+ which removes the synchronized limitation.

17.6 LEVEL 2 Pool sizing becomes irrelevant — but backpressure does not

With VTs, the old "carefully size your pool to N=200" art goes away. Just spawn one per task.

But — and this matters — your downstream resources still have limits. Your DB might handle 50 concurrent connections. Don't fire a million queries at it!

Backpressure moves from "queue size" to "permits on a Semaphore guarding the dependency":

public class UserRepo {
    private final Semaphore dbPermits = new Semaphore(50);   // max 50 concurrent DB calls

    public User find(long id) throws InterruptedException {
        dbPermits.acquire();   // extra VTs wait politely here
        try {
            return jdbc.query("...", id);
        } finally {
            dbPermits.release();
        }
    }
}

Even with a million VTs in the JVM, only 50 will actually hit the database concurrently. The rest queue at the semaphore — cheaply, since each VT costs almost nothing.

17.7 LEVEL 2 ThreadLocal under VTs — and ScopedValue

ThreadLocal still works, but it has a problem at scale: a million VTs each holding a 1 KB ThreadLocal value = 1 GB of memory. And each VT has its own — even if 99% never read it.

Java 21 introduced ScopedValue as a structured replacement (we covered it in Part 11.7). Recap:

final static ScopedValue<String> USER = ScopedValue.newInstance();

ScopedValue.where(USER, "alice").run(() -> {
    handleRequest();   // USER.get() returns "alice" anywhere in this call tree
});
// Outside the run() block, USER.isBound() is false. No leak risk.

17.9 LEVEL 3 What's actually happening underneath

For the curious, here's a deeper picture:

  • Continuations — A virtual thread's stack is reified as a Java object on the heap. When it blocks, the runtime captures the continuation; when it resumes, the runtime re-installs it on a carrier. This is the JVM-level mechanism that makes VTs cheap to suspend.
  • JDK rewiring — The Java standard library (java.net, java.io, java.util.concurrent) was rewritten to be VT-aware. When a VT calls InputStream.read on a socket, it doesn't actually block its OS thread — it parks the VT in non-blocking mode under the hood and unmounts.
  • Carrier pool — By default, the carrier pool size = Runtime.getRuntime().availableProcessors(). You don't tune this directly. It's a ForkJoinPool internally.
Real case: a million concurrent connections

The Helidon and Micronaut teams demonstrated single JVMs serving over a million concurrent HTTP connections using virtual threads — on a laptop. Java's "thread pool sizing" career skill is gradually becoming obsolete for I/O workloads. Pretty soon, "use virtual threads" will be the default answer to most concurrency questions.

17.10 What you've learned

  • Virtual threads = lightweight (KB), millions possible.
  • The JVM mounts/unmounts them on a small carrier pool of real threads.
  • "Thread per request" becomes practical at any scale.
  • One-line migration from old thread pools.
  • Watch out for pinning (Java 21–23): replace synchronized with ReentrantLock when possible.
  • Backpressure shifts from queue depth to semaphores on downstream resources.
  • Don't use VTs for CPU-bound work.

Part 18 — Structured Concurrency (Java 21+ preview)

Why this part

What you'll learn

A new pattern that pairs with virtual threads: "if a method spawns sub-tasks, all of them must finish before the method returns." Treats a group of concurrent tasks as one unit — like a try-with-resources block, but for concurrency.

Why it matters

Solves the biggest mess in concurrent code: orphaned tasks. You spawn 3 things, one fails, the other two leak running, the failure gets buried, and you have no clue what's happening. Structured concurrency makes that impossible — failures cancel siblings automatically, lifetimes are nested, debugging becomes sane.

Beginner advice

Still preview / incubating in Java 21–23. Worth learning to be future-ready, but most production code in 2024 still uses CompletableFuture.

Pair to virtual threads. Solves "concurrent code is unstructured": you spawn 3 tasks, one fails, the other two leak running, exceptions get lost.

The principle: if a task spawns subtasks, those subtasks must complete before the parent returns. Lifetimes are nested, like try/finally — but for concurrency.

18.1 The shape

try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Subtask<User>        u = scope.fork(() -> userClient.find(id));
    Subtask<List<Order>> o = scope.fork(() -> orderClient.list(id));

    scope.join();             // wait for all subtasks
    scope.throwIfFailed();    // throw if any failed

    return new Profile(u.get(), o.get());
}

  • ShutdownOnFailure — first failure cancels siblings (like allOf + fail-fast).
  • ShutdownOnSuccess<T> — first success cancels siblings (like anyOf).

18.4 First-success example

    try (var scope = new StructuredTaskScope.ShutdownOnSuccess<String>()) {

        scope.fork(() -> ddg.search(q));
        return scope.join().result();   // first one wins; others cancelled
    }
}
When to use

For new Java 21+ code, structured concurrency + virtual threads is the cleanest model for parallel I/O. For older Java, CompletableFuture remains the standard.

Part 19 — Spring @Async

Why this part

What you'll learn

Spring's @Async annotation: slap it on a method, and Spring runs that method on a thread pool of your choice instead of the calling thread. Plus the famous proxy gotcha that breaks it silently.

Why it matters

Most Java backends are Spring Boot. @Async is everywhere. But it has more footguns than any other concurrency feature in this guide — self-invocation, lost MDC context, lost transactions, lost security context. Knowing them up front saves a lot of "but it works in tests!" bugs.

If you work in Spring (very likely in Java backend), @Async is the idiomatic way to run methods on a separate thread.

19.3 The proxy gotcha (#1 @Async bug)

Self-invocation breaks @Async

Spring's @Async works via a proxy. Calls from inside the same class skip the proxy — so @Async is silently ignored.

@Service
public class UserService {
    public void register(User u) {
        save(u);
        sendWelcome(u);   // ❌ runs synchronously! Self-call.
    }
    @Async
    public void sendWelcome(User u) { ... }
}

Fix: put the @Async method in a different bean, or inject self via @Autowired ApplicationContext / @Lazy self-reference.

19.4 Other @Async pitfalls

  • Return type: only void, Future<T>, or CompletableFuture<T>. Other return types are silently ignored / set to null.
  • Exceptions in void @Async methods are lost — only the configured AsyncUncaughtExceptionHandler sees them. Prefer returning CompletableFuture so caller can handle errors.
  • No transaction propagation — @Async methods run on a different thread, so the caller's @Transactional doesn't extend to them. Re-annotate the @Async method if it needs its own transaction.
  • SecurityContext doesn't propagate by default. Use DelegatingSecurityContextAsyncTaskExecutor if needed.
  • MDC (logging context) doesn't propagate. Decorate the executor with a task decorator that copies MDC.

19.5 Real production setup with MDC propagation

ThreadPoolTaskExecutor e = new ThreadPoolTaskExecutor();
e.setTaskDecorator(runnable -> {
    Map<String,String> ctx = MDC.getCopyOfContextMap();
    return () -> {
        Map<String,String> old = MDC.getCopyOfContextMap();
        try {
            if (ctx != null) MDC.setContextMap(ctx);
            runnable.run();
        } finally {
            if (old != null) MDC.setContextMap(old); else MDC.clear();
        }
    };
});
Real case: where async logging stops working

Your beautiful traceId in logs vanishes the moment @Async kicks in — child thread doesn't have the MDC. The decorator above fixes it. Most production Spring apps need this.

Part 20 — Concurrent Collections

Why this part

What you'll learn

Drop-in replacements for HashMap, ArrayList, etc. that are designed for concurrent use. Plus BlockingQueue — the most useful concurrent class you've never heard of.

Why it matters

Most multi-threaded data sharing should go through a concurrent collection — not a locked plain collection. They're faster (lock-striped or lock-free internally) and have atomic compound methods (computeIfAbsent, merge) that prevent the check-then-act bugs from Part 5.

Plain-English summary

Three families to know: ConcurrentHashMap (thread-safe map, daily driver), CopyOnWriteArrayList (read-mostly list, like event listeners), and BlockingQueue (the bridge between producer and consumer threads).

Plain HashMap, ArrayList are not thread-safe — concurrent mutation can corrupt internal state (HashMap can even spin forever in old Java due to a bad rehash).

Collections.synchronizedMap(...) wraps with a single big lock — works but kills throughput. The java.util.concurrent collections are designed for high concurrency.

Part 21 — Synchronizers

Why this part

What you'll learn

Five small classes that solve common coordination problems: CountDownLatch ("wait until N events happen"), CyclicBarrier ("N peers meet here"), Semaphore ("at most N at a time"), Phaser (advanced barrier), Exchanger ("two threads swap data").

Why it matters

These are the "right tool for the job" for many patterns. Trying to build a "wait for 3 services to start" with locks alone is painful — CountDownLatch does it in 3 lines. Knowing they exist is half the win.

21.1 CountDownLatch — wait for N events to happen once

One-shot. Threads call await() until the counter reaches 0 (decremented by countDown()).

// "Wait for 3 services to start before accepting traffic"
CountDownLatch ready = new CountDownLatch(3);

Runnable startService = () -> {
    initialize();
    ready.countDown();
};
new Thread(startService).start();
new Thread(startService).start();
new Thread(startService).start();

ready.await();   // blocks until all 3 done
log.info("All services up");
Use cases
  • App startup gate ("don't accept requests until all dependencies ready").
  • Test synchronization ("wait until all worker threads observed the event").
  • Parallel-then-merge: spawn N tasks, latch counts down, main waits then aggregates.

Cannot be reset. Use CyclicBarrier if you need re-use.

21.2 CyclicBarrier — N threads meet at a point, all proceed together

// 4 simulation workers, each runs phases; all wait for each other between phases
CyclicBarrier barrier = new CyclicBarrier(4, () ->
    log.info("Phase complete; advancing"));   // optional barrier action

for (int p = 0; p < 10; p++) {
    runPhase();
    barrier.await();    // each thread blocks until all 4 arrive
}

21.3 Semaphore — control how many can enter

// Allow at most 5 concurrent calls to a 3rd-party API
Semaphore permits = new Semaphore(5);

public Result call() throws InterruptedException {
    permits.acquire();
    try { return http.get(url); }
    finally { permits.release(); }
}

Like a mutex with N permits. Permits are not tied to threads — any thread can release a permit acquired by another (handy for handoff patterns, dangerous if used wrong).

21.4 Phaser — flexible, dynamic barrier

Like CyclicBarrier but parties can register/deregister mid-flight, and you can have multiple phases of different sizes. Niche but powerful for staged pipelines.

21.5 Exchanger — two threads swap a value

Exchanger<Buffer> ex = new Exchanger<>();

// Thread A — fills a buffer, then swaps for an empty one
Buffer myBuf = new Buffer();
fill(myBuf);
myBuf = ex.exchange(myBuf);   // blocks until B arrives

// Thread B — drains, then swaps
Buffer myBuf2 = new Buffer();
drain(myBuf2);
myBuf2 = ex.exchange(myBuf2);

Useful for double-buffering pipelines.

This is where everything you've learned comes together. Each pattern is taken from real production systems.

22.1 Producer-Consumer Pipeline

Goal: producers add work, consumers process it, with backpressure and graceful shutdown.

public class OrderPipeline {
    private final BlockingQueue<Order> queue = new ArrayBlockingQueue<>(1000);
    private final List<Thread> consumers = new ArrayList<>();
    private final AtomicBoolean running = new AtomicBoolean(true);

    public void start(int consumerCount) {
        for (int i = 0; i < consumerCount; i++) {
            Thread t = new Thread(this::consume, "order-consumer-" + i);
            t.start();
            consumers.add(t);
        }
    }

    public boolean submit(Order order) {
        return queue.offer(order);   // non-blocking; caller decides what to do on full
    }

    private void consume() {
        while (running.get() || !queue.isEmpty()) {
            try {
                Order o = queue.poll(200, TimeUnit.MILLISECONDS);
                if (o != null) process(o);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return;
            } catch (Throwable t) {
                log.error("order processing failed", t);   // don't kill the consumer
            }
        }
    }

    public void shutdown() throws InterruptedException {
        running.set(false);
        for (Thread t : consumers) t.join(5000);
    }
}
Where you'd use this

Internal job queue (no Kafka), email sender batching, log shipper, write-behind cache. The bounded queue is the key — it provides backpressure: if consumers can't keep up, offer returns false and the producer can either drop, retry, or fail-fast.

22.2 Rate Limiter

Two flavours: concurrent-call limiter and requests-per-second.

Concurrent limit (Semaphore)

public class ConcurrencyLimiter {
    private final Semaphore permits;
    public ConcurrencyLimiter(int max) { permits = new Semaphore(max, true); }

    public <T> T execute(Callable<T> op) throws Exception {
        if (!permits.tryAcquire(100, TimeUnit.MILLISECONDS))
            throw new RateLimitExceeded();
        try { return op.call(); }
        finally { permits.release(); }
    }
}

Token bucket (rate-per-second)

Use Guava's RateLimiter or Resilience4j's. Rolling-your-own is rarely worth it. The classic algorithm:

public class TokenBucket {
    private final long capacity;
    private final double refillPerNanos;
    private double tokens;
    private long lastRefillNs;

    public synchronized boolean tryConsume(int n) {
        refill();
        if (tokens >= n) { tokens -= n; return true; }
        return false;
    }

    private void refill() {
        long now = System.nanoTime();
        tokens = Math.min(capacity, tokens + (now - lastRefillNs) * refillPerNanos);
        lastRefillNs = now;
    }
}
Where you'd use this

Throttle outbound calls to a 3rd-party API (Stripe limits 100 req/s; Twilio 1 req/s/number). Per-customer quota. Defending your own API from abusive clients.

22.3 Parallel API Aggregator

(See full example in Part 14.10.) The skeleton:

public Dashboard load(long uid) {
    var u = call(() -> userClient.find(uid),     User.empty());
    var o = call(() -> orderClient.list(uid),    List.of());
    var w = call(() -> walletClient.balance(uid), Wallet.empty());
    return CompletableFuture.allOf(u, o, w)
        .thenApply(v -> new Dashboard(u.join(), o.join(), w.join()))
        .orTimeout(2, TimeUnit.SECONDS)
        .exceptionally(ex -> Dashboard.empty())
        .join();
}
Where you'd use this

Anywhere you build a "page" from multiple microservices: e-commerce product page (catalog + reviews + recommendations + price), banking dashboard, social feed. The graceful degradation (returning empty() on failure) is what keeps your page rendering when one downstream is down.

22.4 Background Job Processor with Retry

public class JobRunner {
    private final ScheduledExecutorService scheduler =
        Executors.newScheduledThreadPool(2);
    private final ExecutorService workers;

    public void submit(Job job) {
        run(job, 0);
    }

    private void run(Job job, int attempt) {
        workers.submit(() -> {
            try {
                job.execute();
                metrics.success(job.name);
            } catch (RuntimeException e) {
                metrics.failure(job.name);
                if (attempt < job.maxAttempts) {
                    long delay = (long)(Math.pow(2, attempt) * 100) + jitter();
                    log.warn("job {} failed (attempt {}), retrying in {}ms", job.name, attempt, delay);
                    scheduler.schedule(() -> run(job, attempt + 1), delay, TimeUnit.MILLISECONDS);
                } else {
                    log.error("job {} dead-lettered after {} attempts", job.name, attempt);
                    deadLetter(job, e);
                }
            }
        });
    }

    private long jitter() { return ThreadLocalRandom.current().nextInt(100); }
}
Why exponential backoff + jitter?

Without jitter, all retries from a fleet sync up — they retry simultaneously, creating "thundering herd" spikes that crash whatever they're calling. Jitter desynchronises them. AWS published this concept in their famous "Exponential Backoff and Jitter" article.

22.5 Concurrent Web Scraper

Crawl a list of URLs in parallel, with limits and timeouts.

public class Scraper {
    private final HttpClient http = HttpClient.newHttpClient();
    private final ExecutorService pool;
    private final Semaphore domainPermits = new Semaphore(5);   // be polite per domain

    public Map<String, String> scrape(List<String> urls) {
        List<CompletableFuture<Map.Entry<String, String>>> futures = urls.stream()
            .map(url -> CompletableFuture.supplyAsync(() -> {
                try {
                    domainPermits.acquire();
                    try {
                        HttpRequest req = HttpRequest.newBuilder(URI.create(url))
                            .timeout(Duration.ofSeconds(5)).build();
                        return Map.entry(url, http.send(req, HttpResponse.BodyHandlers.ofString()).body());
                    } finally { domainPermits.release(); }
                } catch (Exception e) {
                    log.warn("scrape {} failed", url, e);
                    return Map.entry(url, "");
                }
            }, pool))
            .toList();

        return futures.stream()
            .map(CompletableFuture::join)
            .filter(e -> !e.getValue().isEmpty())
            .collect(Collectors.toMap(Map.Entry::getKey, Map.Entry::getValue));
    }
}

With virtual threads (Java 21+), drop the Semaphore complication and just use Executors.newVirtualThreadPerTaskExecutor() for the pool — let each scrape have its own VT.

22.6 Connection Pool

The HikariCP/JDBC connection pool, simplified:

public class ConnectionPool {
    private final BlockingQueue<Connection> pool;
    private final Supplier<Connection> factory;

    public ConnectionPool(int size, Supplier<Connection> factory) {
        this.factory = factory;
        pool = new ArrayBlockingQueue<>(size);
        for (int i = 0; i < size; i++) pool.add(factory.get());
    }

    public Connection acquire(Duration timeout) throws InterruptedException {
        Connection c = pool.poll(timeout.toMillis(), TimeUnit.MILLISECONDS);
        if (c == null) throw new PoolExhaustedException();
        if (!c.isValid(1)) { c.close(); return factory.get(); }
        return c;
    }

    public void release(Connection c) {
        if (c != null) pool.offer(c);
    }
}

// Usage
Connection c = pool.acquire(Duration.ofSeconds(5));
try { /* use c */ }
finally { pool.release(c); }
Real case: pool exhaustion

The single most common production outage: code that forgets to release a connection on the error path. Every error leaks a connection. After enough errors, the pool is empty and ALL requests block on acquire. Lesson: always use try/finally or try-with-resources for any pooled resource. Or use Spring's JdbcTemplate which handles it automatically.

22.7 TTL Cache

public class TtlCache<K, V> {
    private record Entry<V>(V value, long expiresAtMs) {}

    private final ConcurrentHashMap<K, Entry<V>> map = new ConcurrentHashMap<>();
    private final long ttlMs;
    private final Function<K, V> loader;

    public V get(K k) {
        long now = System.currentTimeMillis();
        Entry<V> e = map.get(k);
        if (e != null && e.expiresAtMs > now) return e.value;

        // computeIfAbsent makes the load atomic for the same key
        return map.compute(k, (key, existing) -> {
            if (existing != null && existing.expiresAtMs > now) return existing;
            return new Entry<>(loader.apply(key), now + ttlMs);
        }).value;
    }

    public void cleanupExpired() {
        long now = System.currentTimeMillis();
        map.entrySet().removeIf(e -> e.getValue().expiresAtMs <= now);
    }
}
Cache stampede

If 1000 threads all miss the cache simultaneously and call loader, you've just DDOS'd your DB. The compute above prevents this per-key — only one loader runs at a time per key. For production, use Caffeine — it has AsyncLoadingCache, refresh-ahead, weight-based eviction, etc.

22.8 Pipeline / Map-Reduce

Multi-stage processing where each stage runs concurrently.

public class EventPipeline {
    private final BlockingQueue<RawEvent>     in     = new ArrayBlockingQueue<>(1000);
    private final BlockingQueue<ParsedEvent>  parsed = new ArrayBlockingQueue<>(1000);
    private final BlockingQueue<EnrichedEvent> enriched = new ArrayBlockingQueue<>(1000);

    public void start() {
        // Stage 1: parse (CPU-bound)
        startStage(in, parsed, this::parse, 4);

        // Stage 2: enrich (I/O-bound — talks to DB)
        startStage(parsed, enriched, this::enrich, 20);

        // Stage 3: persist
        startStage(enriched, null, this::persist, 4);
    }

    private <A, B> void startStage(BlockingQueue<A> src, BlockingQueue<B> dst,
                                      Function<A, B> fn, int n) {
        for (int i = 0; i < n; i++) {
            new Thread(() -> {
                while (!Thread.currentThread().isInterrupted()) {
                    try {
                        A a = src.take();
                        B b = fn.apply(a);
                        if (dst != null) dst.put(b);
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                    }
                }
            }).start();
        }
    }
}

Each stage has its own pool sized for its workload (CPU stages get N_cpu threads; I/O stages get many more). Bounded queues between stages provide automatic backpressure: if "persist" is slow, "enrich" stalls, which stalls "parse", which signals upstream to slow down.

22.9 Double-Checked Locking Singleton (and the holder idiom)

The classic "lazy thread-safe singleton" problem.

Wrong (the broken pre-Java-5 version)

public class BrokenSingleton {
    private static BrokenSingleton instance;     // no volatile!
    public static BrokenSingleton get() {
        if (instance == null) {
            synchronized (BrokenSingleton.class) {
                if (instance == null) instance = new BrokenSingleton();
            }
        }
        return instance;
    }
}
// Bug: another thread can read non-null but PARTIALLY constructed instance
//      (write of "instance =" can be reordered before constructor finishes).

Correct DCL (Java 5+ with volatile)

public class DclSingleton {
    private static volatile DclSingleton instance;
    public static DclSingleton get() {
        DclSingleton local = instance;
        if (local == null) {
            synchronized (DclSingleton.class) {
                local = instance;
                if (local == null) instance = local = new DclSingleton();
            }
        }
        return local;
    }
}

Best — initialization-on-demand holder idiom

public class HolderSingleton {
    private HolderSingleton() {}
    private static class Holder {
        static final HolderSingleton INSTANCE = new HolderSingleton();

    public static HolderSingleton get() { return Holder.INSTANCE; }
}

22.10 Circuit Breaker

Protect your service from cascading failures when a downstream is sick.

┌─ CLOSED ─┐ failure threshold reached ┌─ OPEN ─┐ │ pass-thru│ ──────────────────────────────▶ │ reject │ │ count │ │ all │ │ failures │ ◄─────────────── success └───┬────┘ └─────┬────┘ ┌─ HALF-OPEN ─┐ │ timeout │ │ allow ONE │ ◀──┘ │ ◄──────── failure ────┤ test call │ └──────┬──────┘ │ success ▼ close again 
public class CircuitBreaker {
    enum State { CLOSED, OPEN, HALF_OPEN }

    private final int failureThreshold;
    private final long openDurationMs;
    private final AtomicReference<State> state = new AtomicReference<>(State.CLOSED);
    private final AtomicInteger failures = new AtomicInteger();
    private volatile long openedAt;

    public <T> T execute(Callable<T> op, T fallback) throws Exception {
        State s = state.get();
        if (s == State.OPEN) {
            if (System.currentTimeMillis() - openedAt > openDurationMs) {
                state.compareAndSet(State.OPEN, State.HALF_OPEN);
            } else return fallback;
        }
        try {
            T r = op.call();
            onSuccess();
            return r;
        } catch (Exception e) {
            onFailure();
            return fallback;
        }
    }

    private void onSuccess() {
        failures.set(0);
        state.set(State.CLOSED);
    }
    private void onFailure() {
        if (failures.incrementAndGet() >= failureThreshold) {
            if (state.compareAndSet(State.CLOSED, State.OPEN) ||
                state.compareAndSet(State.HALF_OPEN, State.OPEN)) {
                openedAt = System.currentTimeMillis();
                log.warn("Circuit OPENED");
            }
        }
    }
}
Where you'd use this

Around any external dependency: payment gateway, recommendation service, fraud check API. Without it, when downstream gets slow, your threads pile up waiting → your own service goes down → cascading failure. Production apps usually use Resilience4j rather than rolling their own.

22.11 Distributed Counter (eventual consistency)

For high-write counters (page views, likes), avoid contention with sharding.

public class ShardedCounter {
    private final AtomicLong[] shards;
    public ShardedCounter(int shardCount) {
        shards = new AtomicLong[shardCount];
        for (int i = 0; i < shardCount; i++) shards[i] = new AtomicLong();
    }
    public void inc() {
        shards[ThreadLocalRandom.current().nextInt(shards.length)].incrementAndGet();
    }
    public long value() {
        long total = 0;
        for (AtomicLong s : shards) total += s.get();
        return total;
    }
}

This is what LongAdder does internally. Use LongAdder for in-process; for distributed, use Redis INCR shards keyed by hash, then sum.

22.12 Graceful Shutdown

The pattern that prevents data loss during deploys.

public class GracefulApp {
    private final ExecutorService workers;
    private final ScheduledExecutorService scheduler;
    private final DataSource ds;

    public void start() {
        Runtime.getRuntime().addShutdownHook(new Thread(this::shutdown, "shutdown-hook"));
    }

    public void shutdown() {
        log.info("Graceful shutdown starting");

        // 1. Stop accepting new work (e.g., set health check to "draining")
        healthCheck.setStatus("DRAINING");

        // 2. Let load balancer notice (typically 5–30s)
        sleepQuietly(10_000);

        // 3. Stop schedulers
        scheduler.shutdown();
        awaitOrLog(scheduler, Duration.ofSeconds(10), "scheduler");

        // 4. Drain workers
        workers.shutdown();
        awaitOrLog(workers, Duration.ofSeconds(30), "workers");
        if (!workers.isTerminated()) workers.shutdownNow();

        // 5. Close I/O
        try { ((HikariDataSource)ds).close(); } catch (Exception e) { log.warn("ds close", e); }

        log.info("Graceful shutdown complete");
    }

    private void awaitOrLog(ExecutorService e, Duration d, String name) {
        try {
            if (!e.awaitTermination(d.toSeconds(), TimeUnit.SECONDS))
                log.warn("{} did not terminate within {}", name, d);
        } catch (InterruptedException ex) {
            Thread.currentThread().interrupt();
        }
    }
}
Real case: deploy lost orders

An e-commerce team deployed via rolling restart. Each restart killed pods mid-request. ~50 orders/day lost during deploys, traced months later. Fix: graceful shutdown + Kubernetes preStop hook + 30s grace period. Lost orders → 0.

Part 23 — Anti-Patterns (don't do these)

23.1 Calling Thread.stop()

Deprecated since Java 1.2. It releases all locks instantly, leaving locked data structures in inconsistent states. Use interrupt().

23.2 synchronized(this) in library code

Anyone holding a reference to your object can synchronize on it and starve you. Always use a private final lock object.

23.3 Calling external code while holding a lock

synchronized(lock) {
    for (Listener l : listeners) l.onEvent(e);   // listener might block, deadlock, take forever
}

Fix: snapshot under the lock, dispatch outside.

List<Listener> snapshot;
synchronized(lock) { snapshot = new ArrayList<>(listeners); }
for (Listener l : snapshot) l.onEvent(e);

23.4 Sharing SimpleDateFormat across threads

It's not thread-safe. Two threads using the same instance produce garbage dates. Use DateTimeFormatter (Java 8+) or a ThreadLocal.

23.5 Using HashMap from multiple threads

Pre-Java-8 it could spin-loop forever during concurrent rehash. Even now, it can drop entries or report wrong sizes. Use ConcurrentHashMap.

23.6 Returning null from a Future-returning method on error

Caller now has to check both the returned null AND future.get(). Always return a failed future:

return CompletableFuture.failedFuture(e);

23.7 Holding a database connection while calling external HTTP

try (Connection c = ds.getConnection()) {
    User u = repo.find(c, id);
    EnrichResult er = httpClient.enrich(u);   // 200ms — connection held this whole time!
    repo.update(c, u, er);
}

Connection pool will exhaust under load. Fix: get the user (close connection), call HTTP, then re-acquire connection to update.

23.8 Optimistic spinning without bound

while (!atomicRef.compareAndSet(curr, next)) { curr = atomicRef.get(); }   // busy-loop

Under high contention this burns CPU. Either use LongAdder, fall back to a lock after N retries, or use updateAndGet which has a controlled loop.

23.9 Sleeping inside a critical section

synchronized(lock) {
    state.update();
    Thread.sleep(5000);   // blocks everyone else for 5 seconds
}

23.10 Treating InterruptedException as a regular exception

try { Thread.sleep(100); }
catch (InterruptedException e) { log.warn("interrupted"); }   // flag LOST

Always either propagate or restore the flag (Thread.currentThread().interrupt()).

23.11 Mixing synchronized and Lock on the same data

Two locking schemes don't compose — you'll have races. Pick one and stick with it.

23.12 Using volatile for compound updates

private volatile int count;
public void inc() { count++; }   // race

23.13 Unbounded queues in production thread pools

Memory grows until OOM. Always bound your queues. We covered this in Part 12.

23.14 Logging from inside a hot lock

synchronized(lock) {
    state.update();
    log.debug("updated");   // log appender might block on I/O
}

Async appenders mitigate this; better — log outside the lock.

23.15 Catching Throwable in a thread's run and silently continuing

Hides corruption (e.g., OutOfMemoryError). Catch specific exceptions; let Errors propagate to the uncaught handler.

24.6 Checklist for diagnosing concurrency bugs

  1. Reproduce. Run in a tight loop with many threads. Add small random sleeps to widen race windows. Use chaos.
  2. Identify shared state. Anything mutable visible to >1 thread is suspect.
  3. Check the guards. Every read AND every write must be: under the same lock, OR volatile (visibility only), OR atomic.
  4. Spot compound operations. map.get + map.put = bug. Use atomic compound methods.
  5. Take 3 thread dumps under load. Stack patterns reveal hotspots.
  6. Add structured logging. Include thread name + traceId in every log.
  7. Run tests with -Xcomp or -server — sometimes bugs only surface in optimised JIT code.

Part 25 — Best Practices & Design

25.1 The hierarchy of concurrency, from cheapest to most-expensive

  1. No shared state. Each thread has its own copy. No synchronization needed. Always the cheapest.
  2. Immutable shared state. Share-and-forget. Final fields, List.of(), records. Automatically thread-safe.
  3. Thread-confined state. Only one thread ever touches it. ThreadLocal, single-thread executor.
  4. Lock-free shared state. Atomics, ConcurrentHashMap, AtomicReference with immutable snapshots.
  5. Lock-protected shared state. Last resort. Use the smallest critical section possible.

25.2 Immutability is your superpower

public record User(String name, List<String> roles) {
    public User {                                // compact constructor
        roles = List.copyOf(roles);                  // defensive copy + unmodifiable
    }
}

Records (Java 14+) give you immutability with one line. Java 21+ adds @SuppressWarnings("preview") sealed hierarchies, etc.

25.4 Always-on production checklist

  • Every executor has a meaningful thread name prefix.
  • Every queue is bounded.
  • Every Future.get() has a timeout.
  • Every CompletableFuture chain has orTimeout + exceptionally.
  • Every ThreadLocal write is paired with remove() in a finally.
  • Graceful shutdown drains pools before stopping.
  • Periodic tasks have an outer try/catch that logs but doesn't propagate.
  • Critical sections don't perform I/O.
  • Separate pools for separate workloads.
  • Health check + circuit breakers around every external dependency.
  • Metrics: pool active count, queue depth, rejection count, deadlock count.

25.5 Designing scalable concurrent systems

  • Decompose by data, not code. Hash-partition work so different threads never touch the same data.
  • Prefer message passing over shared memory. Queues + workers beat shared maps + locks.
  • Bounded everything. Pools, queues, retries.
  • Backpressure is a feature. Make slow producers feel slowness; never let them outrun consumers silently.
  • Fail fast, recover gracefully. Every async boundary needs explicit error handling and a fallback.
  • Make work cancellable. Honor InterruptedException end-to-end.
  • Localise contention. Don't put hot data on the same cache line (false sharing); use @Contended or padding for the rare case it matters.

25.6 When NOT to use threads

  • The work is tiny (< 1ms) — overhead dwarfs gain.
  • The work is inherently sequential (must process events in order).
  • You're CPU-bound and already saturating cores.
  • Sharing state would be unavoidable and complex. Sequential code is easier to debug. Choose simplicity.

Part 26 — Interview Questions (with solutions)

30 questions ranging from junior to senior staff level. Try to answer each before opening the solution.

Conceptual

1. What's the difference between a process and a thread?

Processes have isolated memory; threads share heap memory within a process. Process creation is heavy (~ms); thread creation is light (~µs). Communication between threads is via shared variables; between processes via IPC. A bug in one thread can crash the whole process; processes don't share that fate.

2. Concurrency vs Parallelism?

Concurrency = multiple tasks in progress (possibly time-sliced on one core). Parallelism = multiple tasks executing simultaneously (requires multiple cores). Concurrency is about structure; parallelism is about execution.

3. Why is start() different from run()?

run() is just a method call — runs in the calling thread. start() asks the JVM to spawn a new OS thread which then calls run(). Calling start() twice throws IllegalThreadStateException.

4. What does volatile guarantee, and what does it NOT?

Guarantees: visibility (writes seen by all threads immediately) and ordering (no reordering across volatile access). Does NOT guarantee atomicity for compound operations like x++.

5. Why is count++ not thread-safe even with volatile?

It's three operations: read, increment, write. Two threads can both read 5, both write 6 — losing one increment. Volatile only fixes visibility, not atomicity. Use AtomicInteger or synchronized.

6. What's the happens-before relationship?

A partial order on actions defined by the JMM. If A happens-before B, then A's effects are visible to B and A appears to occur before B. Edges are created by: program order in same thread, lock release/acquire on same monitor, volatile write/read, thread start/join, etc.

7. Why must we use while not if with wait()?

Spurious wakeups: wait() can return without anyone calling notify. Even when notified, the condition might no longer hold by the time the awakened thread re-acquires the lock. Always re-check in a loop.

8. What's the difference between notify() and notifyAll()?

notify() wakes one arbitrary waiter on the monitor's wait set; notifyAll() wakes all. Prefer notifyAll unless all waiters wait on the exact same condition — otherwise you risk lost wakeups.

9. Explain the four conditions for deadlock.

Mutual exclusion, hold-and-wait, no preemption, circular wait. Break any one to prevent deadlock. Common preventions: lock ordering, tryLock with timeout, avoid nested locking.

10. What's livelock?

Threads keep responding to each other but make no progress. Like two polite people stepping aside in a corridor in sync forever. Fix: randomized backoff/jitter.

API & Usage

11. Runnable vs Callable?

Runnable.run() returns void and can't throw checked exceptions. Callable.call() returns a value and can throw. Use Callable when you need a result; submit it to an ExecutorService to get a Future.

12. What's wrong with Executors.newCachedThreadPool() in production?

Creates threads without bound. Under load, can spawn thousands and OOM the JVM. Build your own with ThreadPoolExecutor + bounded queue + sensible rejection policy.

13. Future vs CompletableFuture?

Future is blocking-only — you call get(). CompletableFuture adds composition: thenApply, thenCompose, thenCombine, allOf, error handling, timeouts, manual completion. Modern code should use CompletableFuture.

14. thenApply vs thenCompose?

thenApply(fn): fn returns a value, result is wrapped (CF<CF<T>> if fn returns CF). thenCompose(fn): fn returns another CF; flattens to CF<T>. Like map vs flatMap.

15. Why pass an explicit Executor to CompletableFuture.supplyAsync?

Without one, it uses ForkJoinPool.commonPool, which is sized for CPU work and shared with parallel streams. Blocking I/O on it stalls the whole JVM.

16. synchronized vs ReentrantLock?

Both are mutual-exclusive and reentrant. ReentrantLock adds tryLock with timeout, interruptible acquire, fair option, and multiple Conditions. Prefer synchronized for simplicity; reach for ReentrantLock when you need its features.

17. How does ConcurrentHashMap achieve concurrency?

Java 7: lock-striping (16 segments by default). Java 8+: per-bin CAS for inserts, synchronized only on collision chains. Reads are largely lock-free.

18. CountDownLatch vs CyclicBarrier?

Latch: one-shot, decoupled (anyone counts down, anyone awaits). Barrier: reusable, symmetric (N parties await each other). Latch for "wait for X events", Barrier for "N peers sync up".

19. What's ThreadLocal and what's its main pitfall?

Per-thread storage. Pitfall: in thread pools, threads live forever, so unremoved values cause memory leaks (also classloader leaks during webapp redeploys). Always remove() in a finally.

20. What are virtual threads and when would you use them?

Lightweight threads (Java 21+) scheduled by the JVM onto a small pool of carrier threads. When a VT blocks, the JVM unmounts it from the carrier so other VTs run. Use them for I/O-heavy "thread per request" workloads — millions are feasible. Don't use for CPU-bound work.

29. Why does this snippet sometimes never terminate? 
while (!stopped) { ... }

If stopped is non-volatile, the JIT can hoist the read out of the loop into a register — never reload. Visibility is broken. Fix: declare volatile boolean stopped, or use AtomicBoolean.

30. Senior question: how would you build a robust HTTP client?

Compose: connection pool (bounded), per-call timeout, retries with exponential backoff + jitter (idempotent calls only), circuit breaker, semaphore-based concurrency limit per host, structured logging with traceId via MDC. In Java, this is what Resilience4j provides; in Spring, layer it on a RestTemplate or WebClient. Don't roll all of this from scratch unless you have to — but understand each layer.
